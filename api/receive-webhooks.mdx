Nozle sends a JSON `POST` to your endpoint when something changes, for example `subscription.started` or `invoice.payment_status_updated`. This page is about those webhooks. For the events Stripe and Razorpay send to Nozle, see [Webhooks](/api/webhooks).

## Register an endpoint

Create an endpoint in the dashboard under **Developers > Webhooks**, or with `POST /webhook_endpoints`:

```json
{
  "webhook_endpoint": {
    "webhook_url": "https://app.example.com/nozle/webhooks",
    "signature_algo": "standard",
    "name": "Production",
    "event_types": ["subscription.started", "invoice.payment_status_updated"]
  }
}
```

`name` is a label. `event_types` limits the events the endpoint receives: leave it out, or send `null` or `["*"]`, to receive every type. `signature_algo` is `standard` (the default for new endpoints and the one to use), or the legacy `hmac` and `jwt`. Endpoints you created earlier keep their scheme until you change it. Each URL can be registered once per organization. The API reference has a Webhook Endpoints section.

The URL must be public. Nozle refuses private, loopback, link-local and cloud metadata addresses, both IP addresses and names that resolve to them, when you save the endpoint and again on every delivery. Use a tunnel to test against a local server.

Payloads carry only `nozle_id` and the plain key names. From Core 6.0.0 the former-prefix keys and the former `X-*-Signature` headers are gone: see [legacy key names](/api/api-standards#legacy-key-names-removed-in-core-600).

Each delivery is a JSON body with a `webhook_type` such as `subscription.started`, `livemode` (`false` for a [sandbox](/guides/getting-started/sandbox) delivery) and the object it is about, for example `subscription`. The [webhook events](/api/webhook-events) page lists every event type, when it fires and what its payload holds.

A failed credit note refund is sent as `credit_note.refund_failure`. An unknown type in `event_types` is rejected with a `422` `invalid_types` error. `credit_note.refund_failure` is accepted there; the former name `credit_note.provider_refund_failure` is still accepted and saved as `credit_note.refund_failure`, and endpoints saved with the former name are moved to it.

## Headers

| Header | Value |
|---|---|
| `webhook-id` | The delivery ID. It is the same on every attempt of one webhook. |
| `webhook-timestamp` | Unix time in seconds, set on each attempt, so it changes on every retry. |
| `webhook-signature` | One or more space-separated signatures, each written `v1,<base64>`. |
| `X-Nozle-Signature-Algorithm` | `standard`. |
| `X-Nozle-Unique-Key` | The same value as `webhook-id`, kept for receivers that already deduplicate on it. |

A `standard` delivery does not carry `X-Nozle-Signature`. `hmac` and `jwt` deliveries keep it, as described under [legacy schemes](#legacy-schemes-hmac-and-jwt).

## The `standard` scheme

`standard` follows the Standard Webhooks specification, so the same code works with any library that implements it.

- The endpoint secret looks like `whsec_` followed by Base64 text. Read it on the endpoint in **Developers > Webhooks**, or in the `secret` field of the endpoint (needs the `developers:manage` permission). Keep it on your server.
- The signed content is `webhook-id`, `.`, `webhook-timestamp`, `.` and the raw request body, joined as one string.
- The signature is `Base64(HMAC-SHA256(key, signed content))`. The key is the Base64-decoded part of the secret after `whsec_`.
- Reject a request whose `webhook-timestamp` is more than 5 minutes (300 seconds) from your clock, in either direction. This stops a replay of a captured request.
- Compare in constant time, and accept the request when any `v1` signature in the header matches. Ignore entries with another version.

### Rotate the secret

`POST /webhook_endpoints/{id}/rotate_secret` (or **Rotate secret** in the dashboard) creates a new secret and returns the endpoint. The previous secret keeps working for 24 hours, and the response has `previous_secret_expires_at`. During that time every delivery carries two signatures in `webhook-signature`, one per secret, so you can deploy the new secret without dropping a delivery. Configure the new secret, then stop using the old one. Verification that accepts any listed signature handles both without changes.

## Verify the signature

Verify the **raw request body** before you parse it. A framework that parses and re-serialises the JSON can change the bytes and break the check.

### With the SDK

The server SDKs verify the headers, the timestamp and the signature, make no network call for `standard`, and return the parsed event. Pass the endpoint secret; pass both secrets while you rotate. `standard` verification requires `@nozle-js/node` `0.23.0`, `nozle-sdk` `0.23.0` or `github.com/nozle-dev/nozle-go` `v0.22.0`.

<Tabs>
<Tab title="Node.js">
```ts
import { Nozle, createWebhookHandler } from '@nozle-js/node'

const nozle = new Nozle()

// Next.js route handler, Remix, Hono, Bun or Deno: answers 200, 400 when the request is not genuine,
// 405 for a method other than POST, or 500 when onEvent throws.
export const POST = createWebhookHandler(nozle, {
  secret: process.env.NOZLE_WEBHOOK_SECRET, // a string, or an array while you rotate
  onEvent: async (event) => {
    if (await alreadyHandled(event.id)) return
    if (event.type === 'subscription.started') await activate(event.object)
  },
})
```

Elsewhere, call `nozle.webhooks.verify({ body, headers, secret })` with the raw body; it throws `WebhookVerificationError` with a `code`. `toleranceSeconds` changes the 300-second window.

### Without the SDK

<Tabs>
<Tab title="Node.js">
```ts
import { createHmac, timingSafeEqual } from 'node:crypto'

function isValid(rawBody: Buffer, headers: Record<string, string>, secret: string): boolean {
  const id = headers['webhook-id']
  const timestamp = headers['webhook-timestamp']
  const signatures = headers['webhook-signature']
  if (!id || !timestamp || !signatures) return false
  if (!/^\d+$/.test(timestamp) || Math.abs(Date.now() / 1000 - Number(timestamp)) > 300) return false
  const key = Buffer.from(secret.replace(/^whsec_/, ''), 'base64')
  const expected = createHmac('sha256', key).update(`${id}.${timestamp}.`).update(rawBody).digest()
  return signatures.split(' ').some((entry) => {
    const [version, value] = entry.split(',')
    if (version !== 'v1' || !value) return false
    const received = Buffer.from(value, 'base64')
    return received.length === expected.length && timingSafeEqual(received, expected)
  })
}
```
</Tab>
<Tab title="Python">
```python
import base64, hashlib, hmac, time

def is_valid(raw_body: bytes, headers: dict, secret: str) -> bool:
    webhook_id = headers.get("webhook-id")
    timestamp = headers.get("webhook-timestamp")
    signatures = headers.get("webhook-signature")
    if not (webhook_id and timestamp and signatures) or not timestamp.isdigit():
        return False
    if abs(time.time() - int(timestamp)) > 300:
        return False
    key = base64.b64decode(secret.removeprefix("whsec_"))
    signed = f"{webhook_id}.{timestamp}.".encode() + raw_body
    expected = hmac.new(key, signed, hashlib.sha256).digest()
    for entry in signatures.split():
        version, _, value = entry.partition(",")
        if version == "v1" and hmac.compare_digest(base64.b64decode(value), expected):
            return True
    return False
```

## Legacy schemes: `hmac` and `jwt`

Endpoints created before `standard` can keep `hmac` or `jwt`. Their deliveries carry `X-Nozle-Signature`, `X-Nozle-Signature-Algorithm` (`jwt` or `hmac`) and `X-Nozle-Unique-Key`. These signatures have no timestamp, so a replayed request cannot be rejected by its age. To move an endpoint, update it with `signature_algo: "standard"` and deploy a verifier that reads the `webhook-*` headers; the SDK verifiers read the `X-Nozle-Signature-Algorithm` header on each request and handle all three. Each of these headers is also still sent under its former-prefix name.

For `hmac` and `jwt`, the SDK takes `hmacKey` (Python `hmac_key`, Go `hmacKey`) as before, and `jwt` needs no secret because the SDK reads Nozle's public key once with your secret key.

### Verify `hmac` by hand

The signature is `Base64(HMAC-SHA256(hmac_key, raw body))`. The `hmac_key` is your organization's signing secret, shown on the **Developers > Webhooks** page of the dashboard.

<Tab title="Node.js">
```ts
import { createHmac, timingSafeEqual } from 'node:crypto'

function isValid(rawBody: Buffer, signature: string, hmacKey: string): boolean {
  const expected = createHmac('sha256', hmacKey).update(rawBody).digest()
  const received = Buffer.from(signature, 'base64')
  return received.length === expected.length && timingSafeEqual(received, expected)
}
```

		return false

### Verify `jwt` by hand

The signature is an RS256 JWT. Its claims are `data`, the payload as a JSON string, and `iss`. Fetch the public key from `GET /webhooks/json_public_key` with your secret key. The response is `{"webhook": {"public_key": "..."}}`, where the key is the PEM text encoded in Base64.

```ts
import jwt from 'jsonwebtoken'

const pem = Buffer.from(publicKeyBase64, 'base64').toString('utf8')
const claims = jwt.verify(signature, pem, { algorithms: ['RS256'] }) as { data: string }
const isGenuine = claims.data === rawBody.toString('utf8')
```

Cache the key; it changes only when Nozle rotates it. The older `GET /webhooks/public_key` returns the same key as plain text and is deprecated.

## Webhooks to the Engine

An endpoint that points at Nozle's Engine (`/webhooks/nozle`) is verified with the sending organization's own signing key, the same `hmac_key` as above. It must use the `hmac` signature algorithm: `jwt` endpoints are rejected. An unsigned, forged or cross-organization request, or one whose organization is unknown, gets `401` in every environment and nothing is processed. If Nozle cannot read the key, the Engine answers `503` and Core retries. A signed webhook that names another organization's subscription does not create that subscription's credit grants.

## Delivery, retries and ordering

- Respond with a `2xx` within 10 seconds. A `3xx` is a failure: Nozle does not follow redirects, so register the final URL. Any other status, a timeout or a connection error is a failed attempt.
- Nozle makes up to 8 attempts. After a failed attempt it waits 5 seconds, 5 minutes, 30 minutes, 2 hours, 5 hours, 10 hours and 10 hours, each with up to 15% extra delay. After the eighth failure the webhook is marked failed.
- To stop retries of one webhook, answer with the response header `webhook-delivery: abort-message`. Use it for a delivery you will never accept, such as an event for an account you no longer have.
- Delivery is at least once. Deduplicate on `webhook-id`, which is the same on every attempt. The `webhook-timestamp` is new on every attempt, so verify each attempt against its own timestamp.
- Order is not guaranteed. Treat a payload as the state of the object at that moment and read the object from the API when you need the latest.
- Return `200` for event types you do not handle, so they are not retried.

Nozle keeps delivery records for 90 days.

### An endpoint that keeps failing

When an endpoint has failed deliveries and has had no successful delivery for 5 days, Nozle disables it: `disabled_at` is set, you receive the `webhook_endpoint.failing` email, and no new webhooks are created for it. Fix your receiver, then re-enable it with `PUT /webhook_endpoints/{id}` and `"disabled": false`, or in the dashboard.

### Replay, recover and test

- `GET /webhooks` lists deliveries. Filter by `status`, `webhook_endpoint_id`, `webhook_type` and a date range.
- `POST /webhooks/{id}/retry` sends one delivery again, with its original `webhook-id`.
- `POST /webhook_endpoints/{id}/recover` with `{"since": "2026-10-28T00:00:00Z"}` sends again every failed delivery of the endpoint since that time, up to 14 days back. Deduplicate on `webhook-id`, as always.
- `POST /webhook_endpoints/{id}/test` sends a test event to the endpoint, signed like any other delivery.
