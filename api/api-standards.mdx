## Requests and responses

Nozle APIs use JSON request and response bodies. Send:

```http
Content-Type: application/json
Accept: application/json
Authorization: Bearer sk_nozle_your_secret_key
```

Every response to an accepted API key carries `X-Nozle-Livemode: true` for your live organization or `false` for your [sandbox](/guides/getting-started/sandbox) (_Unreleased_).

Response timestamps use ISO 8601 UTC strings. Request timestamps follow each endpoint: [Feature Events](/api/events), [Cost Events](/api/cost-events) and [credit usage](/api/usage-track) accept Unix seconds (a number or a numeric string) or an RFC 3339 string with a time zone offset or `Z`. For Cost Events and credit usage the broader forms are available from the Engine release that includes this change; before it, credit usage takes RFC 3339 only and Cost Events take a number only. A date without a time and a time without an offset are rejected everywhere. Monetary amounts use integer minor units, such as cents, unless an endpoint explicitly documents a decimal string.

## Pagination

Collection endpoints use `page` and `per_page` query parameters. Paginated responses include metadata with the current page, adjacent pages, total pages, and total record count.

```json
{
  "meta": {
    "current_page": 1,
    "next_page": 2,
    "prev_page": null,
    "total_pages": 4,
    "total_count": 70
  }
}
```

## External identifiers

Prefer stable external identifiers from your own system when an endpoint accepts them. They make reconciliation easier and prevent your application from depending on database-generated UUIDs.

## Idempotency and retries

For metered events and credit operations, generate a unique transaction or idempotency identifier and reuse it when retrying the same logical operation. Do not generate a new identifier after a timeout unless you intend to create a second operation.

Retry transient network failures and HTTP `429` or `5xx` responses with exponential backoff and jitter. Do not automatically retry validation or authorization failures.

The Node.js, Python, and Go SDKs do not retry unless you turn it on (`maxRetries`, `max_retries`, `WithMaxRetries`); the setting retries only requests that are safe to repeat. To retry in your own code, do it only after a network error, a `429`, or a `5xx`, and send the same idempotency key with the same request, including its timestamp.

## Errors

Use the HTTP status code as the primary error category and log the response body for diagnosis. Common statuses include:

| Status | Meaning |
|---|---|
| `400` | Malformed request |
| `401` | Missing or invalid authentication |
| `403` | Authenticated but not permitted |
| `404` | Resource not found |
| `422` | Valid JSON with invalid resource attributes |
| `429` | Request rate exceeded |
| `5xx` | Temporary server failure |

See [Errors](/api/errors) for retry guidance and application-safe handling.

## Compatibility names

Some inherited response properties retain compatibility names from the underlying billing contract. Use the exact names displayed in the generated endpoint schemas. Those names can change, and a change is announced in the [changelog](/changelog) first.

### Legacy key names (removed in Core 6.0.0)

API 1.0.0 renamed the identifier keys of REST responses, webhook payloads and CSV exports and the EU tax codes to `nozle_` (`nozle_id`) or to no prefix (`customer_id`, `plan_id`). Core 3.7.0 brought the former names back next to the new ones for a deprecation window. **Core 6.0.0 ends that window early: the former names are gone everywhere, and the earlier end date no longer applies.** The public API carries only the Nozle names. This is a breaking change.

- **Responses and webhook payloads** carry no key with the former product prefix. Read `nozle_id`, and the plain key names such as `customer_id`, `invoice_id`, `subscription_id`, `plan_id`, `fee_id` and `wallet_id`. This includes the fee estimates of `POST /events/estimate_instant_fees` and `batch_estimate_instant_fees` and `POST /credit_notes/estimate`.
- **Older SDK versions break.** nozle-js older than 0.10.0 (Node), nozle-python older than 0.10.0 and nozle-go older than 0.9.1 read a credit system's id only from the former key. Against Core 6.0.0 the credit system `id` is empty (Node, Go) or the call raises `NozleAPIError` (Python). Upgrade the SDK before Core 6.0.0.
- **CSV exports** (invoices, invoice fees, credit notes, credit note items) no longer repeat the id columns at the end under their former names. Read the `*nozle_id` columns, by column name.
- **EU tax codes:** the former `*_eu_*` codes no longer resolve to `nozle_eu_*`, in `tax_codes` inputs or in `GET`, `PUT` and `DELETE /taxes/{code}`. Send the `nozle_eu_*` code; an old code returns `404` or is refused like any unknown code.
- **Webhook headers:** deliveries carry `webhook-id`, `webhook-timestamp` and `webhook-signature` (the `standard` scheme). Verify with those.
- **Request headers and inputs:** send `x-nozle-organization` (the former organization header is no longer read), and `invoice_ids` on `POST /payment_requests` (the former `*_invoice_ids` input is refused). Wallet `recurring_transaction_rules[]` name an existing rule with `nozle_id`. A renewed dashboard session token comes back in the `x-nozle-token` response header only.
- **Stripe metadata:** Nozle writes `nozle_*` metadata keys on the Stripe objects it creates (`nozle_customer_id`, `nozle_invoice_id`, `nozle_payable_id`, `nozle_payable_type`, `nozle_payment_id`, `nozle_credit_note_id`, `nozle_organization_id`, `nozle_billing_entity_id`). Objects created before Core 6.0.0 keep the old keys, and Nozle still settles their payments by the provider id. See [Stripe](/integrations/stripe#metadata-on-stripe-objects).

Event properties you send are never changed.
