_Unreleased._ Nozle limits how fast one workspace can call its APIs, so that a runaway loop in one integration cannot slow down billing for everyone else. The Engine API (usage, credits, checkout, the LLM proxy and event ingestion) has its limits from Engine 2.61.0. Core's REST API keeps its own per-minute limit.

## Engine API limits

The Engine counts per workspace, and every server that uses the workspace's keys shares the same limits. A live workspace and its [sandbox](/guides/getting-started/sandbox) are counted separately.

| Limit | Live | Sandbox | Counted against |
|---|---|---|---|
| Requests | 100 per second | 25 per second | The workspace |
| Events | 5,000 per second | 500 per second | The workspace |
| In flight | 50 at once | 50 at once | Each API key |

**Requests.** Every call made with an API key counts as one request: `/can`, `/usage/check`, credit balances and operations, holds, checkout, the plan catalog, margin reads, `POST /events/{transaction_id}/void` and the [LLM proxy](/api/llm-proxy). A full second's worth can be sent at once, then the allowance refills continuously, so 100 requests at once is fine, and so is a steady 100 per second.

**Events.** Ingestion counts events instead of requests, and does not use the request allowance:

| Call | Counts |
|---|---|
| `POST /events` | 1 event |
| `POST /events/batch` | The number of events in the batch |
| `POST /usage/track` | 1 event |
| `POST /usage/holds/{hold_id}/finalize` | 1 event |

A batch can still hold up to 5,000 events. A batch larger than the per-second rate (for example 5,000 events in a sandbox) is accepted when the workspace sent no events in the last second. The events after it then wait until that batch is paid for at the sandbox rate.

**In flight.** One API key can have at most 50 requests open at the same time. Event ingestion and the LLM proxy hold no slot, so long streamed model calls never block your other calls. LLM proxy calls still count against the request rate.

Calls Core makes to the Engine on your behalf are never limited.

## What a refused call looks like

A call over a limit does nothing and answers `429`:

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 1
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1
Content-Type: application/json

{
  "status": 429,
  "code": "rate_limited",
  "error": "Too many requests for this workspace: at most 100 per second. Retry after the Retry-After header.",
  "error_details": {
    "limit": "requests",
    "limit_value": 100
  }
}
```

`error_details.limit` says which limit was reached:

| `limit` | Meaning | `limit_value` |
|---|---|---|
| `requests` | The workspace sent more requests per second than its limit. | Requests per second |
| `events` | The workspace sent more events per second than its limit. | Events per second |
| `concurrency` | This API key already has its maximum of requests in flight. | Requests in flight |

The LLM proxy answers a `rate_limited` refusal in this Engine shape too, not in the provider's error shape. A `429` with the code `usage_limit_exceeded` from the proxy is a different thing: a customer's [usage limit](/guides/entitlements/spend-limits), which retrying does not fix.

## Headers

Every Engine call that was counted carries these headers, on success too, so you can slow down before you are refused:

| Header | Meaning |
|---|---|
| `X-RateLimit-Limit` | The limit the call was counted against: requests per second, or events per second on an ingestion call. On a `concurrency` refusal, the requests one key may have in flight. |
| `X-RateLimit-Remaining` | How many requests (or events) you can still send now without waiting. |
| `X-RateLimit-Reset` | Seconds until the limit is fully available again. |
| `Retry-After` | Only on a `429`. Seconds to wait before you retry, at least 1. |

The headers are missing when a call was not counted, for example when the limiter could not be reached and the call passed.

## Core API limits

Core's REST API (`https://api.nozle.app/core/api/v1`) counts requests per API key and per client IP address, each in a fixed one-minute window.

| Requests | Limit |
|---|---|
| Core REST API, per API key | 6,000 per minute |
| Core REST API, per IP address | 6,000 per minute |

Requests the Engine makes to Core on your behalf are not counted against your key. A request over the limit answers `429` with a `Retry-After` header, in seconds until the window ends, and this body:

```json
{
  "status": 429,
  "error": "Too Many Requests",
  "code": "rate_limited"
}
```

The dashboard's sign-in, sign-up, invitation and password-reset forms have their own limits. See [Sign-in limits](/guides/settings/account-security#sign-in-limits).

## Back off and retry

A refused call did nothing, so it is always safe to send again:

- Wait at least the `Retry-After` seconds, then retry. If the retry is refused again, double the wait each time and add random jitter, so your servers do not all retry at the same moment.
- Retry a mutation with the same `Idempotency-Key` and the same body, and an event with the same `transaction_id`.
- Send events in batches with [`POST /events/batch`](/api/events) instead of one request per event. A batch counts its events, not one request per event.
- Spread large jobs, such as imports or backfills, over several seconds or minutes instead of sending them in one burst. Watch `X-RateLimit-Remaining` to pace them.
- Keep fewer than 50 calls open per key. If you need more parallel work, queue it.

The Node.js, Python and Go SDKs retry a `429` up to 2 times by default, after the `Retry-After` seconds, and only for requests that are safe to repeat. See [API standards](/api/api-standards). A `429` with the code `usage_limit_exceeded` is never retried.

## Refusals in the request log

An Engine call refused with `429` appears in the [request log](/api/request-log), including refused event ingestion, so you can see which calls were limited and when.
