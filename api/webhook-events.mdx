Nozle sends one JSON `POST` per event to every endpoint of your organization that subscribes to the event type. There are 74 types. This page lists them all. Registering an endpoint, verifying the signature and the retry rules are in [Receive Nozle webhooks](/api/receive-webhooks).

Each event has its own page in the API reference under **Webhook Events**, with the payload schema and an example captured from Core.

## The delivery

Every delivery has the same envelope. `webhook_type` is the event type, `object_type` names the key that holds the object, `organization_id` is your organization, and `livemode` is `true` for your live organization and `false` for your [sandbox](/guides/getting-started/sandbox):

```json
{
  "webhook_type": "plan_upgrade_intent.needs_review",
  "object_type": "plan_upgrade_intent",
  "organization_id": "00000000-0000-4000-8000-000000000001",
  "livemode": true,
  "plan_upgrade_intent": {
    "nozle_id": "00000000-0000-4000-8000-000000000002",
    "status": "needs_review",
    "error_code": "plan_upgrade_apply_failed",
    "customer_id": "00000000-0000-4000-8000-000000000003",
    "subscription_id": "00000000-0000-4000-8000-000000000004",
    "target_plan_id": "00000000-0000-4000-8000-000000000005",
    "amount_cents": 919,
    "currency": "USD",
    "provider_payment_id": "pi_example",
    "created_at": "2026-10-12T22:20:28Z",
    "updated_at": "2026-10-22T07:10:02Z"
  }
}
```

- The object under `object_type` is the same object the REST API returns for that resource, so you can use one parser for both. A few events wrap it, for example `invoice.payment_dispute_lost` holds `{ "invoice": {...}, "provider_error": "..." }` under `payment_dispute_lost`.
- Payloads carry only the Nozle key names (`nozle_id` and the plain `<key>` names). From Core 6.0.0 the former-prefix keys are gone: see [legacy key names](/api/api-standards#legacy-key-names-removed-in-core-600).
- `livemode` is _Unreleased_. A sandbox delivery's `organization_id` is the sandbox's own organization ID. If one receiver takes both, check `livemode` before acting on an event.
- Examples are captured from Core with real identifiers replaced by placeholders.

## Choose the events you receive

An endpoint with no `event_types` receives every type, and gets every type Nozle adds later. To receive only some, send an array when you create or update the endpoint:

```json
{
  "webhook_endpoint": {
    "webhook_url": "https://app.example.com/nozle/webhooks",
    "name": "Production",
    "event_types": ["subscription.started", "invoice.payment_status_updated"]
  }
}
```

- `null` or `["*"]` means every type. An empty array is rejected.
- Names are trimmed and lower-cased. An unknown type is rejected with a `422` `invalid_types` error.
- `credit_note.provider_refund_failure` is the former name of `credit_note.refund_failure`. It is still accepted and saved under the new name.
- Respond `2xx` to types you do not handle, so Nozle does not retry them.

## All events

### Alerts

| Event | Object key | When it fires |
|---|---|---|
| `alert.triggered` | `triggered_alert` | A usage alert on a subscription (or a wallet balance alert) crosses one of its thresholds. |

### Customers

| Event | Object key | When it fires |
|---|---|---|
| `customer.created` | `customer` | A customer is created, from the API, the dashboard or an upsert that creates one. |
| `customer.updated` | `customer` | A customer is updated, from the API (an upsert on an existing `external_id`) or the dashboard. |
| `customer.accounting_provider_created` | `customer` | A customer is created in an accounting integration (for example NetSuite or Xero). |
| `customer.accounting_provider_error` | `accounting_provider_customer_error` | Syncing a customer to an accounting integration fails. |
| `customer.crm_provider_created` | `customer` | A customer is created in a CRM integration (for example HubSpot or Salesforce). |
| `customer.crm_provider_error` | `crm_provider_customer_error` | Syncing a customer to a CRM integration fails. The error object names the provider in `accounting_provider` and `accounting_provider_code`, the same keys as the accounting error. |
| `customer.payment_provider_created` | `customer` | A customer is created at a payment provider (Stripe, Razorpay and the other providers). |
| `customer.payment_provider_error` | `payment_provider_customer_error` | Creating or syncing a customer at a payment provider fails. |
| `customer.checkout_url_generated` | `payment_provider_customer_checkout_url` | A provider checkout URL is generated for a customer, for example to add a payment method. For a Stripe connection with a publishable key and a card-only customer, the URL is a Nozle-hosted card page, not stripe.com. |
| `customer.tax_provider_error` | `tax_provider_customer_error` | Fetching taxes for a customer from a tax integration (Anrok or Avalara) fails. |
| `customer.vies_check` | `customer` | The EU VAT number of a customer is checked against VIES. The `vies_check` field has the VIES answer, or the error when the check fails. |

### Payments

| Event | Object key | When it fires |
|---|---|---|
| `payment.succeeded` | `payment` | A payment succeeds at the provider (Stripe, Razorpay and the other providers). |
| `payment.requires_action` | `payment` | A payment needs the customer to act, for example 3D Secure authentication. `next_action` has the details. |
| `payment.scheduled` | `payment` | Nozle will debit a payment automatically from the customer's saved card or mandate. The payload is the payment plus `scheduled_at` (ISO 8601, UTC) and `method_type` (`card`, `upi` or `bank`). It is sent once per `scheduled_at`; a changed time sends it again. Nozle sends it for Stripe card payments that the bank debits after its notice, and for Razorpay card and UPI debits when the debit is scheduled (not for a bank eMandate, and not when `pre_debit_notice` is off). |
| `payment.schedule_cancelled` | `payment` | An automatic debit announced by `payment.scheduled` will not happen. The payload is the payment plus `scheduled_at` (the announced time) and `reason`: `mandate_changed`, `invoice_paid`, `invoice_voided`, `notice_failed` or `other`. It has no `method_type`, and it is sent only after `payment.scheduled` was sent for the payment. |
| `payment_provider.error` | `payment_provider_error` | A payment provider connection reports an error, for example when Nozle cannot register its webhook at Stripe. |
| `payment_request.created` | `payment_request` | A payment request is created, by dunning or automatically for an invoice that Core did not charge (`automatic` is `true`). |
| `payment_request.payment_failure` | `payment_provider_payment_request_payment_error` | A payment attempt for a payment request fails, or its Pay link cannot be built. `provider_error` says why, for example `payment_request_invoices_changed`. |
| `payment_request.payment_status_updated` | `payment_request` | The payment status of a payment request changes. An automatic request is closed when its invoice is paid another way, settled by a credit note or voided. |
| `plan_upgrade_intent.needs_review` | `plan_upgrade_intent` | A paid plan change cannot be applied and its intent goes to review. The payment is refunded. Sent once per intent, even when two payments of the same checkout are reviewed at the same moment. |

## Events to know about

### Sent only on some paths

- `fee.tax_provider_error` is reserved. You can subscribe to it, but Core has no code path that sends it today.
- `event.error` is deprecated. Use `events.errors`.
- `invoice.add_on_added` is not a Nozle event. Earlier versions of the API reference listed it, and no endpoint can subscribe to it.
- `customer.crm_provider_error` names the CRM in `accounting_provider` and `accounting_provider_code`, the keys the accounting error uses.

### `dunning.step`

_Unreleased (Core 11.16.0)._ Sent for each step of the [dunning policy](/guides/billing/dunning) of an unpaid invoice: `payment_failed` on day 0, `reminder`, `final_reminder`, `end_action` on the last day of the grace, and `resolved` once when the invoice no longer needs paying. Only campaigns with an end action send it; `dunning_campaign.finished` is unchanged for the others. `next_action` is the next step of the timeline (`retry` included) and is `null` after the last one and on `resolved`. The invoice and customer ids are left out of this example; the Dunning Campaigns webhook reference lists every key.

```json
{
  "webhook_type": "dunning.step",
  "object_type": "dunning_step",
  "organization_id": "00000000-0000-4000-8000-000000000001",
  "livemode": true,
  "dunning_step": {
    "invoice_number": "ACME-47DD-012-001",
    "external_customer_id": "customer_123",
    "dunning_campaign_code": "block_after_grace",
    "step": "reminder",
    "day": 3,
    "grace_days": 7,
    "end_action": "block",
    "started_at": "2026-10-20T09:00:00Z",
    "deadline_at": "2026-10-27T09:00:00Z",
    "next_action": "retry",
    "next_action_at": "2026-10-25T09:00:00Z",
    "total_due_amount_cents": 4900,
    "currency": "USD"
  }
}
```

### `payment_request.created` and `payment_request.payment_status_updated`

The payment request carries `automatic`: `true` for a request Core created itself for a finalized invoice it did not charge, `false` for one created by dunning or by hand. An automatic request is closed (`succeeded`, or `failed` when its invoice is voided) when its invoice is paid another way or settled by a credit note, and `payment_request.payment_status_updated` is sent. The `customer` and `invoices` fields are omitted from this example:
