## Base URLs

| Base URL | Endpoints |
|---|---|
| `https://api.nozle.app/engine/api/v1` | Usage events (`/events`, `/events/batch`), entitlements, checkout, margin, credits, and Nozle intelligence APIs |
| `https://api.nozle.app/core/api/v1` | Customers, plans, subscriptions, invoices, wallets, billing resources, and the public sign-up endpoints (`/auth/*`) |

## Credential model

| Key type | Prefix | Location | Access |
|---|---|---|---|
| Publishable | `pk_nozle_` (live), `pk_nozle_test_` (sandbox) | Browser | Alone: `GET /api/v1/plans` and `GET /api/v1/plans/{code}` only, which return the trimmed public plan. See the [public plan catalog](/api/list-plans). With a [customer token](#customer-tokens): also that one customer's entitlements, usage, credit balances and subscription, read only. |
| Secret | `sk_nozle_` (live), `sk_nozle_test_` (sandbox) | Trusted backend | Organization-scoped server operations allowed by the key's permissions |

Every key belongs to one organization. A [sandbox](/guides/getting-started/sandbox) is its own organization, linked to your live one, and its keys carry `_test_` in the prefix.

## Live and sandbox keys

Live and sandbox use the same API URLs. The key's organization decides which data a request reaches; the prefix must agree with it:

- A `sk_nozle_test_` or `pk_nozle_test_` key that belongs to a live organization, or a key without `_test_` that belongs to a sandbox, is refused with `401`.
- After a [sandbox reset](/guides/getting-started/sandbox#reset-the-sandbox), every key of the old sandbox is refused with `401`.
- Every response to an accepted key, including a `402` refusal, carries `X-Nozle-Livemode: true` for a live organization or `false` for a sandbox. Core REST, the Engine API, event ingestion and the LLM proxy send it, and browsers can read it. A `401` does not carry it.

| Response | Body |
|---|---|
| Core REST `401` | `{"status": 401, "error": "Unauthorized"}` |
| Engine API `401` | `{"error": "invalid api key"}` |

The `401` does not say which rule refused the key. Check the prefix against the environment you meant to use, and that the key is current.

Only members with the **Admin** role can create, rotate or delete secret keys in the dashboard. The **Finance** and **Manager** roles cannot.

## Store your key when you create it

The dashboard (and the GraphQL `createApiKey` and `rotateApiKey` mutations) show the full key once, when you create or rotate it (Core 7.0.0 and later). After that every read shows it masked, as `••••••••` and the last 3 characters, in the dashboard and in GraphQL (`apiKeys`, `apiKey(id)`, `updateApiKey`, `destroyApiKey`). A sandbox key keeps its prefix, for example `sk_nozle_test_••••••••a1b`. Nozle cannot show it again. Copy it into your secret manager straight away. If you lose a key, rotate it and update your backend with the new one. Rotating gives the new key the same permissions as the old one. When you rotate a key in the dashboard, choose how long the old key keeps working so you can deploy the new one first: it can stop at once, or after 1 hour, 24 hours or 7 days. GraphQL `rotateApiKey` takes the same choice as `expiresAt`; without it the old key stops at once.

Send server credentials as a Bearer token:

```http
Authorization: Bearer sk_nozle_your_secret_key
```

A publishable key alone never reads or changes a customer: customer reads and mutations return `403 publishable_key_not_allowed` even if a browser supplies an arbitrary customer ID. To let the browser read the signed-in customer's billing state, your backend mints a [customer token](#customer-tokens) for that customer. Checkout, invoices, previews, cancellation, top-ups and every other write go through an authenticated merchant backend: it derives the Nozle customer from the logged-in user or team and calls Nozle with a least-privilege `sk_`.

## Customer tokens

A customer token lets a browser read **one** customer's billing state with your publishable key, without a backend route per read. Core 11.66.0 and Engine 2.64.0.

1. Your backend mints a token for the signed-in customer with a secret key: [`POST /customer_tokens`](/api-reference/customers/create-a-customer-token) with `customer_id` (the customer's external ID, taken from your session, never from the browser), optional `ttl_seconds` and optional `features`. It answers `{"token": "...", "customer_id": "...", "expires_at": "..."}`. The key needs `customer:read`; a publishable key is refused.

   **A token lives at most one hour.** `ttl_seconds` is an integer from 60 to 3600, and defaults to 3600. Any other value answers `422`. Mint a new token when one expires.
2. The browser sends both credentials:

```http
Authorization: Bearer pk_nozle_your_publishable_key
X-Nozle-Customer-Token: <token>
```

A token is read-only, short-lived, and accepted only on these reads of its own customer:

| Service | Routes |
|---|---|
| Engine | `GET /can`, `GET /subscriptions/current`, `GET /billing/status`, `GET /customers/{customer}/credit-systems`, `GET /customers/{customer}/credit-systems/{code}/balance`, `GET /customers/{customer}/credit-operations` |
| Core | `GET /customers/{customer}/current_usage`, `GET /customers/{customer}/past_usage`, `GET /subscriptions?external_customer_id={customer}` |

Every other route refuses the publishable key with `403 publishable_key_not_allowed`, with or without a token, writes included (`/usage/track`, `/checkout`, top-ups, cancellations). A secret key ignores the header.

**What a token may read.** A token reads only what both the secret key that minted it and the publishable key may read. Each read needs its permission on both keys:

| Permission | Token reads |
|---|---|
| `customer_usage` | Current and past usage, and `GET /can` |
| `subscription` | `GET /subscriptions`, `GET /billing/status` and `GET /subscriptions/current` |
| `credit_system` | Credit balances and credit operations |

Minting needs only `customer:read`, so a key scoped to `customer:read` alone mints a token that reads none of these: each of those reads answers `403` (Core `read_action_not_allowed_for_<permission>`, for example `read_action_not_allowed_for_subscription`; the Engine `permission_denied`). Mint with a key that also has the read permissions the browser needs.

**A token belongs to one customer record.** It reads the customer it was minted for, not whoever holds that external ID later. If the customer is deleted, its tokens answer `401 invalid_customer_token`, also after a new customer reuses the external ID.

**Token reads return less.** A token is for showing a customer their own state, so:

- On [current usage](/api-reference/customers/retrieve-customer-current-usage), `feature_code` is the only usage filter. `charge_id`, `charge_code`, `group` and the `filter_by_*` parameters are ignored.
- On [`GET /can`](/api/check-entitlement), the answer has no `economics` and no `policy` fields, and `metadata` is ignored.

| Refusal | Meaning |
|---|---|
| `403 customer_token_customer_mismatch` | The request names another customer, or none. |
| `403 customer_token_feature_not_allowed` | The token was minted with `features`, and `/can` or a usage read names another feature (usage reads need `feature_code`). Subscription and credit reads are not feature-scoped. |
| `401 customer_token_expired` | Mint a new token. `@nozle-js/react` does this for you. Expiry allows 30 seconds of clock skew. |
| `401 invalid_customer_token` | Tampered, of another organization or environment (a sandbox token on a live key), minted before a revocation, or its customer was deleted. |

**Revoke** every token of the organization, for example after one leaked: [`POST /customer_tokens/revoke`](/api-reference/customers/revoke-customer-tokens) with a secret key that has `customer:write`. Tokens minted before it are refused from the next request, on Core and the Engine; tokens minted afterwards work. Rotating Nozle's signing secret also invalidates every token. A token is a bearer credential for one customer's billing data: keep the lifetime short, never log it, and serve it only to the signed-in customer.

With React, pass `getCustomerToken` and `customerId` (the signed-in customer's external ID) to `BillingProvider` and the [customer hooks](/sdks/react/hooks#read-from-nozle-with-a-customer-token) use it. With Node.js, mint with `nozle.customerTokens.create(customerId, { ttlSeconds, features })`.

## Key permissions

A secret key can be limited to read or write access per resource, for example `credit_system:read` or `plan:write`. A key without the permission a route needs gets `403`.

- Permissions restrict a key only when your organization has the API key permissions feature. On other organizations, creating a key with permissions is refused with `premium_integration_missing` instead of storing permissions that would not apply. A key created without permissions has full access.
- Rotating a key gives the new key the same permissions as the old one.
- Plan transition policies have their own resource, `plan_transition_policy`. Keys that existed before it have the same access to it that they have to `plan`.
- [Check credit usage](/api/usage-check) needs `credit_system:read` and [Track and consume credits](/api/usage-track) needs `credit_system:write`.
- Set a key's permissions in the dashboard under **Developers > API keys**, when you create a secret key or with **Edit**. The read and write picker shows only for secret keys on organizations with API key permissions. With API key permissions, a secret key with read and write on every resource is labelled **Full access**, and any other key **Restricted** with its grants, for example **Restricted · plan: read**. On other organizations, every secret key is labelled **Full access (permissions not enforced on this plan)**. A publishable key is labelled **Plan catalog · read only**.

### Engine routes

On organizations with API key permissions, these Engine routes check the key too. A key without the permission gets `403` with `code: permission_denied` and the message `API key requires <resource>:<mode> permission`. Organizations without API key permissions see no change.

| Route | Permission |
|---|---|
| `POST /customers` | `customer:write` |
| `POST /usage/check` | `credit_system:read` |
| `POST /usage/track` | `credit_system:write` |
| `POST /check-and-deduct` | `credit_system:write` and `wallet_transaction:write` |
| `POST /cost-events` | `event:write` |
| `GET /cost-models`, `GET /cost-models/{id}` | `analytic:read` |
| `POST /cost-models`, `DELETE /cost-models/{id}` | `analytic:write` |
| `POST /cost-intelligence/shared-costs/{id}/preview`, `GET /cost-intelligence/report` | `analytic:read` |
| `POST /cost-intelligence/shared-costs/{id}/allocate` | `analytic:write` |
| `GET /analytics/*`, `GET /margin/*`, `POST /margin/simulate` | `analytic:read` |

`POST /analytics/snapshot` and `POST /onboarding/chat` are internal to Nozle. They accept only Nozle's internal service token, and a secret key gets `403` with `internal service authentication required`.

## Browser access (CORS)

The publishable-key plan catalog, `GET /plans` and `GET /plans/{code}` on the Engine, answers CORS from any origin, so the [React components](/sdks/react/components) can load plans on your own site. The catalog and its preflight return `Access-Control-Allow-Origin: *` and `Access-Control-Allow-Methods: GET, OPTIONS`, never `Access-Control-Allow-Credentials`. The Engine's [customer token](#customer-tokens) reads answer the same way when the request carries `X-Nozle-Customer-Token` (or its preflight names it). Every other Engine route answers only the origins Nozle allows, so call them from your backend.

Core (`https://api.nozle.app/core`) answers browser calls only from an allowlist of exact origins (Nozle Cloud lists the dashboard). A call from another origin gets no CORS headers, so the browser blocks it. Two exceptions: the customer portal, where `POST /graphql` carrying a `customer-portal-token` header is allowed from any origin so the [billing portal](/sdks/react/billing-portal) works on your site, and the [customer token](#customer-tokens) reads (`current_usage`, `past_usage`, `GET /subscriptions`) carrying `X-Nozle-Customer-Token`. Calls from your server with an API key are not affected. Self-hosted Core: see the Core environment variables.

<Warning>
Never expose a secret or master key in client-side code. CORS and `Origin` headers do not authenticate a caller.
</Warning>

## Public authentication endpoints

These are Core routes, for example `https://api.nozle.app/core/api/v1/auth/send-otp`. The Engine does not serve them.

- `POST /api/v1/auth/send-otp`
- `POST /api/v1/auth/verify-otp`
- `POST /api/v1/auth/signup`

The signup code endpoints answer the same way for every email, so they do not reveal whether an email already has an account:

- `send-otp` (`email`) answers `200` with `{"success": true, "expiresIn": 300}`. A new email receives a 6-digit code that is valid for 5 minutes; an email that already has an account receives a login email instead of a code. A second request for the same email within 60 seconds, or more than 10 requests from one IP address in an hour, answers `429` with `retryAfter` in seconds.
- `verify-otp` (`email`, `code`) answers `200` with `{"verified": true, "verificationToken": "..."}`, which `signup` accepts for 10 minutes. A wrong, expired or missing code answers `401` with `{"error": "invalid code"}`. Before, an expired code answered `410`: treat `401` as "invalid or expired, request a new code". A code that is not 6 digits answers `400`.
- Each email has 5 attempts per 15 minutes, and each IP address 20 per hour. Requesting a new code does not reset the attempts. Past the limit, `verify-otp` answers `429` with `too many attempts, try again later`.

Get API keys from [app.nozle.dev](https://app.nozle.dev) under **Developers > API keys**.
