Base URL: `https://api.nozle.app/engine/api/v1`.

Create a payment-gated plan checkout from a trusted merchant backend.

**Auth:** secret key only. Publishable keys are always rejected.

<Info>
The merchant backend derives `customer_id` from its authenticated user or team. Do not trust a browser-provided customer ID. The response can contain a Stripe or Razorpay checkout, a processing state, or a completed or scheduled transition.
</Info>

## Modes

### Plan checkout

Use this when a customer is selecting a plan.

<ParamField body="customer_id" type="string" required>
  External customer ID. The customer must already exist.
</ParamField>

<ParamField body="plan_code" type="string" required>
  The plan code to subscribe the customer to (e.g. `pro`).
</ParamField>

Plan checkout is payment-gated. Free-to-paid checkout uses an incomplete subscription. Paid-to-paid upgrades keep the old subscription active in a durable pending intent and apply the billing change only after the payment provider confirms the required payment and Nozle fulfills the change.

If prepaid credits fully cover a paid plan change, Nozle applies it without an external payment and returns `type: "completed"`. A downgrade or other cycle-end transition may return `type: "scheduled"`.

Checkout is only for plans that need an up-front payment. For a customer with no subscription, a free plan, a plan with a trial, or a plan billed in arrears returns `422 checkout_not_required`: start it with [`subscribe`](/api/subscribe) instead. Entity checkout is the exception and completes these plans with `payment_source: "none"`.

Changing the plan of an existing subscription needs a [plan transition policy](/api/plan-transition-policies) for that pair of plans, except from a free plan to a paid plan. The selected self-service downgrade flow uses a signed quote with the end-of-period transition endpoint described below.

## Selected subscription and signed quote

<ParamField body="subscription_id" type="string">
  External subscription ID. Select it explicitly for self-service. An unselected checkout for a customer with multiple active subscriptions is rejected as ambiguous.
</ParamField>

<ParamField body="quote_id" type="string">
  Opaque signed quote from `POST /subscriptions/preview`. Requires `subscription_id`; forward it unchanged after the customer confirms the amounts and dates.
</ParamField>

Use an `Idempotency-Key` header for the confirmed action and retain it across uncertain retries. A new-subscription checkout retried while its first attempt is unpaid reopens that attempt; see [Retry a new-subscription checkout](#retry-a-new-subscription-checkout). Invalidated or expired new quotes require a fresh preview/confirmation; replay of an already accepted action reuses its recorded checkout. See [Subscription self-service](/api/subscription-management) for quote, downgrade and recovery contracts.

## Return URL

<ParamField body="return_url" type="string">
  URL Stripe should return to after embedded checkout completes. It must use an exactly allowlisted HTTPS origin. If omitted, Nozle uses the configured dashboard return URL.
</ParamField>

<ParamField body="success_url" type="string">
  Backward-compatible alias for `return_url`.
</ParamField>

## Request examples

Plan checkout:

```json
{
  "customer_id": "customer_123",
  "plan_code": "growth",
  "return_url": "https://app.example.com/settings/billing"
}
```

## Response

<ResponseField name="type" type="string" required>
  `stripe`, `razorpay`, `processing`, `completed`, or `scheduled`. This endpoint never returns `hosted`. The SDK types still declare it, and only the deprecated `POST /credits/purchase` of the Engine API returns it.
</ResponseField>

<ResponseField name="client_secret" type="string">
  Stripe results only: the `cs_` secret of an embedded Stripe Checkout Session. Mount it with Stripe Embedded Checkout (the React `Checkout` component does this). Plan and invoice checkout never return a Stripe-hosted URL. Credit top-ups do: see [Create Credit Top-up Purchase](/api/create-credit-top-up-purchase).
</ResponseField>

<ResponseField name="clientSecret" type="string">
  Camel-case alias for `client_secret`.
</ResponseField>

<ResponseField name="invoice_id" type="string">
  Nozle invoice ID being paid. A paid upgrade returns `plan_upgrade_intent_id` instead.
</ResponseField>

<ResponseField name="plan_upgrade_intent_id" type="string">
  Paid upgrades only: the pending upgrade. Use it with the subscription scope to poll status; the old plan stays active until payment succeeds.
</ResponseField>

<ResponseField name="amount_cents" type="integer">
  Amount due for the checkout session, in the invoice currency's smallest unit.
</ResponseField>

<ResponseField name="currency" type="string">
  Invoice currency.
</ResponseField>

### Razorpay and recovery fields

A `razorpay` result supplies `checkout_id`, `order_id`, public `key_id`, `amount_cents`, `currency`, `expires_at`, and `invoice_id` or `plan_upgrade_intent_id`. A mandate checkout (`register_mandate: true`) adds `customer_id`, `recurring: true`, and `mandate_max_amount_cents`. Open the Razorpay modal, then verify the handler's signature on your backend. Activation requires captured payment and completed fulfillment. See [the Razorpay flow](/guides/billing/checkout#razorpay).

A `processing` result supplies `checkout_id` and `status`. Razorpay returns it while the order is not ready yet or after it expired. Stripe returns it for a replayed quoted upgrade while the payment is complete and its webhook is pending. Recover it rather than starting another checkout. A bulk Entity checkout first answers `{"entity_subscription_checkout": {"type": "processing", "status": "open", "checkout_id": "...", ...}}`. The `status` of a `processing` result is an internal operation status. The nested `checkout` of an expired unpaid Razorpay order in checkout status is `{"type": "processing", "status": "ready"}` while the top-level `status` is `expired`. Both scoped verification and status recovery are described in [Subscription self-service](/api/subscription-management#payment-status-and-recovery).

A Razorpay payment link is never a result of this endpoint. It comes from an invoice payment URL (`POST /invoices/{id}/payment_url`, which returns `{"invoice_payment_details": {"customer_id", "external_customer_id", "payment_provider", "invoice_id", "payment_url"}}`) or from a [credit top-up purchase](/api/create-credit-top-up-purchase), and has no checkout ID to poll.

### Retry a new-subscription checkout

A new-subscription checkout leaves an incomplete subscription until its first payment succeeds. Calling checkout again for the same customer and plan while that subscription is incomplete reopens the first checkout for the same invoice instead of failing, with or without the same `Idempotency-Key`. Asking for a different plan while it is open returns `409 subscription_checkout_in_progress`. For Razorpay the reopened checkout is the same order. An invoice checkout (`invoice_id` in the request) for the `invoice_id` of the first response works too.

### Credit-funded response

When no external payment remains due:

```json
{
  "type": "completed",
  "status": "succeeded",
  "payment_source": "credits",
  "subscription_id": "subscription_uuid",
  "plan_code": "pro",
  "invoice_id": "invoice_uuid",
  "amount_cents": 0,
  "currency": "USD"
}
```

A `completed` result has `payment_source` `credits` when the change was funded without an external payment (including a free-to-free change, which still creates a zero-amount invoice) and `none` when nothing was invoiced. Entity checkouts add `external_entity_id` and `external_subscription_id` to every result.

### Scheduled response

```json
{
  "type": "scheduled",
  "status": "pending",
  "subscription_id": "pending_subscription_uuid",
  "plan_code": "starter",
  "transition_direction": "downgrade",
  "transition_policy": "next_period",
  "effective_at": "2026-11-01T00:00:00.000000Z"
}
```

`subscription_id` is the pending subscription; there is no separate `pending_subscription_id` field. A new scheduled change while a change is pending replaces that change and returns a new pending ID. A paid upgrade checkout does not replace or withdraw a pending downgrade: see [Paid upgrades: current limits](#paid-upgrades-current-limits).

`effective_at` is an RFC 3339 timestamp rendered in the customer's timezone. For a customer in `Asia/Kolkata` it reads `2026-11-01T00:00:00.000000+05:30`, which is the same instant as `2026-10-31T18:30:00Z`. Parse it as a timestamp and do not assume a trailing `Z`. A scheduled change takes effect at that instant: the active subscription is terminated and the pending subscription becomes active, keeping its `billing_time`.

### Paid upgrades: current limits

These limits were observed on a paid upgrade checkout that returns a `stripe` result with `plan_upgrade_intent_id`. Configure around them until Core is fixed.

- **Invoice grace period.** If the billing entity has an invoice grace period above 0 days, the upgrade invoice stays a draft. The customer's payment is still collected, but Nozle cannot apply the upgrade. With `credit_action: "credit"` the upgrade ends in `needs_review` with `plan_upgrade_amount_changed`, because the quoted amount credited the unused time and the draft invoice did not. Without a credit, the payment handler fails with `payment_status_update_on_draft_invoice` and the upgrade stays pending. Set the grace period to 0 for billing entities that sell paid upgrades, or refund and reconcile an affected payment by hand.
- **Pending downgrade.** An upgrade checkout created while a downgrade is pending returns a payable session. Paying it ends in `needs_review` with `plan_upgrade_subscription_changed`, because the subscription changed under the upgrade. Withdraw the pending downgrade first, with [`POST /subscriptions/transitions/withdraw`](/api/subscription-management#withdraw-a-pending-downgrade), then start the upgrade.
- **Status.** Poll the upgrade with `GET /checkout/{plan_upgrade_intent_id}?customer_id=…&subscription_id=…` (Engine names). `status` is `awaiting_payment` until payment, then `succeeded` with `fulfillment_status` `succeeded` and an `invoice_id`. `needs_review` means the payment was taken but the upgrade was not applied. See [Subscription self-service](/api/subscription-management#payment-status-and-recovery).

With a grace period of 0 and no pending change, a credited upgrade applies as quoted: the old subscription is terminated, the new one is active, and `billing_time` is unchanged.

## Errors

| Status | Code | Cause |
| --- | --- | --- |
| `400` | `invalid_return_url` | `return_url` origin is not allowlisted. Checked before anything else. |
| `400` | — | `subscription_id` combined with `invoice_id` or `external_entity_id`, or neither `plan_code` with `customer_id` nor `invoice_id` given. |
| `404` | `plan_not_found`, `customer_not_found` | Unknown plan or customer. |
| `422` | `plan_transition_policy_required` | The customer has an active subscription and the pair of plans has no [transition policy](/api/plan-transition-policies). |
| `422` | `plan_upgrade_invoice_missing` | An upgrade to a plan billed in arrears: nothing is due up front. |
| `422` | `plan_already_active`, `target_plan_is_not_a_downgrade` | See [transition policies](/api/plan-transition-policies). |
| `422` | `subscription_not_active` | Raised by plan-transition calls on a subscription that is not active. A checkout that names a terminated subscription ID was treated as a new checkout in testing, so do not rely on this code from checkout. |
| `409` | `subscription_selection_required` | The customer has several active subscriptions and no `subscription_id` was given. |
| `409` | `plan_upgrade_checkout_in_progress` | Another upgrade checkout for the same subscription is open. Recover it with checkout status. |
| `409` | `entity_subscription_checkout_in_progress` | Another Entity checkout for the same subscription is open. |
| `422` | `validation_errors` | `error_details.checkout` is `billing_anchor_checkout_in_progress`: a bulk Entity checkout found an Entity with an incomplete subscription, or a first paid checkout for the customer still open. It is a `422`, not a `409`. |
| `409` | `idempotency_key_reused` | The key was used with a different request. An invoice checkout on Stripe returns it when Stripe refuses the reused key. |
| `409` | `plan_change_quote_changed`, `subscription_change_pending` | The quote no longer matches the subscription. Preview again. |
| `422` | `checkout_not_required` | The plan needs no up-front payment (free, trial, or billed in arrears) and the customer has no subscription. Use `subscribe`. |
| `422` | `payment_provider_required` | No Stripe or Razorpay connection for the customer. |
| `422` | `stripe_customer_required` | Nozle could not create the customer in Stripe. A customer that is not in Stripe yet normally gets one at checkout, so this code appears only when that creation fails. See the [Stripe integration](/integrations/stripe#errors). |
| `422` | `razorpay_requires_inr` | A Razorpay checkout for an invoice that is not in INR. See the [Razorpay integration](/integrations/razorpay#errors). |
| `422` | `plan_already_active` | The customer, or Entity, is already on this plan. |
| `409` | `subscription_checkout_in_progress` | A new-subscription checkout for this customer is still open on a different plan. Pay or abandon it, or check out the same plan to reopen it. |
| `422` | `razorpay_customer_connection_cannot_change` | The customer already started a Razorpay checkout and was moved to another Razorpay connection. Create a new customer instead. See the [Razorpay integration](/integrations/razorpay#assign-the-connection-to-customers). |
| `404` | `payment_provider_not_found` | The customer's connection code matches no Razorpay connection. |
| `422` | `third_party_error` | The provider rejected the request, for example Razorpay with a wrong key secret. |
| `422` | `subscription_and_idempotency_key_required` | `quote_id` sent without `subscription_id` or an `Idempotency-Key`. |

## Webhook requirement

Stripe must be able to reach your Nozle public API URL. When a Stripe provider is connected, Nozle registers the Stripe webhook endpoint for that tenant's Stripe account:

```text
https://api.nozle.app/core/webhooks/stripe/{organization_id}?code={stripe_provider_code}
```

Checkout relies on these Stripe events:

- `payment_intent.succeeded`
- `payment_intent.payment_failed`
- `payment_intent.canceled`

The same endpoint also receives `setup_intent.succeeded`, `payment_method.detached`, `customer.updated`, `charge.refund.updated` and `charge.dispute.closed`. See the [Stripe integration](/integrations/stripe#webhook-setup).

Razorpay webhooks are configured by you in the Razorpay dashboard. See the [Razorpay integration](/integrations/razorpay#webhook-setup) for the URL, headers, and events.
