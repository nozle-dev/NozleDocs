title: "Create Checkout Session"
api: "POST https://api.nozle.app/engine/api/v1/checkout"

Base URL: `https://api.nozle.app/engine/api/v1`.

Create a payment-gated plan checkout from a trusted merchant backend.

**Auth:** secret key only. Publishable keys are always rejected.

<Info>
The merchant backend derives `customer_id` from its authenticated user or team. Do not trust a browser-provided customer ID. The response can contain a Stripe-hosted or Razorpay checkout, a processing state, or a completed or scheduled transition.
</Info>

## Modes

### Plan checkout

Use this when a customer is selecting a plan.

<ParamField body="customer_id" type="string" required>
  External customer ID. The customer must already exist.
</ParamField>

<ParamField body="plan_code" type="string" required>
  The plan code to subscribe the customer to (e.g. `pro`).
</ParamField>

Plan checkout is payment-gated. Free-to-paid checkout uses an incomplete subscription. Paid-to-paid upgrades keep the old subscription active in a durable pending intent and apply the billing change only after the payment provider confirms the required payment and Nozle fulfills the change.

If prepaid credits fully cover a paid plan change, Nozle applies it without an external payment and returns `type: "completed"`. A downgrade or other cycle-end transition may return `type: "scheduled"`.

Checkout is only for plans that need an up-front payment. For a customer with no subscription, a free plan, a plan with a trial, or a plan billed in arrears returns `422 checkout_not_required`: start it with [`subscribe`](/api/subscribe) instead. A plan with a pay-in-advance fixed charge is the exception, even with a trial or billed in arrears: checkout invoices the fixed charge in the request and returns a payable session for it, like any paid plan. The customer's saved card is never charged off-session for that invoice. Entity checkout is the exception and completes these plans with `payment_source: "none"`.

Changing the plan of an existing subscription needs a [plan transition policy](/api/plan-transition-policies) for that pair of plans, except from a free plan to a paid plan. The selected self-service downgrade flow uses a signed quote with the end-of-period transition endpoint described below.

### Invoice checkout

<ParamField body="invoice_id" type="string">
  Nozle invoice to collect payment for. With `invoice_id`, `plan_code` is not required. It cannot be combined with `subscription_id`.
</ParamField>

## Selected subscription and signed quote

<ParamField body="subscription_id" type="string">
  External subscription ID. Select it explicitly for self-service. An unselected checkout for a customer with multiple active subscriptions is rejected as ambiguous.
</ParamField>

<ParamField body="quote_id" type="string">
  Opaque signed quote from `POST /subscriptions/preview`. Requires `subscription_id`; forward it unchanged after the customer confirms the amounts and dates.
</ParamField>

Use an `Idempotency-Key` header for the confirmed action and retain it across uncertain retries. A new-subscription checkout retried while its first attempt is unpaid reopens that attempt; see [Retry a new-subscription checkout](#retry-a-new-subscription-checkout). Invalidated or expired new quotes require a fresh preview/confirmation; replay of an already accepted action reuses its recorded checkout. See [Subscription self-service](/api/subscription-management) for quote, downgrade and recovery contracts.

## Return URL

<ParamField body="return_url" type="string">
  URL the customer returns to after paying on the Stripe-hosted page. It may contain the literal `{CHECKOUT_SESSION_ID}`, which Stripe replaces with the Checkout Session ID. It must be an absolute HTTPS URL on one of your organization's allowed origins (`checkout_return_origins`) or on an origin Nozle allows for every organization. The Engine applies no list of its own: it sends the URL to Core, which decides, and a refused URL answers `400` with `invalid_return_url`. If omitted, Nozle uses your organization's default return URL (`checkout_default_return_url`), else your first allowed origin. Set both in the dashboard under **Developers > Checkout return**, or through the API. See [return URLs and your organization's origins](/guides/billing/checkout#return-urls-and-your-organizations-origins).
</ParamField>

<ParamField body="cancel_url" type="string">
  URL Stripe sends a customer to when they leave the hosted page without paying. Validated like `return_url` (a refused one answers `400` with `invalid_return_url`). Without it, the return URL is used.
</ParamField>

<ParamField body="success_url" type="string">
  Backward-compatible alias for `return_url`.
</ParamField>

Plan checkout:

```json
  "plan_code": "growth",
  "return_url": "https://app.example.com/settings/billing"

```

## Response

<ResponseField name="type" type="string" required>
  `hosted` (Stripe), `razorpay`, `processing`, `completed`, or `scheduled`. There is no `stripe` result and no client secret any more. The deprecated `POST /credits/purchase` of the Engine API also returns `hosted`. That endpoint requires an `Idempotency-Key` header and a `currency` field (the ISO 4217 code of the top-up package, for example `USD`), and answers `400` with the code `idempotency_key_required` or `currency_required` without them; a retry with the same key returns the first purchase. Use [Create Credit Top-up Purchase](/api/create-credit-top-up-purchase) (`POST /credit-top-up-purchases`) instead.
</ResponseField>

<ResponseField name="url" type="string">
  `hosted` results: the Stripe-hosted Checkout page. Redirect the customer to it. `payment_url` carries the same value.
</ResponseField>

<ResponseField name="checkout_id" type="string">
  `hosted` results: the Stripe Checkout Session ID (`cs_...`). It is not a status ID: poll a paid upgrade with its `plan_upgrade_intent_id`.
</ResponseField>

<ResponseField name="expires_at" type="string">
  `hosted` results: when the hosted page expires.
</ResponseField>

<ResponseField name="invoice_id" type="string">
  Nozle invoice ID being paid. A paid upgrade returns `plan_upgrade_intent_id` instead.
</ResponseField>

<ResponseField name="plan_upgrade_intent_id" type="string">
  Paid upgrades only: the pending upgrade. Use it with the subscription scope to poll status; the old plan stays active until payment succeeds.
</ResponseField>

<ResponseField name="amount_cents" type="integer">
  Amount due for the checkout session, in the invoice currency's smallest unit.
</ResponseField>

<ResponseField name="currency" type="string">
  Invoice currency.
</ResponseField>

### Hosted Stripe result

Every Stripe checkout (a new subscription's first invoice, an invoice, a paid plan change) is a Stripe-hosted Checkout Session:

```json
{
  "type": "hosted",
  "url": "https://checkout.stripe.com/c/pay/cs_...",
  "payment_url": "https://checkout.stripe.com/c/pay/cs_...",
  "checkout_id": "cs_...",
  "invoice_id": "invoice_uuid",
  "amount_cents": 19900,
  "currency": "USD",
  "expires_at": "2026-11-01T12:00:00Z"
}
```

A paid upgrade has `plan_upgrade_intent_id` instead of `invoice_id`. Redirect the customer to `url`. A saved card is charged first: when that works you get `completed`, `processing` or `scheduled` and no page opens. No Stripe publishable key and no Stripe.js are needed on your page. Nozle sends Adaptive Pricing disabled so the customer is charged in the invoice currency. Nothing is paid until Stripe's webhook reaches Nozle: after the customer returns, wait for your webhook, or reload the subscription or [billing status](/api/billing-status). Only a paid upgrade has a status call: poll [`GET /checkout/{plan_upgrade_intent_id}`](/api/subscription-management#payment-status-and-recovery) with the customer and subscription scope. While the buyer is paying, `status` is `awaiting_payment` and the nested `checkout` is the hosted result again; `processing` means Stripe took the payment and Nozle is applying it; `succeeded` comes with a nested `completed`; `expired` means the Stripe session is no longer open. The `checkout_id` of a hosted result is the Stripe Checkout Session ID and is not a status ID.

### Razorpay and recovery fields

A `razorpay` result supplies `checkout_id`, `order_id`, public `key_id`, `amount_cents`, `currency`, `expires_at`, and `invoice_id` or `plan_upgrade_intent_id`. A mandate checkout (`register_mandate: true`) adds `customer_id`, `recurring: true`, and `mandate_max_amount_cents`. Open the Razorpay modal, then verify the handler's signature on your backend. Activation requires captured payment and completed fulfillment. See [the Razorpay flow](/guides/billing/checkout#razorpay).

A `processing` result supplies `checkout_id` and `status`. Razorpay returns it while the order is not ready yet or after it expired. Stripe returns it for a replayed quoted upgrade while the payment is complete and its webhook is pending. Recover it rather than starting another checkout. A bulk Entity checkout first answers `{"entity_subscription_checkout": {"type": "processing", "status": "open", "checkout_id": "...", ...}}`. The `status` of a `processing` result is an internal operation status. The nested `checkout` of an expired unpaid Razorpay order in checkout status is `{"type": "processing", "status": "ready"}` while the top-level `status` is `expired`. Both scoped verification and status recovery are described in [Subscription self-service](/api/subscription-management#payment-status-and-recovery).

A Razorpay payment link is never a result of this endpoint. It comes from an invoice payment URL (`POST /invoices/{id}/payment_url`, which returns `{"invoice_payment_details": {"customer_id", "external_customer_id", "payment_provider", "invoice_id", "payment_url"}}`) or from a [credit top-up purchase](/api/create-credit-top-up-purchase), and has no checkout ID to poll.

### Retry a new-subscription checkout

A new-subscription checkout leaves an incomplete subscription until its first payment succeeds. Calling checkout again for the same customer and plan while that subscription is incomplete reopens the first checkout for the same invoice instead of failing, with or without the same `Idempotency-Key`. For Razorpay the reopened checkout is the same order. An invoice checkout (`invoice_id` in the request) for the `invoice_id` of the first response works too.

Asking for a different plan replaces the abandoned checkout: the old checkout expires as described below and the new checkout is returned. `409 subscription_checkout_in_progress` (`entity_subscription_checkout_in_progress` for a single Entity checkout) is returned only while the provider is still processing a payment for the old checkout, or when that checkout turns out to be paid. The same applies to single Entity checkouts.

### Unpaid checkout expiry

An unpaid plan checkout or single Entity checkout expires after 23 hours, the same lifetime as an [Entity checkout batch](/api/entity-subscriptions#purchase-multiple-entity-plans-together). The Stripe Checkout Session and the Razorpay order (`expires_at`) expire at the same time. When it expires, Nozle:

- cancels the incomplete subscription with `cancelation_reason: timeout` and sends `subscription.canceled`;
- closes the payment-gated invoice;
- returns the coupons, credit-note credits and wallet credits that invoice used;
- expires the Stripe Checkout Session or Razorpay order that is still open.

A checkout that was paid in time is activated instead. While the provider is still processing a payment, the checkout is kept and checked again an hour later. A checkout whose payment fails also closes its invoice and returns the same credits.

### Upgrade checkout that ran out of time

Before a paid upgrade checkout whose time ran out is reported `expired` or replaced, Nozle asks the payment provider what became of it:

- **Closed without a payment** (a Stripe Checkout Session that is still open is expired at Stripe first, or a Razorpay order without a payment): the upgrade expires, and a new checkout opens a new session or order.
- **Paid in time, webhook late:** Nozle settles the payment as the webhook would and applies the upgrade. No second checkout is offered, so the customer is not charged twice.
- **Payment still processing, or the provider cannot be reached:** nothing changes and a new checkout answers `409 plan_upgrade_checkout_in_progress`. Poll the [checkout status](/api/subscription-management#payment-status-and-recovery) and try again later.

Once a late payment has been applied, a new checkout of the same plan answers `422 plan_already_active`, with Stripe and Razorpay alike. If the checkout request that found the late payment asked for another plan, it answers `409 plan_upgrade_checkout_in_progress` with the `checkout_id` of the paid checkout; reload the subscription before you start the next change.

### Credit-funded response

When no external payment remains due:

```json
{
  "type": "completed",
  "status": "succeeded",
  "payment_source": "credits",
  "subscription_id": "subscription_uuid",
  "plan_code": "pro",
  "invoice_id": "invoice_uuid",
  "amount_cents": 0,
  "currency": "USD"
}
```

A `completed` result has `payment_source` `credits` when the change was funded without an external payment (including a free-to-free change, which still creates a zero-amount invoice) and `none` when nothing was invoiced. Entity checkouts add `external_entity_id` and `external_subscription_id` to every result.

### Scheduled response

```json
{
  "type": "scheduled",
  "status": "pending",
  "subscription_id": "pending_subscription_uuid",
  "plan_code": "starter",
  "transition_direction": "downgrade",
  "transition_policy": "next_period",
  "effective_at": "2026-11-01T00:00:00.000000Z"
}
```

`subscription_id` is the pending subscription; there is no separate `pending_subscription_id` field. A new scheduled change while a change is pending replaces that change and returns a new pending ID. A paid upgrade checkout is refused with `409 subscription_change_pending` while a change is pending: withdraw it first. See [Paid upgrades: current limits](#paid-upgrades-current-limits).

`effective_at` is an RFC 3339 timestamp rendered in the customer's timezone. For a customer in `Asia/Kolkata` it reads `2026-11-01T00:00:00.000000+05:30`, which is the same instant as `2026-10-31T18:30:00Z`. Parse it as a timestamp and do not assume a trailing `Z`. A scheduled change takes effect at that instant: the active subscription is terminated and the pending subscription becomes active, keeping its `billing_time`.

### Paid upgrades: current limits

These limits were observed on a paid upgrade checkout that returns a `stripe` result with `plan_upgrade_intent_id`. Configure around them until Core is fixed.

- **Invoice grace period.** If the billing entity has an invoice grace period above 0 days, the upgrade invoice stays a draft. The customer's payment is still collected, but Nozle cannot apply the upgrade. With `credit_action: "credit"` the upgrade ends in `needs_review` with `plan_upgrade_amount_changed`, because the quoted amount credited the unused time and the draft invoice did not. Without a credit, the payment handler fails with `payment_status_update_on_draft_invoice` and the upgrade stays pending. Set the grace period to 0 for billing entities that sell paid upgrades, or refund and reconcile an affected payment by hand.
- **Pending change.** A paid upgrade checkout is refused with `409 subscription_change_pending` while the subscription has a scheduled cancellation or a scheduled plan change. Withdraw the pending downgrade with [`POST /subscriptions/transitions/withdraw`](/api/subscription-management#withdraw-a-pending-downgrade), or keep the subscription, then start the upgrade. Cancelling at period end, scheduling a plan change or applying an immediate downgrade cancels an open upgrade checkout: its Stripe Checkout Session or Razorpay order is expired. A payment the provider is already processing is left to settle.
- **Status.** Poll the upgrade with `GET /checkout/{plan_upgrade_intent_id}?customer_id=…&subscription_id=…` (Engine names). `status` is `awaiting_payment` until payment, then `succeeded` with `fulfillment_status` `succeeded` and an `invoice_id`. `needs_review` means the payment was taken but the upgrade was not applied. See [Subscription self-service](/api/subscription-management#payment-status-and-recovery).

- **Failed upgrades leave nothing behind.** A quoted upgrade with nothing to pay that fails after the change was prepared (for example because the grace period keeps its invoice a draft) is rolled back: the subscription stays on its plan, no credit note is created, and the same request can be retried once the cause is fixed. An upgrade whose credit for the unused time of the old plan cannot be computed (the credit usage of a plan family interval switch is unavailable) fails with `503 credit_usage_unavailable` and applies nothing, instead of applying without the credit. Retry later.

With a grace period of 0 and no pending change, a credited upgrade applies as quoted: the old subscription is terminated, the new one is active, and `billing_time` is unchanged.

## Errors

The Engine checks the request in this order: valid JSON body, customer scope, the `subscription_id` combinations, the required fields, then the `Idempotency-Key` length. Only then is the request sent to Core, which checks `return_url` and returns the other errors below.

Every error body carries `error` and `code`. Core's errors also carry `status`, as `{"status": 409, "error": "Conflict", "code": "subscription_change_pending"}`, plus `error_details` or `checkout_id` where noted. Branch on the HTTP status and `code`, not on `error`.

| Status | Code | Cause |
| --- | --- | --- |
| `400` | `invalid_request` | The body is not valid JSON, `subscription_id` is combined with `invoice_id` or `external_entity_id`, neither `plan_code` with `customer_id` nor `invoice_id` is given, or the `Idempotency-Key` is longer than 255 bytes. |
| `400` | `invalid_return_url` | Core refused `return_url`: it is not an absolute HTTPS URL, or its origin is not one of your organization's allowed origins. See [return URLs](/guides/billing/checkout#return-urls-and-your-organizations-origins). |
| `403` | `customer_scope_mismatch` | Trusted internal authentication with an `X-Nozle-Customer-Id` header that differs from `customer_id`. |
| `404` | `plan_not_found`, `customer_not_found`, `subscription_not_found` | Unknown plan or customer, or `subscription_id` is not an active subscription of the customer (for example a terminated one). |
| `422` | `plan_transition_policy_required` | The customer has an active subscription and the change needs a [transition policy](/api/plan-transition-policies): an immediate downgrade, a plan the default does not reach, or a trial. Upgrades and end-of-period downgrades between public plans need none. |
| `422` | `validation_errors` | `error_details.base` is `amount_below_provider_minimum`: an invoice checkout whose amount left to pay is under the payment provider's minimum charge (for example less than $0.50 on Stripe). |
| `422` | `plan_upgrade_invoice_missing` | An upgrade to a plan billed in arrears: nothing is due up front. |
| `422` | `plan_already_active`, `target_plan_is_not_a_downgrade` | See [transition policies](/api/plan-transition-policies). |
| `409` | `subscription_selection_required` | The customer has several active subscriptions and no `subscription_id` was given. |
| `409` | `plan_upgrade_checkout_in_progress` | Another upgrade checkout for the same subscription is open, or its time ran out while the provider reports a payment in progress or cannot be reached. Recover it with checkout status. See [Upgrade checkout that ran out of time](#upgrade-checkout-that-ran-out-of-time). |
| `409` | `entity_subscription_checkout_in_progress` | A single Entity checkout on a different plan is still being paid: the provider is processing its payment, or it was paid. An abandoned one is replaced instead. |
| `409` | `billing_anchor_checkout_in_progress` | A single or bulk Entity checkout found that the customer's first paid Entity checkout is still open and no billing anchor is set yet. A bulk checkout returned `422 validation_errors` for this before October 28, 2026. |
| `409` | `idempotency_key_reused` | The key was used with a different request. An invoice checkout on Stripe returns it when Stripe refuses the reused key. |
| `409` | `plan_change_quote_changed` | The quote no longer matches the subscription. Preview again. |
| `409` | `subscription_change_pending` | The subscription has a scheduled cancellation or plan change, or an upgrade payment in progress. Withdraw the change, or wait for the payment, then preview again. |
| `422` | `checkout_not_required` | The plan needs no up-front payment (free, trial, or billed in arrears) and the customer has no subscription. Use `subscribe`. |
| `422` | `payment_provider_required` | The customer is not assigned to Razorpay and the organization has no Stripe connection. |
| `422` | `stripe_customer_required` | Nozle could not create the customer in Stripe. A customer that is not in Stripe yet normally gets one at checkout, so this code appears only when that creation fails. See the [Stripe integration](/integrations/stripe#errors). |
| `422` | `razorpay_requires_inr` | A Razorpay checkout for an invoice that is not in INR. See the [Razorpay integration](/integrations/razorpay#errors). |
| `422` | `plan_already_active` | The customer, or Entity, is already on this plan, including right after a late upgrade payment for it was applied. |
| `409` | `subscription_checkout_in_progress` | A new-subscription checkout for this customer on a different plan is still being paid: the provider is processing its payment, or it was paid. An abandoned one is replaced instead. |
| `422` | `validation_errors` | For an invoice checkout, `error_details.base` is `invalid_invoice_status_or_payment_status` when the invoice is paid, voided, a draft, closed, failed or has nothing due. |
| `422` | `razorpay_customer_connection_cannot_change` | The customer already started a Razorpay checkout and was moved to another Razorpay connection. Create a new customer instead. See the [Razorpay integration](/integrations/razorpay#assign-the-connection-to-customers). |
| `404` | `payment_provider_not_found` | The customer's connection code matches no Razorpay connection. |
| `422` | `third_party_error` | The provider rejected the request, for example Razorpay with a wrong key secret. |
| `422` | `subscription_and_idempotency_key_required` | `quote_id` sent without `subscription_id` or an `Idempotency-Key`. |
| `503` | `credit_usage_unavailable` | The credit for the unused time of the old plan could not be computed. Nothing was applied. Retry later. |

## Webhook requirement

Stripe must be able to reach your Nozle public API URL. When a Stripe provider is connected, Nozle registers the Stripe webhook endpoint for that tenant's Stripe account:

```text
https://api.nozle.app/core/webhooks/stripe/{organization_id}?code={stripe_provider_code}
```

Checkout relies on these Stripe events:

- `payment_intent.succeeded`
- `payment_intent.payment_failed`
- `payment_intent.canceled`

The same endpoint also receives `setup_intent.succeeded`, `payment_method.detached`, `customer.updated`, `refund.updated`, `refund.failed` and `charge.dispute.closed`. See the [Stripe integration](/integrations/stripe#webhook-setup).

Razorpay webhooks are configured by you in the Razorpay dashboard. See the [Razorpay integration](/integrations/razorpay#webhook-setup) for the URL, headers, and events.
