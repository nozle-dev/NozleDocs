## HTTP status codes

| Status | Meaning |
|---|---|
| `200`–`299` | Successful request. |
| `400` | Missing, invalid, or conflicting parameters. |
| `401` | Missing or invalid credential. |
| `403` | Credential lacks permission or a publishable key attempted a protected operation. |
| `404` | Resource was not found within the authenticated organization. |
| `413` | The request body is too large: `payload_too_large`. An events batch is limited to 16 MiB, decoded. |
| `402` | Payment required. `workspace_suspended` (or `card_required`): your workspace is blocked by Nozle, see [Workspace billing errors](#workspace-billing-errors). `customer_payment_overdue`: one of your customers is blocked by your dunning policy, see [Customer payment overdue](#customer-payment-overdue). `budget_exceeded` from the LLM proxy: a customer's hard spend limit is used up, see [Spend and usage limits](#spend-and-usage-limits). |
| `409` | Idempotency key or resource-state conflict, such as another checkout in progress. Reload the state, then retry. |
| `422` | Request is syntactically valid but violates a product rule, or the resource's current state refuses it (for example a voided invoice). |
| `429` | Request was rate limited, or (LLM proxy) `usage_limit_exceeded`: a customer's hard usage limit is reached, which is a refusal, not a rate limit. |
| `500` | Unexpected server error. The body is still JSON with a `code`. |
| `502` | A service Nozle depends on did not answer: `upstream_unavailable`. Safe to retry. |
| `503` | Temporary dependency, lock, or service failure. |

Nozle never returns `405` for a business rule; a refused state is a `422` with a `code`.

## Response shape

Endpoints return a short error description and may include a stable code or additional fields:

```json
{
  "status": 422,
  "error": "Unprocessable Entity",
  "code": "not_voidable"
}
```

Every Core error carries `status`, `error` and `code`; validation errors add `error_details`. A malformed body is `400` with `code: "bad_request"`.

Do not parse human-readable text when a machine-readable `code` is available.

## Retry guidance

- Retry read requests only within your latency and request budget.
- Retry idempotent mutations with the same idempotency key and payload.
- Retry events with the same transaction ID.
- Honor `Retry-After` when returned.
- Do not retry validation, authorization, or insufficient-credit decisions without changing the underlying state.

## Common failures

Match on the status and `code`, not on the message text.

| Status and `code` | What happened | What to do |
|---|---|---|
| `401` (`missing authorization header`, `invalid authorization format, expected Bearer token`, `invalid api key`) | The Engine got no `Authorization` header, one that is not `Bearer <key>`, or a key it does not know or that was revoked. A sandbox key (`sk_nozle_test_`) on a live organization, a live key on a sandbox and a key of a reset sandbox are refused the same way, and Core answers `{"status": 401, "error": "Unauthorized"}`. | Send `Authorization: Bearer sk_...` with a current key of the environment you mean. See [Live and sandbox keys](/api/authentication#live-and-sandbox-keys). |
| `403` (`publishable_key_not_allowed` from Core; a `403` message from the Engine) | A `pk_` key called something other than the plan catalog. | Call from your backend with an `sk_` key. See [public plan catalog](/api/list-plans). |
| `404` `customer_not_found` | No customer has that ID, for example on `subscribe`. | Create the customer with `POST /customers`, then call again. |
| `404` `active_subscription_not_found` | `usage.check` or `usage.track` for a customer with no active subscription. | Activate a subscription for the customer. |
| `422` `active_subscription_ambiguous` | The customer has more than one active subscription, so credit usage cannot pick one. | End all but one subscription. |
| `409` `idempotency_key_reused` | The `Idempotency-Key` was used before with a different request. | Retry the identical request with the same key, including the same `timestamp`. Use a new key for a new operation. See [usage tracking](/api/usage-track). |
| `409` `feature_billed_in_money` | `usage.check` or `usage.track` for a Feature that credits pay for and the plan also bills with a priced charge, which would bill the usage twice. | Set the charge to $0 so credits pay, or remove the credits so the charge bills. See [credits or money](/api/usage-track#credits-or-money-not-both). |
| `422` `feature_not_consumable` | The Feature is boolean or config, so there is no usage to consume. | Use a metered Feature. |
| `422` `credit_usage_configuration_invalid` (`no effective credit rate`) | The event time is before the credit rate became effective. | Use a later time, or fix the rate. |
| `200` with `error_details` from `POST /events/batch` (Engine 2.28.0) | Some events of the batch were refused, keyed by their position. The other events were stored. | Fix and resend only the listed events. Do not resend the whole batch. |
| `422` `validation_errors` with `events: ["too_many_events"]` | The batch has more than 5000 events (`no_events` when it is empty). Nothing is stored. | Send at most 5000 events per request. The SDK batch calls split for you. |
| `400` `invalid_request` | A field is missing or malformed, for example a `timestamp` that is a date only. | Read the message and fix the field. |
| `400` `invalid_return_url` | Core refused the checkout `return_url`: its origin is neither Nozle's nor one of your organization's `checkout_return_origins`. | Add the origin in the dashboard under **Developers > Checkout return**, or send a `return_url` on an allowed origin. Core's own checkout routes answer `422` `return_url: invalid_or_untrusted` for the same case. See [return URLs](/guides/billing/checkout#return-urls-and-your-organizations-origins) and [create checkout](/api/create-checkout). |
| `422` `customer_currency_mismatch` on `currency` (Core 11.9.0) | A subscription, invoice, wallet, top-up or fixed coupon is in another currency than the customer's. | Use the customer's currency, or allow several currencies per customer. See [customer currency](/api/create-customer#customer-currency). |
| `422` `customer_currency_locked` on `currency` (Core 11.9.0) | A customer update changed the currency while the customer has open subscriptions, unpaid invoices, wallet balance or credit left. | Keep the currency. See [customer currency](/api/create-customer#customer-currency). |
| `422` `currencies_does_not_match` on `plan_code` (every plan change path from Core 11.9.0) | A plan change targets a plan in another currency. | Pick a plan in the subscription's currency. |
| `422` `payment_provider_required` | The customer's payment provider is not connected. | Connect it, or assign one to the customer. See [checkout](/guides/billing/checkout). |
| `422` `payment_already_processing` in `error_details.base` (pay link, invoice checkout) | An automatic debit of the invoice is waiting for the bank to settle (for example an Indian card during the bank's notice), or a payment of its last Checkout Session is processing. Paying now would charge twice. | Wait for the `invoice.payment_status_updated` webhook. If the debit fails, ask for a pay link again. |
| `422` `invoice_carried_forward` in `error_details.base` (pay link, invoice checkout, Core 11.16.0) | The amount due is below the payment provider's minimum charge, so it was carried to the customer's next invoice. The invoice is settled. | Nothing to pay now. See [Amounts below the provider minimum](/guides/billing/invoices#amounts-below-the-provider-minimum). |
| `422` `invoices_carried_forward` (`POST /payment_requests`, Core 11.16.0) | Every invoice of the payment request is below the payment provider's minimum charge and was carried to the next invoice. Nothing is created. | Nothing to collect now. |
| `503` `credit_usage_contention` (`Retry-After: 1`), `credit_usage_temporarily_unavailable` (`Retry-After: 1`), `credit_usage_publication_backlog` (`Retry-After: 30`) | The credit balance is busy, or publication is delayed: 1,000 or more usage events are still being retried, or the oldest is older than 5 minutes. A dead-lettered event no longer blocks usage. | Retry the same request with the same `Idempotency-Key` after the `Retry-After` seconds. |
| `503` `usage_unavailable` from `can()` | The usage lookup failed, or (Engine 2.31.0) lost usage counters are being rebuilt and the feature has a hard usage limit. The body carries a `request_id`. | Treat it as an unavailable decision, not a denial, and retry after a second. Quote the `request_id` if it persists. |
| `503` `budget_unavailable` (Engine 2.31.0) | `/can`, `/usage/check`, `/usage/track` or the budgets list could not read the spend limits while a hard one may apply. | Retry after `Retry-After` (1 second). It is not a denial. |
| `422` `spend_limit_unrateable_charges` (Core 11.23.0) | A spend limit covers a usage charge the Engine cannot rate per event. `charges` lists them. | Change the charge model or the Feature's aggregation, or limit another Feature. See [what can be limited](/guides/entitlements/spend-limits#what-can-be-limited). |

An event that was accepted but never counted usually means the event name does not equal the feature code, or processing has not finished: events are processed asynchronously, so read usage again after a few seconds.

## Multi-currency plan family errors

Available from Core 11.10.0. These come from plans sold in several currencies. All are `422` with `code: validation_errors` unless noted; the key in `error_details` comes before the colon. See [Multi-currency pricing](/guides/billing/multi-currency-pricing).

| Status and `code` | What happened | What to do |
|---|---|---|
| `422` `plan_family: plan_family_variant_mismatch` | A plan of the family differs from the reference plan of its interval in something other than money. `error_details.plan_family_variant_mismatch` lists `plan_code`, `currency`, `interval`, `reference_plan_code`, `reference_currency` and the first differing `field`. | Make the structure match; only money may differ. See [the parity rule](/guides/billing/multi-currency-pricing#the-parity-rule). |
| `422` `plan_family: plan_family_variant_prices_missing` | An edit changes the structure, and another currency's plan has no amount for a new or rescaled part (a new charge or tier, a changed `package_size`, a changed threshold `recurring` flag, changed `custom_properties`). Nothing is saved. `error_details.plan_family_variant_prices_missing` lists `plan_code`, `currency` and `field`. | Send the amounts in `currency_amounts` with `PUT /plans/{code}`. A part-edit endpoint cannot take them. See [Edit prices](/guides/billing/multi-currency-pricing#edit-prices-in-several-currencies). |
| `422` `plan_family: plan_family_custom_charge_not_supported` | A `custom` charge on an interval sold in several currencies. Same detail as above. | Sell that interval in one currency, or use another charge model. |
| `422` `currency_amounts: value_is_invalid` | `currency_amounts` names a currency that is not another plan of the edited plan's interval, or a path that plan does not have. `error_details.currency_amounts_invalid` lists `currency` and `field`. | Use uppercase codes of the family's other currencies and the paths of the error's `field`. |
| `422` `interval: plan_family_interval_already_exist` | The family already has a current plan for this interval and currency. | Edit that plan, or use another family. |
| `422` `currencies: plan_family_currency_in_use` | `updatePlanFamily` leaves out a currency the family sells. | List every sold currency. Stop selling one by deleting its plans. |
| `422` `currencies: plan_family_currency_not_sold`, `default_currency: plan_family_currency_not_sold` | `updatePlanFamily` names a currency no current plan of the family sells. | Create a plan in that currency first. |
| `422` `currency: value_is_invalid` | `GET /plans` with an unknown `currency`. | Send an ISO 4217 code. |
| `422` `currency: currency_not_offered` | Checkout or subscribe by `plan_family_code`: the family has no plan for this interval and currency. | Pick one of the family's `prices[]`. |
| `422` `interval: value_is_mandatory`, `interval: value_is_invalid` | Checkout or subscribe by `plan_family_code` without an `interval`, or with an unknown one. | Send `weekly`, `monthly`, `quarterly`, `semiannual` or `yearly`. |
| `422` `plan_family_code: incompatible_with_plan_code` | Both `plan_code` and `plan_family_code` were sent. | Send one of them. |
| `404` `plan_family_not_found` | No plan family has this `plan_family_code`. | Check the code in `families[]` of `GET /plans`. |
| `400` `invalid_request` (Engine 2.21.0) | `currency` or `external_customer_id` on the Engine `GET /plans` is repeated, longer than 255 bytes or has a control character. | Send each once. |
| `403` `customer_scope_mismatch` (Engine 2.21.0) | A customer-scoped catalog request names another customer in `external_customer_id`. | Leave it out; the request lists its own customer's currency. |
| `422` `unknown_currency`, `404` `fx_rates_not_found`, `400` `invalid_date` (Engine 2.21.0) | `GET /fx/rates` with a `base` that has no stored rate, a `date` before every stored rate, or a malformed `date`. | Use an ISO 4217 code, a later date, and `YYYY-MM-DD`. |
| `400` `invalid_request` (Engine 2.21.0) | `GET /analytics/revenue-by-plan` with a `group_by` other than `plan` or `family`. | Send `plan` or `family`. |

## Sandbox errors

_Unreleased._ These come from a [sandbox](/guides/getting-started/sandbox), mostly from the dashboard.

| Status and `code` | What happened | What to do |
|---|---|---|
| `422` `sandbox_requires_test_key` | A live Stripe or Razorpay credential was used in a sandbox (connection or Stripe import). The field is `secret_key` (Stripe) or `key_id` (Razorpay). | Use `sk_test_`, `rk_test_` or `rzp_test_`. |
| `403` `not_available_in_sandbox` | A payment provider other than Stripe and Razorpay, or a tax, accounting or CRM integration, was connected in a sandbox. | Test it in live, or leave it out of sandbox tests. |
| `422` `not_available_in_sandbox` | A customer email was resent (`POST /invoices/{id}/resend_email`, credit notes, payment receipts) in a sandbox. | Nothing to do: a sandbox sends no customer email. |
| `403` `live_organization_only` | Members, invitations, roles, sign-in methods and SSO, your Nozle plan and billing, or AI onboarding, from a sandbox. | Switch to live. |
| `429` `sandbox_reset_rate_limited` | The sandbox was reset more than once in 10 minutes or 5 times in a day. | Wait and reset again. |

## Workspace billing errors

_Unreleased._ These errors are about your own workspace's account with Nozle, not about your customers. They are always on. A sandbox key gets the same errors as the live organization it belongs to. See [Workspace billing](/guides/getting-started/workspace-billing).

| Status and `code` | What happened | What to do |
|---|---|---|
| `402` `workspace_suspended` | Nozle invoices of your workspace stayed unpaid until the end of the grace of your Nozle plan (7 days by default). Wins over `card_required` when both apply. | Do not retry blindly: every retry is refused until the invoices are paid. Pay the Nozle invoices (the **Nozle invoices** page or the link in the emails). The next request works again. |
| `402` `card_required` | Nozle no longer asks for a card at onboarding and no longer sets this code. A workspace flagged before that change gets it until the flag is cleared at the release. | A member adds a card in the dashboard, or waits for the flag to be cleared. |
| `422` `workspace_past_due` | A downgrade (immediate or scheduled for the end of the period) or a cancellation of your Nozle plan while a Nozle invoice is past due. The plan change preview of a downgrade is refused too. Upgrades, paying and adding a payment method are allowed. Dashboard GraphQL carries it in `extensions.code`. | Pay the owed Nozle invoices, then change the plan. |

Do not retry either `402`. The Nozle SDKs surface a `402` as their API error with `code` `workspace_suspended` or `card_required`, and never retry it.

Bodies by surface (`CODE` is `card_required` or `workspace_suspended`):

| Surface | Body |
|---|---|
| Core REST with an API key | `{"status": 402, "error": "Payment Required", "code": "CODE"}` |
| Engine API with an API key | `{"code": "CODE", "error": "<text>"}` |
| Event ingestion | `{"status": 402, "error": "<text>", "code": "CODE"}` |
| LLM proxy | The error shape of the provider the route targets, with `code` also at the top level. See [LLM proxy errors](/api/llm-proxy#errors). |
| Account MCP | `{"error": "CODE", "error_description": "<text>"}` |
| Dashboard GraphQL | the field fails with `extensions.code = "CODE"` (HTTP 402) |
| Dashboard-login routes (`/api/v1/onboarding/...`, `/oauth/authorize`) | a JSON error `CODE` |

Texts:

| Surface | `card_required` | `workspace_suspended` |
|---|---|---|
| Engine API and event ingestion | `Add a card to your Nozle workspace to use the API.` | `This workspace is suspended because its Nozle invoices are unpaid. Pay them to resume.` |
| Account MCP | `Add a card to your Nozle workspace` | `Pay the Nozle invoices to unblock this workspace` |

A refused event is not queued and is not billed later: see [what is lost](/guides/getting-started/workspace-billing#suspension).

## Customer payment overdue

_Unreleased (Engine 2.22.0, Core 11.16.0)._ The Engine answers `402` `customer_payment_overdue` for one of your customers whose unpaid invoices are past the grace of their plan, when the dunning campaign they follow ends with `block`. Your other customers are not affected. See [Dunning policy](/guides/billing/dunning).

| Surface | Body |
|---|---|
| `GET /can` | `{"allowed": false, "reason": "customer_payment_overdue", "code": "customer_payment_overdue", "error": "<text>"}` |
| `POST /usage/check`, `POST /usage/track` | `{"code": "customer_payment_overdue", "error": "<text>"}` |
| LLM proxy, OpenAI routes | `{"error": {"message": "<text>", "type": "payment_required", "code": "customer_payment_overdue"}, "code": "customer_payment_overdue"}` |
| LLM proxy, Anthropic routes | `{"type": "error", "error": {"type": "billing_error", "message": "<text>", "code": "customer_payment_overdue"}, "code": "customer_payment_overdue"}` |
| `POST /events` | `{"status": 402, "error": "<text>", "code": "customer_payment_overdue"}` |
| `POST /events/batch`, every event refused | `{"status": 402, "error": "<text>", "code": "customer_payment_overdue", "error_details": {"<index>": {"external_customer_id": ["customer_payment_overdue"]}}}` |
| `POST /events/batch`, some events refused | `200` with the stored `events` and the refused ones in `error_details`, keyed by index. From Engine 2.28.0 invalid events are refused the same way, so a batch is no longer all or nothing. |

The text is `This customer's invoices are unpaid past their grace period. Usage resumes once they are paid.` Do not retry: the block lifts on the next request after the invoices are paid, voided or credited. Refused events are not queued.

## Spend and usage limits

_Engine 2.31.0, Core 11.23.0._ A customer that used up a hard [spend limit](/guides/entitlements/spend-limits) is refused with `budget_exceeded`; a hard usage limit in units refuses with `usage_limit_exceeded`. Both are about that customer, not your workspace, and retrying does not help until the period ends or the limit is raised.

| Surface | Answer |
|---|---|
| `GET /can` | `200` `{"allowed": false, "reason": "budget_exceeded", ..., "budget": {...}}`; `usage_limit_exceeded` the same way, without `budget` |
| `POST /usage/check`, `POST /usage/track` | `200` `{"allowed": false, "reason": "budget_exceeded", "budget": {...}}` |
| `POST /usage/holds` | `200` budget hold with `allowed: false`, `status: "denied"`, `reason: "budget_exceeded"` and `budget` |
| LLM proxy | `402` `budget_exceeded` with a top-level `budget`; `429` `usage_limit_exceeded`. Both in the provider's error shape. |
| `POST /events`, `POST /events/batch` | Never refused by a limit: usage that happened is billed. |

The SDKs return the `200` refusals as results. Where a call throws for an error response, a `402` `budget_exceeded` is a `BudgetExceededError` (with `budget`) and a `429` `usage_limit_exceeded` a `UsageLimitExceededError`, in [Node.js](/sdks/node/errors#spend-and-usage-limits), [Python](/sdks/python/errors#spend-and-usage-limits) and [Go](/sdks/go/errors#spend-and-usage-limits). They do not retry a `usage_limit_exceeded`.

Setting a limit can fail with `422` `spend_limit_unrateable_charges`:

```json
{
  "status": 422,
  "error": "Unprocessable Entity",
  "code": "spend_limit_unrateable_charges",
  "charges": [{ "code": "storage_gb", "charge_model": "custom" }]
}
```

Saving a charge or charge filter the Engine cannot rate, on a plan whose spend limit with an amount covers it, fails with `422` `validation_errors` and `charge_model` (or `properties` for a filter): `spend_limit_unrateable_charges`.
