---
title: "Subscription self-service"
description: "Select a subscription, preview a signed quote, recover checkout, and withdraw a pending downgrade."
---

Base URL: `https://api.nozle.app/engine/api/v1`. All routes below require a secret key and an authenticated merchant backend. The backend derives `customer_id`; the selected **external** `subscription_id` must belong to that customer and organization.

These hosted endpoints are available. Use their SDK wrappers and controls with React `0.10.2`, Node `0.10.0`, Python `0.10.0`, or Go `v0.9.1`, or later; see [the billing portal integration](/sdks/react/billing-portal).

## Endpoint map

| Operation | Method and path |
| --- | --- |
| Current plan, pending change and eligible plans | `GET /subscriptions/options?customer_id=…&subscription_id=…` |
| Signed plan-change quote | `POST /subscriptions/preview` |
| Quoted upgrade | `POST /checkout` |
| Cancel, Keep or scheduled downgrade | `POST /subscriptions/transitions` |
| Cancellation/Keep preview | `POST /subscriptions/transitions/preview` |
| Withdraw a specific pending downgrade | `POST /subscriptions/transitions/withdraw` |
| Recover checkout | `GET /checkout/{checkout_id}?customer_id=…&subscription_id=…` |
| Verify Razorpay checkout | `POST /checkout/{checkout_id}/verify?customer_id=…&subscription_id=…` |

These paths are for Engine. Its customer/subscription fields map to Core's external identifiers; Core uses `/subscription_transitions/options` and `/subscription_transitions/withdraw` under its own `/api/v1` base. Do not mix the two path sets.

## Read state and eligible plans

`GET /subscriptions/options` returns:

| Field | Meaning |
| --- | --- |
| `subscription` | Internal `id`, `external_id`, `plan_code`, `status`, nullable `ending_at`, and `plan`. |
| `pending_change` | Pending internal `id`, `plan_code`, `name`, `effective_at` and `plan`, or null. |
| `eligible_plans` | Plans with `direction` and `timing`, allowed by the [default policy](/api/plan-transition-policies#the-default-policy) or by a configured [transition policy](/api/plan-transition-policies) for the pair, which wins. Without a pair policy, public plans are listed: upgrades with `timing` `immediate`, downgrades at the end of the period. From a free plan, paid plans also appear through the organization's free-to-paid policy. An immediate downgrade is listed only when a pair policy allows it. |
| `checkout` | Latest intent summary `{ id, status, plan_code }`, or null. Use checkout status for payment recovery. |

`pending_change.effective_at` and the quote's `effective_at` are RFC 3339 timestamps in the customer's timezone, for example `2026-11-01T00:00:00.000000+05:30`. Parse the offset; do not assume `Z`.

A plan contains `code`, `name`, `amount_cents`, `currency`, and `interval`. Keep monetary minor-unit values exact. An empty eligible list can reflect a trial, hidden or older plans that need a pair policy, scheduled cancellation, a pending change, external billing authority, or unresolved checkout. Price comparisons and public catalog membership do not establish permission to change plans.

## Preview and confirm a plan change

Send `customer_id`, `subscription_id`, and `plan_code` to `POST /subscriptions/preview`:

```json
{
  "customer_id": "customer_123",
  "subscription_id": "subscription_123",
  "plan_code": "pro_monthly"
}
```

This route needs the `invoice:read` API permission, not a `subscription` permission. `subscription_id` is optional, but without it a customer with several active subscriptions gets `409 subscription_selection_required`.

The response includes `quote_id`, `transition_direction`, `timing`, `currency`, `credit_amount_cents`, `debit_amount_cents`, `net_amount_cents`, `amount_due_now_cents`, `amount_due_at_effective_cents`, `effective_at`, and nullable `renewal_at`.

It also includes `subscription_id` (Core's internal UUID of the current subscription), `external_subscription_id`, `invoice_issuing_date`, and `next_billing_date` with its camel-case alias `nextBillingDate`. `credit`, `debit`, and `net` repeat the three cent amounts in major units (for example `12.5`); use the `*_cents` fields for exact values.

Previewing a change that the [default policy](/api/plan-transition-policies#the-default-policy) does not allow and no pair policy covers (an immediate downgrade, a hidden or older plan, a trial) returns `422 plan_transition_policy_required`. The response also echoes the policy it applied: `transition_policy`, `billing_anchor`, `proration_behavior`, `credit_action`, `refund_mode`, and `final_invoice_action`.

A plan that is pending deletion cannot be a target: the preview, the checkout and `POST /subscriptions` return `422` with `plan_code: [plan_pending_deletion]`. Applying an immediate downgrade that leaves an amount due returns `422 payment_required`; the customer pays that change first through [Create checkout](/api/create-checkout).

Quotes expire after five minutes. Show the returned amounts and dates for confirmation, and forward the opaque `quote_id` unchanged. State, policy or amount changes invalidate the quote with HTTP 409. Refresh and obtain a new confirmation instead of silently applying a different price.

For an upgrade, send that quote with an `Idempotency-Key` header to [Create checkout](/api/create-checkout):

```json
{
  "customer_id": "customer_123",
  "subscription_id": "subscription_123",
  "plan_code": "pro_monthly",
  "quote_id": "opaque-signed-quote",
  "return_url": "https://app.example.com/settings/billing"
}
```

Use explicit subscription selection. A customer with multiple active subscriptions cannot use an ambiguous unselected preview/checkout. Replays of an already accepted quoted request reuse the original result even after quote expiry; preserve the same request and idempotency key when recovering an uncertain response.

## Schedule a downgrade

After confirming a downgrade quote, send `POST /subscriptions/transitions` with an `Idempotency-Key` and:

```json
{
  "customer_id": "customer_123",
  "subscription_id": "subscription_123",
  "operation": "downgrade",
  "target_plan_code": "starter_monthly",
  "timing": "end_of_period",
  "billing_anchor": "keep_anchor",
  "quote_id": "opaque-signed-quote"
}
```

The existing transition result is nested under `subscription_transition`. Reload options to display the current plan separately from the pending plan and its effective date. The self-service flow uses end-of-period timing and preserves the billing anchor.

Scheduling or replacing a downgrade sends the `subscription.updated` webhook for the pending subscription. A downgrade cannot be scheduled while the subscription is cancelling at period end: the call returns `409 subscription_change_pending`. Keep the subscription first, then schedule the downgrade.

## Cancel and Keep

Preview `operation: "cancel"` with `timing: "end_of_period"` through `/subscriptions/transitions/preview`. Send the same parameters to `/subscriptions/transitions` with `expected_effective_at` set to the exact preview's `subscription_transition.effective_at`, plus an `Idempotency-Key` header. A stale date returns HTTP 409 before cancellation.

Keep uses `operation: "uncancel"`, the customer/subscription identifiers and an `Idempotency-Key`. It accepts no settlement overrides. Keep also clears the settlement the cancellation stored, such as skipping the credit note or the final invoice, so a later cancellation follows its own request or your organization's policy again. Keep is available only before the ending is due; it does not restart a terminated subscription. Cancellation removes a pending downgrade and cancels an open paid upgrade checkout, and Keep does not recreate them.

## Withdraw a pending downgrade

Read and retain `pending_change.id` from options when the customer opens the confirmation. Send `POST /subscriptions/transitions/withdraw` with an `Idempotency-Key` and:

```json
{
  "customer_id": "customer_123",
  "subscription_id": "subscription_123",
  "pending_subscription_id": "46c9e633-1314-4842-997a-97f801a58029"
}
```

`pending_subscription_id` is the pending internal UUID, not the active subscription's external ID. Core, called directly at `POST /subscription_transitions/withdraw`, names the other two fields `external_customer_id` and `external_subscription_id`. The response contains `subscription`, `withdrawn_pending_subscription_id` and `replayed`. A stale owned pending ID returns `409 pending_subscription_changed`; an unknown or unowned resource returns `404 pending_subscription_not_found`. The same idempotency key returns the original result with `replayed: true`. The active subscription remains in place.

A new scheduled change while a change is pending replaces that change and creates a new pending ID. Re-read `pending_change.id` from options before you withdraw. A paid upgrade checkout is refused with `409 subscription_change_pending` while a downgrade or cancellation is scheduled: withdraw the pending downgrade, or keep the subscription, first. Scheduling a change or cancelling at period end cancels an open upgrade checkout. See [Paid upgrades: rules](/api/create-checkout#paid-upgrades-rules).

## Outstanding invoices and lost disputes

A plan change that takes effect now is refused with `422 outstanding_invoice` while the subscription has an unpaid invoice, or a paid invoice whose payment was lost in a dispute (a chargeback). This covers the quote, `POST /checkout`, an immediate `POST /subscriptions/transitions` (and its preview) and the options. The invoice is listed in `outstanding_invoices`; a dispute-lost invoice shows `total_due_amount_cents: 0`. A checkout paid after the dispute was lost ends in `needs_review` (`plan_upgrade_outstanding_invoice`). A termination or plan change never credits the unused part of a period whose payment was lost in a dispute. Before, a lost dispute left the invoice paid, so the change went ahead and credited money the customer had already got back.

## Payment status and recovery

Use both `customer_id` and `subscription_id` when recovering or verifying a customer checkout. Razorpay verification forwards the genuine browser fields `razorpay_order_id`, `razorpay_payment_id` and `razorpay_signature`. Provider secrets stay on the server; only the scoped checkout's public key reaches Razorpay's browser UI.

Status returns `checkout_id`, `provider`, `status`, `fulfillment_status`, `amount_cents`, `currency`, optional `invoice_id`, and optional resumable `checkout`. Payment status is `awaiting_payment`, `processing`, `succeeded`, `failed`, `expired`, or `needs_review`; fulfillment is `pending`, `processing`, or `succeeded`.

A successful browser callback is not proof of fulfillment. Wait for authoritative activation and reload the selected subscription. Razorpay upgrades require a captured payment. `needs_review` on a paid upgrade (observed with Stripe) also appears when a dispute was lost on a previous invoice of the subscription: the payment is taken but the upgrade is not applied. An upgrade while a downgrade or cancellation is pending is refused up front with `409 subscription_change_pending`, before the customer pays. See [Paid upgrades: rules](/api/create-checkout#paid-upgrades-rules). Retry a recoverable open checkout using its existing ID; treat expired checkouts and `needs_review` as distinct outcomes. Unknown payment outcomes require your support/reconciliation route before another collection.

Idempotency keys must be nonempty and at most 255 UTF-8 bytes. Keep one key and the same payload for retries of one confirmed action; use a new key for a newly confirmed action. Persist merchant replay context across process restarts. Map ownership failures, stale confirmations and payment-review states without exposing raw upstream error bodies.
