---
title: LLM Proxy
description: Reverse proxy for OpenAI and Anthropic with automatic token tracking
---


Base URL: `https://api.nozle.app/engine/api/v1`

Reverse proxy routes that forward LLM requests to OpenAI or Anthropic and record their token usage as a usage event in your organization. The event is stored durably before the proxied response returns and is sent to your organization's usage events with your organization's own secret key, not the `X-Nozle-Key` of the request. If Nozle's billing service is unavailable, delivery is retried with backoff for about five hours. Each event is keyed by its transaction ID, so a retry never records usage twice. Use it when you cannot change your LLM client. When you can, prefer [usage capture in the SDK](/sdks/node/llm-auto-capture): it works with any provider and keeps LLM traffic out of Nozle.

The usage event bills only when your plan has a metered Feature with the same code; see [Set up AI token billing](/guides/ai/token-billing).

<Warning>
LLM proxy routes use `X-Nozle-Key` for Nozle authentication, **not** the `Authorization` header. The `Authorization` header is reserved for the customer's own LLM provider API key, which the proxy forwards untouched to the provider.
</Warning>

---

## /api/v1/proxy/openai/v1/*

Proxies all requests to `https://api.openai.com/v1/*`. Usage is recorded for chat completions (including streams), the Responses API and embeddings.

**Auth:** `X-Nozle-Key` header (`sk_` only)

**Required headers:**

| Header | Description |
|--------|-------------|
| `X-Nozle-Key` | Your Nozle secret key (`sk_nozle_...`). It needs `event:write` permission. |
| `X-Nozle-Customer-Id` | External customer ID to bill for this usage. Missing returns `400`. |
| `Authorization` | Customer's OpenAI API key (`Bearer sk-...`) |

**Optional headers:**

| Header | Description |
|--------|-------------|
| `X-Nozle-Subscription` | External subscription ID to bill. It must be an active subscription of that customer. Needed when the customer has several active subscriptions. |
| `X-Nozle-Feature-Code` | Code of the usage event. Default `llm_tokens`. Must match a metered Feature to bill. |
| `X-Nozle-Feature` | Stored as the `feature` property of the event. |
| `X-Nozle-Credit-Hold` | Metric amount to reserve in credits before the provider is called, for example the most tokens the call can use. Engine 2.33.0. See [Credit holds](#credit-holds). |

```bash title="cURL"
curl -X POST https://api.nozle.app/engine/api/v1/proxy/openai/v1/chat/completions \
  -H "X-Nozle-Key: sk_nozle_your_secret_key" \
  -H "X-Nozle-Customer-Id: cust_123" \
  -H "Authorization: Bearer sk-customer-openai-key" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "<openai-model>",
    "messages": [{"role": "user", "content": "Hello"}]
  }'
```

## /api/v1/proxy/anthropic/v1/*

Proxies all requests to `https://api.anthropic.com/v1/*`.

**Auth:** `X-Nozle-Key` header (`sk_` only)

**Required headers:**

| Header | Description |
|--------|-------------|
| `X-Nozle-Key` | Your Nozle secret key (`sk_nozle_...`). It needs `event:write` permission. |
| `X-Nozle-Customer-Id` | External customer ID to bill for this usage. Missing returns `400`. |
| `x-api-key` | Customer's Anthropic API key |
| `anthropic-version` | Anthropic API version |

**Optional headers:**

| Header | Description |
|--------|-------------|
| `X-Nozle-Subscription` | External subscription ID to bill. It must be an active subscription of that customer. Needed when the customer has several active subscriptions. |
| `X-Nozle-Feature-Code` | Code of the usage event. Default `llm_tokens`. Must match a metered Feature to bill. |
| `X-Nozle-Feature` | Stored as the `feature` property of the event. |
| `X-Nozle-Credit-Hold` | Metric amount to reserve in credits before the provider is called, for example the most tokens the call can use. Engine 2.33.0. See [Credit holds](#credit-holds). |

```bash title="cURL"
curl -X POST https://api.nozle.app/engine/api/v1/proxy/anthropic/v1/messages \
  -H "X-Nozle-Key: sk_nozle_your_secret_key" \
  -H "X-Nozle-Customer-Id: cust_123" \
  -H "x-api-key: customer-anthropic-key" \
  -H "anthropic-version: 2023-06-01" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "<anthropic-model>",
    "max_tokens": 1024,
    "messages": [{"role": "user", "content": "Hello"}]
  }'
```

<Info>
The proxy returns the provider's response unchanged. Your customer's API key is forwarded but never stored. Token usage is read from the response and recorded as a usage event in your organization, with the code from `X-Nozle-Feature-Code` (default `llm_tokens`) and the `external_subscription_id` of the subscription it is billed to.
</Info>

<Warning>
Before this release the proxy recorded usage under Nozle's own organization instead of yours, so proxy usage from earlier calls is not in your account.
</Warning>

## Subscription

Engine finds the subscription to bill before it calls the provider. Without `X-Nozle-Subscription`, the customer must have exactly one active subscription. With it, that subscription must be an active subscription of the customer in your organization. Otherwise Engine answers `422` and the provider is not called:

| Case | Response |
|------|----------|
| Unknown customer, no active subscription, or `X-Nozle-Subscription` names no active subscription of the customer | `422 active_subscription_not_found` |
| Several active subscriptions and no `X-Nozle-Subscription` | `422 active_subscription_ambiguous` |
| The lookup failed | `503 unavailable`. Retry later. |

## How it works

- The path after `/proxy/openai/` or `/proxy/anthropic/` is sent to the provider host unchanged, with the same method, query string, headers and body, except as noted below.
- Engine removes `X-Nozle-Key`, `X-Nozle-Customer-Id`, `X-Nozle-Subscription`, `X-Nozle-Feature`, `X-Nozle-Feature-Code` and `X-Nozle-Credit-Hold` before forwarding. All other headers, including `Authorization` and `x-api-key`, are forwarded. `Accept-Encoding` is set to `identity` so the usage can be read.
- A chat completion stream (`"stream": true` to `/chat/completions`) is sent with `stream_options.include_usage: true`, because OpenAI leaves usage out of streams otherwise.
- Streaming (`text/event-stream`) responses are passed through as they arrive; usage is read from the stream as it passes.
- Usage is recognised by the shape of the response: chat completions, the Responses API, and Anthropic messages, including cached input and cache writes.
- An event is recorded only for a successful response that reports more than zero tokens. It carries `external_customer_id` and the resolved `external_subscription_id`, so it is billed to that subscription. Its `transaction_id` is `llm-<format>-<response id>`, so the same response is never billed twice. Its properties are `provider`, `provider_host`, `model`, `input_tokens` (all input, including cached), `output_tokens`, `latency_ms` and, when sent, `feature`. Recording runs in the background; a recording failure does not change the response.

## Credit holds

From Engine 2.33.0, a call can reserve the customer's credits before it reaches the provider, so concurrent calls cannot spend the same credits. Holds are opt-in per request: without `X-Nozle-Credit-Hold`, the proxy works as described above. See [Create a Credit Hold](/api/create-usage-hold) for how holds reserve credits.

```bash title="cURL"
curl -X POST https://api.nozle.app/engine/api/v1/proxy/openai/v1/chat/completions \
  -H "X-Nozle-Key: sk_nozle_your_secret_key" \
  -H "X-Nozle-Customer-Id: cust_123" \
  -H "X-Nozle-Feature-Code: llm_tokens" \
  -H "X-Nozle-Credit-Hold: 4000" \
  -H "Authorization: Bearer sk-customer-openai-key" \
  -H "Content-Type: application/json" \
  -d '{"model": "<openai-model>", "max_tokens": 2000, "messages": [{"role": "user", "content": "Hello"}]}'
```

- **The amount is yours to give.** `X-Nozle-Credit-Hold` is a positive decimal metric amount of the Feature in `X-Nozle-Feature-Code` (default `llm_tokens`), for example the prompt size plus `max_tokens`. Engine never estimates it from the request body. Any other value answers `400 invalid_request`. The header is not forwarded to the provider.
- **Taken after the usage limit and margin checks.** When the balance does not cover the amount, the proxy answers `402 insufficient_credits` and the provider is not called. Otherwise the response carries `X-Nozle-Credit-Hold-Id` with the hold's ID, and the hold lasts the default 15 minutes.
- **Paid from the hold.** When the call succeeds, the proxy finalizes the hold with the token usage it reads from the response, priced by the Feature's credit rate from the event properties. That credit spend sends the call's usage event, so it replaces the usage event the proxy would otherwise send, and the call is billed once. Less usage than held releases the rest.
- **No usage, no charge.** A provider error, a response the proxy cannot read, or a stream cut before its usage releases the hold.
- **Usage above the hold and the free balance.** For a Feature whose metric sums a property (such as tokens), the proxy pays the largest metric amount the hold plus the free balance covers, at the hold's rate. The balance ends at 0 and never goes below; at a rate whose price does not end within 12 decimals it can keep less than one 12-decimal step (under `0.000000000001`). The unpaid rest of the metric is sent as a usage event whose metric property holds only that rest, with `credit_overrun: true`, `credit_overrun_metric_amount`, `credit_hold_id` and `credit_operation_id` (the credit operation that paid the covered part). The call is counted once: the covered part through the credit spend, the rest through this event. For a metric that counts events, the hold is released and the whole usage is sent as a plain usage event instead.
- **Fallback.** If the finalize fails, the hold is released and the usage is sent as a plain usage event, as without a hold. If Nozle cannot confirm that the hold was not finalized, nothing is sent and the miss is logged: the hold expires on its own, and the call is not charged twice. A finalize of 0 tokens also sends the plain event.
- **When no hold is taken.** For a Feature with no credit rate, a Feature the plan bills in money, or a Feature that is not consumable, the call goes ahead without a hold. From Engine 2.34.0, a Feature billed in money under a hard spend limit takes a budget hold instead: see [Spend limits](#spend-limits). If holds are unavailable, the call is not refused (fail open, as the usage limit check does).

## Spend limits

From Engine 2.34.0 the proxy enforces the customer's [spend limits](/guides/entitlements/spend-limits) before the provider is called, after the usage limit check and with the same decision as [`/can`](/api/check-entitlement#spend-limits). When a hard spend limit covering the `X-Nozle-Feature-Code` Feature is used up, the proxy answers `402 budget_exceeded` and adds the limit as a top-level `budget` next to the provider-shaped error:

```json
{
  "error": {
    "message": "the customer's hard spend limit is reached",
    "type": "payment_required",
    "code": "budget_exceeded"
  },
  "code": "budget_exceeded",
  "budget": {
    "feature_code": "llm_tokens",
    "limit": "200",
    "spent": "200.31",
    "held": "0",
    "remaining": "0",
    "currency": "USD",
    "period": "billing_period",
    "period_start": "2026-11-01T00:00:00Z",
    "period_end": "2026-12-01T00:00:00Z",
    "mode": "hard",
    "status": "exceeded",
    "as_of": "2026-11-14T09:29:58.104Z"
  }
}
```

- `budget_exceeded` is `402`, like `insufficient_credits`. A hard usage limit in units stays `429 usage_limit_exceeded`.
- Without `X-Nozle-Credit-Hold` the check is check-then-call: calls already in flight can take the spend past the limit before the next call is refused.
- **Exact caps.** With `X-Nozle-Credit-Hold: <metric amount>` on a Feature billed in money under a hard spend limit, the proxy takes a budget hold for the call's estimated spend (the charge's price of that amount). When it does not fit, the answer is `402 budget_exceeded` with the message `the customer's hard spend limit does not cover the requested hold`, and the provider is not called. Otherwise the response carries `X-Nozle-Credit-Hold-Id`, and the call's usage is sent as the hold's event, so the spend is counted once.
- If the spend limits or the hold cannot be read, a customer this proxy instance last saw over a hard limit stays refused: the last `budget_exceeded` or `usage_limit_exceeded` refusal is kept until its `period_end` (10 minutes when it has none) and answered again with the same body and `budget` block. Any other call goes ahead with the response header `X-Nozle-Budget-Unverified: true` (from Engine 2.34.0).

## Errors

These come from Engine. Provider errors are returned unchanged, with the provider's status and body.

From Engine 2.22.0 (_Unreleased_), every refusal of the proxy has the error shape of the provider the route targets, so the provider's SDK surfaces the code. The top-level `code` is kept. Before, the body was `{"code": "...", "error": "<message>"}`, with `error` a string.

OpenAI routes:

```json
{
  "error": {
    "message": "This customer's invoices are unpaid past their grace period. Usage resumes once they are paid.",
    "type": "payment_required",
    "code": "customer_payment_overdue"
  },
  "code": "customer_payment_overdue"
}
```

Anthropic routes:

```json
{
  "type": "error",
  "error": {
    "type": "billing_error",
    "message": "This customer's invoices are unpaid past their grace period. Usage resumes once they are paid.",
    "code": "customer_payment_overdue"
  },
  "code": "customer_payment_overdue"
}
```

`error.type` follows the status: `invalid_request_error` for `400` and `422`, `authentication_error` for `401`, `payment_required` (OpenAI) or `billing_error` (Anthropic) for `402`, `permission_error` for `403`, `rate_limit_error` for `429`, and `api_error` for `503`.

| Status | `code` | Message | Meaning |
|--------|--------|---------|---------|
| `400` | `invalid_request` | `missing X-Nozle-Customer-Id header` | `X-Nozle-Customer-Id` is missing. |
| `400` | `invalid_request` | `request body could not be read` | The request body could not be read. |
| `400` | `invalid_request` | `X-Nozle-Credit-Hold must be a positive decimal metric amount` | Engine 2.33.0. `X-Nozle-Credit-Hold` is not a positive decimal. The provider is not called. |
| `401` | `unauthorized` | `missing X-Nozle-Key header` | `X-Nozle-Key` is missing. |
| `401` | `unauthorized` | `invalid nozle key` | The key is unknown. |
| `402` | `workspace_suspended` or `card_required` | | Your workspace is blocked by Nozle. See [Workspace billing errors](/api/errors#workspace-billing-errors). |
| `402` | `insufficient_credits` | `the customer's credit balance does not cover the requested hold` | Engine 2.33.0. The `X-Nozle-Credit-Hold` amount is not covered by the customer's free credits. The provider is not called. |
| `402` | `customer_payment_overdue` | `This customer's invoices are unpaid past their grace period. Usage resumes once they are paid.` | _Unreleased (Engine 2.22.0)._ The customer is blocked by your [dunning policy](/guides/billing/dunning). The provider is not called. |
| `402` | `budget_exceeded` | `the customer's hard spend limit is reached` | Engine 2.34.0. A hard [spend limit](#spend-limits) covering the Feature is used up. The body adds `budget`. The provider is not called. |
| `402` | `budget_exceeded` | `the customer's hard spend limit does not cover the requested hold` | Engine 2.34.0. The `X-Nozle-Credit-Hold` estimate does not fit in a hard spend limit. The body adds `budget`. The provider is not called. |
| `403` | `economic_policy_denied` | `the customer's margin policy denies this call` | A margin policy in `deny` mode refused the call. The provider is not called. |
| `403` | `publishable_key_not_allowed` | `publishable keys are limited to GET /api/v1/plans` | A publishable key was used. |
| `403` | `permission_denied` | `API key requires event:write permission` | The key cannot write events, so the call is refused before it reaches the provider. |
| `422` | `active_subscription_not_found` | `customer has no matching active subscription` | The customer is unknown, has no active subscription, or `X-Nozle-Subscription` names no active subscription of the customer. The provider is not called. |
| `422` | `active_subscription_ambiguous` | `customer has multiple active subscriptions; set X-Nozle-Subscription` | The customer has several active subscriptions. Send `X-Nozle-Subscription`. The provider is not called. |
| `429` | `usage_limit_exceeded` | `the customer's hard usage limit is reached` | The customer reached a hard usage limit of the Feature. A refusal, not a rate limit: retrying does not help until the limit or the period changes. The provider is not called. |
| `502` | | Empty body | Engine could not reach the provider. |
| `503` | `unavailable` | `API key verification is unavailable` | The key could not be verified. Retry later. |
| `503` | `unavailable` | `subscription lookup is unavailable` | The subscription could not be looked up. The provider is not called. Retry later. |
| `503` | `unavailable` | `customer payment state is unavailable` | _Unreleased (Engine 2.22.0)._ Whether the customer is blocked could not be read. The provider is not called. Retry later. |
