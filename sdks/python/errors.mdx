All SDK exceptions derive from `NozleError`.

| Exception | Meaning |
|---|---|
| `NozleValidationError` | Local contract validation failed before network I/O. Also derives from `ValueError`. |
| `NozleAuthenticationError` | The operation used an unsupported key type. Derives from `NozleValidationError`. |
| `NozleTransportError` | No HTTP response was received due to a `requests` transport failure. |
| `NozleAPIError` | Nozle returned a non-2xx response or an invalid JSON success payload. |

```python
from nozle import Nozle, NozleAPIError, NozleAuthenticationError, NozleTransportError, NozleValidationError

nozle = Nozle()  # reads NOZLE_SECRET_KEY

try:
    result = nozle.usage.track(
        "workspace_123",
        "agent_execution",
        idempotency_key="execution-0183f",
    )
except NozleAuthenticationError:
    logger.exception("Nozle secret-key configuration is invalid")
except NozleValidationError as error:
    logger.warning("Invalid Nozle request: %s", error)
except NozleTransportError as error:
    logger.warning("Nozle transport failed for %s", error.operation)
except NozleAPIError as error:
    logger.warning(
        "Nozle %s returned %s: %r",
        error.operation,
        error.status_code,
        error.response_details,
    )
```

Catch `NozleAuthenticationError` before `NozleValidationError` if the branches need different handling because authentication errors are a validation subtype.

## Safe API details

`NozleAPIError` exposes:

- `operation`;
- `status_code`;
- `response_details`;
- `request_id`, the `X-Request-Id` response header (Core sends it, the Engine does not yet), or `None`. Quote it when you contact support; and
- `retry_after`, the seconds from the `Retry-After` header (a number or an HTTP date), or `None`.

When `track()` resolves the subscription itself and the customer has no active subscription, or more than one, it raises `NozleAPIError` with `status_code` 422 and the code `active_subscription_not_found` or `active_subscription_ambiguous`, the same as the Engine. Before `0.17.0` the `status_code` was 200 and only the message gave the cause: do not treat 200 as success. See [subscription resolution](/sdks/python/tracking-events#subscription-resolution).

The transport redacts known secret, token, authorization, and key fields and replaces the active API key if it appears in a string response.

## Workspace blocked (`402`)

Your workspace answers HTTP `402` `workspace_suspended` when its Nozle invoices stayed unpaid past the grace of your Nozle plan (7 days by default). `card_required` is only for a workspace still flagged from before Nozle stopped asking for a card at onboarding. See [Workspace billing errors](/api/errors#workspace-billing-errors). Do not retry: the SDK never retries a `402`, and every retry is refused until a member adds a card or pays the Nozle invoices. Calls work again at once afterwards. Events sent while blocked are refused, not queued. A customer blocked by your [dunning policy](/guides/billing/dunning) gets `402` `customer_payment_overdue` instead; this SDK raises it as the same API error with that `code`.

```python
try:
    nozle.can("cust_123", "code_completion")
except NozleAPIError as error:
    if error.status_code == 402:
        # error.code is "card_required" or "workspace_suspended".
        ...  # tell your team to fix billing; neither allowed nor denied
```

## Retry behavior

By default the SDK does not retry, so a mutation is never replayed without application context. Set `max_retries` (and optionally `retry_delay`) to retry network errors, timeouts, `429` and `5xx` with backoff, or after `NozleAPIError.retry_after` seconds when the service sent `Retry-After`. Only requests that are safe to repeat are retried: reads, calls that carry an idempotency key (such as `usage.track`), event, cost event and customer writes, and the read-only usage check and transition preview. `subscribe`, `checkout` and other writes without a key are never retried.

- For idempotent Entity, credit-transfer, and usage mutations, retry with the same idempotency key and payload.
- For `track()`, retry the same event with the same transaction ID.
- Decide whether a read is safe to retry according to your request budget.
- Do not generate a new idempotency key after an uncertain outcome.

## LLM wrapper warnings

LLM wrappers preserve successful provider responses when Nozle tracking fails. They emit `NozleTrackingWarning` instead of replacing the provider result.

The warning text names only the exception type, not the cause, for example `Nozle tracking failed after a successful LLM response (NozleAPIError)`. Under `python -W error`, the SDK swallows the warning instead of raising it.

```python
import warnings
from nozle import NozleTrackingWarning


warnings.simplefilter("always", NozleTrackingWarning)
```

Use manual queued tracking when telemetry delivery must be durable.
