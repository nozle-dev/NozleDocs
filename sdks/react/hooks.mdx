The current React SDK exports two data hooks: `usePlans` and `useCheckoutSession`. Customer-specific hooks such as `useCan`, `useUsage`, and `usePlan` are intentionally not browser exports; retrieve that state from your authenticated backend.

For customer subscription self-service, use the [billing portal action adapters](/sdks/react/billing-portal). They provide scoped load, preview, apply and recovery callbacks; there is no new generic customer-data hook.

## `usePlans`

Fetches `GET /api/v1/plans` through the `BillingProvider` catalog client.

Each `usePlans` call makes its own request; there is no shared cache, so two components that call it make two requests. The hook refetches when `publishableKey` or `baseUrl` changes. While it refetches, `plans` is `[]` and `isLoading` is `true`. `usePlans` does not fetch during server rendering; it renders the initial loading state.

```tsx
import { usePlans } from '@nozle-js/react'

function PlanList() {
  const { plans, isLoading, error } = usePlans()

  if (isLoading) return <p>Loading plans…</p>
  if (error) return <p role="alert">Plans could not be loaded: {error.message}</p>

  return plans.map((plan) => (
    <div key={plan.code}>
      {plan.name}: {plan.amount_currency} {plan.amount_cents / 100}
    </div>
  ))
}
```

### Return value

| Field | Type | Description |
|---|---|---|
| `plans` | `CatalogPlan[]` | Plans returned by the Nozle catalog. |
| `isLoading` | `boolean` | `true` until the catalog request settles. |
| `error` | `Error \| null` | Set when the request fails: `HTTP <status>` (for example `HTTP 500`) or the thrown message, such as `Failed to fetch`. `plans` is `[]`. |

`CatalogPlan` contains `code`, `name`, `amount_cents`, `amount_currency`, and `interval`.

## `useCheckoutSession`

Calls `BillingProvider.createCheckout` with a plan code and return URL.

```tsx
import { useCheckoutSession } from '@nozle-js/react'

function BuyProButton() {
  const { fetchClientSecret, checkout, isLoading, error } = useCheckoutSession()

  async function startCheckout() {
    const clientSecret = await fetchClientSecret(
      'pro',
      'https://app.example.com/settings/billing',
    )

    if (clientSecret) {
      // Render <Checkout clientSecret={clientSecret} ... />
    }
  }

  return (
    <>
      <button disabled={isLoading} onClick={() => void startCheckout()}>
        {isLoading ? 'Starting…' : 'Choose Pro'}
      </button>
      {error && <p role="alert">{error.message}</p>}
      {checkout && 'type' in checkout && checkout.type === 'scheduled' && (
        <p>Your change is scheduled.</p>
      )}
    </>
  )
}
```

`fetchClientSecret` passes only `planCode` and `returnUrl` to `createCheckout`. It sends no idempotency key; use `CheckoutButton` when you need one.

The hook returns a string only for a Stripe client secret. For a `hosted` result (or a result with a `url`), it navigates to the URL and returns `null`. For `completed`, `scheduled`, `razorpay`, and `processing` results it returns `null` without opening Razorpay or polling; read the result from `checkout` and handle it yourself, for example with `Checkout`'s `checkout` prop. Any other result throws `Checkout response did not include a supported result type`.

### Return value

| Field | Type | Description |
|---|---|---|
| `fetchClientSecret` | `(planCode, returnUrl?) => Promise<string \| null>` | Starts checkout and returns an embedded Stripe secret when present. |
| `checkout` | `CheckoutResult \| null` | Most recent raw checkout result. |
| `isLoading` | `boolean` | Whether checkout creation is in progress. |
| `error` | `Error \| null` | Most recent checkout error. |

## `useBillingContext`

Returns the required billing context and throws outside `BillingProvider`.

```tsx
const { client, createCheckout, verifyCheckout, getCheckoutStatus } = useBillingContext()
```

Use this only when building a custom catalog or checkout component. Prefer `usePlans` and `useCheckoutSession` for common flows.

## `useOptionalBillingContext`

Returns the billing context or `null` outside a provider. `PricingTable` uses this behavior so caller-supplied plans can render without a catalog provider.

## `useNozleClient`

Returns the browser-safe `NozleClient`:

```ts
interface NozleClient {
  publishableKey: string
  baseUrl: string
  catalogFetch(path: string, init?: RequestInit): Promise<Response>
}
```

`catalogFetch` is for public catalog endpoints only. Do not use it to proxy customer billing requests.

## `BillingContext`

`BillingContext` is exported for advanced integrations that need React's direct context API. Its value is either `null` or:

```ts
interface BillingContextValue {
  client: NozleClient
  createCheckout?: CreateCheckout
  verifyCheckout?: VerifyCheckout
  getCheckoutStatus?: GetCheckoutStatus
}
```

Prefer `useBillingContext` or `useOptionalBillingContext` in application components so missing-provider behavior stays explicit.

## Checkout result types

`createCheckout` returns the result your merchant backend received from Nozle. It may be:

| Result | Shape | Component behavior |
|---|---|---|
| Stripe | `{ type: 'stripe', client_secret }` (also `clientSecret`) | `CheckoutButton` passes it to `onStripeClientSecret`. |
| Razorpay | `{ type: 'razorpay', checkout_id, key_id, order_id, amount_cents, currency }` | Loads `https://checkout.razorpay.com/v1/checkout.js`, calls `verifyCheckout`, then polls `getCheckoutStatus`. |
| Hosted | `{ type: 'hosted', payment_url }` | Redirects with `location.assign`. The URL must use HTTPS. |
| Processing | `{ type: 'processing', checkout_id, status }` | Polls `getCheckoutStatus`, which is required. |
| Completed | `{ type: 'completed', ... }` | Calls `onComplete`. |
| Scheduled | `{ type: 'scheduled', ... }` | Calls `onScheduled`. |

Razorpay fields are snake case. A `{ type: 'razorpay', orderId }` result fails: `useCheckoutSession` returns `null`, and `CheckoutButton` shows `Razorpay checkout requires server-issued checkout_id, key_id and order_id`.

Polling calls `getCheckoutStatus` up to 30 times, one second apart, until both `status` and `fulfillment_status` are `succeeded`.

| Error | Cause |
|---|---|
| `Checkout URL must use HTTPS` | A `hosted` `payment_url` (or `url`) is not HTTPS. |
| `Checkout response did not include a supported result type` | `useCheckoutSession` received an unknown result. |
| `onStripeClientSecret is required for embedded Stripe checkout` | `CheckoutButton` received a Stripe client secret without the callback. |

The components also accept `{ type: 'stripe', url }` and a legacy `{ url }`, and redirect to them.

Stripe webhooks remain authoritative. A browser redirect or completion callback does not activate a paid plan by itself.
