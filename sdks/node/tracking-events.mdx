title: "Tracking events"
description: "Send idempotent metered events and control subscription attribution with nozle.track()."
---

`nozle.track()` sends one event to `baseUrl/api/v1/events` (default `https://api.nozle.app/engine/api/v1/events`).

```ts
await nozle.track(
  'workspace_123',
  'api_calls',
  { model: 'example-model', tokens: 1_500 },
  {
    subscriptionId: 'workspace_123_subscription',
    transactionId: 'request_0183f',
    timestamp: '2026-08-04T10:30:00Z',
  },
)
```

## Signature

```ts
track(
  customerId: string,
  event: string,
  metadata?: Record<string, unknown>,
  options?: {
    subscriptionId?: string
    transactionId?: string
    timestamp?: string
  },
): Promise<string>
```

`track()` returns the `transactionId` that was sent. Keep it: it is the `parentTransactionId` for a Cost Event and the value to reuse on a retry.

| Argument | Description |
|---|---|
| `customerId` | External Nozle customer ID. |
| `event` | Event code matching the Feature code. |
| `metadata` | Properties used by metric aggregation or cost attribution. |
| `subscriptionId` | Explicit external subscription target. |
| `transactionId` | Stable event ID used for idempotency. When omitted, the SDK generates a UUIDv7 and returns it. |
| `timestamp` | Optional event time. Use an RFC 3339 string with `Z` or an offset, or Unix seconds as a numeric string. Omit it and the server uses the time it received the event. |

## Subscription resolution

When `subscriptionId` is omitted, the SDK queries `eventsUrl/api/v1/subscriptions` for active subscriptions belonging to the customer:

- exactly one active subscription: its external ID is cached and used;
- no active subscriptions: `track()` rejects with a `NozleApiError` with `status` 422 and `code` `active_subscription_not_found` (message `No active subscription for customer '<id>'`);
- multiple active subscriptions: `track()` rejects with a `NozleApiError` with `status` 422 and `code` `active_subscription_ambiguous` (message `Customer '<id>' has <n> active subscriptions — pass subscriptionId explicitly`).

These are the codes the Engine uses for the same cases. Before `0.17.0` the rejection was a plain `Error`.

Pass `subscriptionId` explicitly for customers with multiple active subscriptions and for latency-sensitive event paths that should avoid the initial lookup.

<Warning>
The cache lasts for the life of the `Nozle` instance. From `0.10.0` the entry is dropped after `subscribe()`, `cancelSubscription()`, `applySubscriptionTransition()`, `checkout()`, a scoped `checkoutStatus()` or `verifyCheckout()`, and `checkoutInvoice()` clears every entry, so the next `track()` looks the subscription up again. Earlier versions never refreshed it. A change made outside this instance, or a `track()` between a paid `checkout()` and its payment, can still use the old subscription ID, and the Events API accepts it. Pass `subscriptionId` in those cases, or call `checkoutStatus()` with a scope after payment.
</Warning>

`subscribe` to a second plan adds a subscription; it does not replace the first. To move a customer to another plan, change or cancel the old subscription, then pass the new subscription ID to `track()`.

## Timestamp format

`timestamp` accepts an RFC 3339 string with `Z` or an offset, such as `2026-08-04T10:30:00Z`, or Unix seconds as a numeric string. A date only (`2026-08-04`) or a time without an offset (`2026-08-04T10:30:00`) throws `track timestamp must be RFC3339 or Unix seconds` before any request is sent. The SDK sends the value as Unix seconds with three decimals.

## Idempotency

Generate a deterministic transaction ID and capture the event timestamp from the business operation whenever possible. Retry the same logical event with both values unchanged. See [errors and retries](/sdks/node/errors).

```ts
const transactionId = `generation:${generationId}:completed`
const timestamp = generationCompletedAt.toISOString()

await nozle.track(customerId, 'text_generation', {
  input_tokens: usage.inputTokens,
  output_tokens: usage.outputTokens,
}, { subscriptionId, transactionId, timestamp })
```

### Safe retries

A timeout, a network error or a `5xx` can arrive after Nozle recorded the event. Nozle records an event once per `transaction_id`, so a retry with the same ID, the same event and the same `timestamp` does not bill it twice. A new ID is a new event. Without a `timestamp`, each attempt is stamped with its own arrival time, so pass one and keep it.

From `@nozle-js/node` 0.13.2, the error `track()` throws carries the ID it sent as `error.transactionId` (typed on `NozleApiError`), also when the SDK generated it. Earlier versions lose a generated ID when the call throws, so pass your own `transactionId` there.

```ts
const timestamp = new Date().toISOString()
try {
  await nozle.track(customerId, 'api_call', { tokens: 100 }, { subscriptionId, timestamp })
} catch (error) {
  const transactionId = (error as { transactionId?: string }).transactionId
  await nozle.track(customerId, 'api_call', { tokens: 100 }, { subscriptionId, transactionId, timestamp })
}
```

## Batching events

From `@nozle-js/node` 0.26.0, `trackBatch()` sends many events through Engine's `/events/batch`. It splits them into gzipped requests of up to 5000 events, sends several at once and returns one result per event. It needs Engine 2.28.0, which accepts gzip and 5000 events per request.

```ts
const result = await nozle.trackBatch([
  { customerId: 'workspace_123', event: 'api_calls', metadata: { tokens: 100 } },
  { customerId: 'workspace_456', event: 'api_calls', timestamp: '2026-10-29T09:30:00Z' },
], { chunkSize: 5000, concurrency: 4 })

for (const r of result.results) {
  if (r.status === 'rejected') console.warn(r.index, r.errors) // { code: ['value_is_mandatory'] }
  if (r.status === 'failed') console.error(r.index, r.transactionId, r.error) // resend with this transactionId
}
```

- **Events.** Each event is `{ customerId, event, subscriptionId?, metadata?, transactionId?, timestamp? }`, the arguments of `track()`.
- **Size.** `chunkSize` is 1 to 5000 (default 5000) events per request, and `concurrency` is 1 to 64 (default 4) requests in flight. An Engine with a lower limit answers `too_many_events`; the SDK then splits that request in half and resends each half.
- **Result.** `{ total, accepted, rejected, failed, results }`. `results[i]` belongs to `events[i]`: `accepted` (stored), `rejected` (Engine refused this event; `errors` maps a field to codes, and resending it unchanged fails again) or `failed` (its request failed, so the event may or may not be stored; `error` says why). `trackBatch()` throws only for invalid arguments.
- **Partial batches.** Engine stores the valid events of a request and names the refused ones by position. An Engine before 2.28.0 refuses a whole request for one invalid event; the SDK then rejects the named events and resends the rest.
- **Idempotency.** Every event has a `transactionId`, yours or a generated one returned in `results[i].transactionId`. A request retried after a network error, a timeout, a `429` or a `5xx` records each event once. IDs must be unique in one call.

`trackBatch()` records events like `track()`; it does not deduct credits. To batch events as they happen, use an [event buffer](#event-buffer).

## Event buffer

From `@nozle-js/node` 0.30.0, `createEventBuffer()` queues events in memory and sends them through `trackBatch()` in the background. Recording an event never waits for the network.

```ts
const buffer = nozle.createEventBuffer({
  // maxBatchSize: 500, flushIntervalMs: 5000, maxQueueSize: 10_000, maxAttempts: 3
  onError: (error, events) => console.error(error.code, error.message, events.map((e) => e.transactionId)),
})

const transactionId = buffer.track({ customerId: 'workspace_123', event: 'api_calls', metadata: { tokens: 100 } })

// At shutdown, or at the end of a serverless handler:
await buffer.close()
```

| Option | Default | Description |
|---|---|---|
| `maxBatchSize` | `500` | 1 to 5000. A flush starts as soon as this many events are waiting. It is also the size of each request. |
| `flushIntervalMs` | `5000` | Flushes whatever is waiting this often. `0` turns the timer off. |
| `maxQueueSize` | `10000` | Most events held at once, waiting or in a request. |
| `maxAttempts` | `3` | Flushes an event may fail in before it is dropped and reported as `failed`. |
| `onError` | warning | `onError(error, events)` receives every event that leaves the buffer unsent. |

An option out of range throws `NozleValidationError` from `createEventBuffer()`.

- **`track(event)`** takes a `trackBatch()` event and returns its `transactionId` at once, without a request: yours, or a generated UUIDv7. Every resend of the event carries that ID, so Engine records it once. It throws `NozleValidationError` only for an invalid event (a missing `customerId` or `event`, or a bad `timestamp`).
- **When it sends.** A flush starts when `maxBatchSize` events are waiting, every `flushIntervalMs`, and on the process's `beforeExit`. The timer never keeps the process alive. Only one flush runs at a time; a trigger during a flush waits for it.
- **`await buffer.flush()`** sends every event waiting now and resolves when done. It never rejects. A failed event stays queued for the next flush.
- **`await buffer.close()`** stops the timer, removes the `beforeExit` hook, sends everything and refuses later events. It keeps flushing until the queue is empty, so a failed event is retried up to `maxAttempts` and then reported.
- **`buffer.size`** is the number of events waiting, not counting a request in flight.
- **Bounded memory.** When `maxQueueSize` events are held, `track()` drops the new event and reports it as `buffer_full`. It does not throw.
- **Backoff.** After a flush in which any event failed, the size, timer and `beforeExit` flushes pause for 1 second. The pause doubles after each further flush with failures, up to 60 seconds. A flush without failures ends it. Events keep queueing meanwhile, up to `maxQueueSize`, so a short outage does not use up `maxAttempts`. An explicit `flush()` or `close()` does not wait for the pause.

### Errors

No event leaves the buffer silently. `onError` gets an `EventBufferError` with a `code`:

| `code` | Meaning |
|---|---|
| `buffer_full` | The queue held `maxQueueSize` events. The new event was dropped. |
| `rejected` | Engine refused the event. `error.errors` maps a field to codes, for example `{ code: ['value_is_mandatory'] }`. It is not retried. |
| `failed` | Its requests failed in `maxAttempts` flushes, after the retries of each `trackBatch()` request. Until then a failed event goes back to the front of the queue with the same `transactionId`. `error.cause` is the last error. |
| `closed` | `track()` was called after `close()`. The event was dropped. |

Without `onError`, each one is emitted as a `NozleTrackingWarning` process warning (`console.warn` on runtimes without process warnings). `onError` must not throw; if it does, the buffer emits the warning instead.

### Exit and serverless

On AWS Lambda, Vercel, Cloudflare and similar platforms, the process may be frozen or ended as soon as the handler returns. Neither the timer nor `beforeExit` runs then. Always `await buffer.flush()` (buffer kept between invocations) or `await buffer.close()` (buffer per invocation) before you return, or the waiting events are lost.

Only `close()` retries a failed event to `maxAttempts` and reports it. Short-lived processes and scripts should end with `await buffer.close()`.

The queue lives in memory only. Events still waiting are lost when the process is killed (for example `SIGKILL`) or calls `process.exit()`, which skips `beforeExit`. During a backoff, `beforeExit` only sets a timer that does not keep the process alive. A process whose Nozle endpoint stays unreachable therefore still exits, and its waiting events are lost without a report unless it called `close()`.

`wrapOpenAI`, `wrapAnthropic` and `captureFetch` do not use the buffer yet. They still send one request per call.

## Operational guidance

- Await `track()` when the request must know whether ingestion succeeded.
- For high-volume workloads, publish through your own durable queue and call `trackBatch()` from a worker. An [event buffer](#event-buffer) batches events in the same process, but holds them in memory only.
- Do not create a new random transaction ID on each retry.
- Do not regenerate the timestamp when retrying an accepted business event.
- Match property names to the Feature aggregation configuration exactly.
- Use `usage.track()` instead when the operation must atomically enforce and deduct product credits.
