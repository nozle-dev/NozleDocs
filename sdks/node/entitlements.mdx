```ts
import { Nozle } from '@nozle-js/node'

const nozle = new Nozle() // reads NOZLE_SECRET_KEY

const check = await nozle.can('workspace_123', 'api_calls')

if (!check.allowed) {
  throw new Error(check.reason ?? 'Feature unavailable')
}
```

`can()` calls `GET /api/v1/can` with the customer, feature, and optional metadata. Metadata is input to the cost and margin estimate only (Cost Sheet conditions and quantities). It does not filter usage: `used`, `limit` and `remaining` always cover all of the feature's usage, whatever `model` or other properties you send.

## Signature

```ts
import type { CanOptions, CanResult } from '@nozle-js/node'

can(
  customerId: string,
  feature: string,
  metadata?: Record<string, string>,
  options?: CanOptions,
): Promise<CanResult>
```

```ts
const check = await nozle.can('workspace_123', 'model_access', {
  model: 'example-large-model',
  region: 'us-east',
})
```

## Choose the subscription

A customer with several active subscriptions needs a selector, as in `@nozle-js/node` 0.17.0 and later. `options` takes `subscriptionId` (the external ID of the subscription) or `entityId` (the external ID of the Entity whose subscription is checked):

```ts
const check = await nozle.can('workspace_123', 'seats', undefined, { subscriptionId: 'sub_team_a' })
const entityCheck = await nozle.can('workspace_123', 'seats', undefined, { entityId: 'entity_42' })
```

Without a selector, `can()` evaluates the customer's only subscription. When the customer has several and not exactly one is its own, the answer is not an error: `can()` returns `allowed: false` with `reason: 'subscription_required'`. Send `subscriptionId` or `entityId` to choose. See [The can() endpoint](/guides/entitlements/can-endpoint#which-subscription-is-checked).

## `CanResult`

| Field | Type | Description |
|---|---|---|
| `allowed` | `boolean` | Whether the request may proceed. |
| `feature_type` | `string?` | Type of the feature. |
| `reason` | `string?` | Denial or decision reason. Present only when it applies. |
| `used` | `number` | Current measured usage. |
| `limit` | `number \| null` | Configured usage limit. `null` when the feature has no limit. |
| `remaining` | `number \| null` | Remaining allowance. `null` when the feature has no limit. |
| `overage` | `boolean?` | `true` when usage has reached a soft limit; the usage is billed as overage. Never a denial by itself. Present only when it applies. |
| `policy` | `CanPolicy?` | The margin policy version that decided the call, with its `decision` and `reason`. Present only when a policy covers the feature. See [Margin policy](#margin-policy). |
| `configuration` | `Record<string, string>?` | Feature configuration. Present only when configured. |
| `economics` | `object?` | Point-in-time Cost Sheet estimate with exact decimal strings, Cost Rule version identifiers, and explicit exclusions. |
| `budget` | `Budget?` | 0.30.0, Engine 2.34.0. The spend limit that refused the call (`reason: 'budget_exceeded'`), else the tightest one covering the feature. See [Spend limits](#spend-limits). |

`economics` contains:

| Field | Description |
|---|---|
| `status` | Estimate status, for example `not_configured`. |
| `estimated_incremental_revenue` | Estimated incremental revenue. |
| `includes` | What the estimate includes. |
| `excludes` | What the estimate excludes. |
| `reason` | Why the estimate has its status, for example `missing_cost_composition`. |
| `calculated_at` | When the estimate was calculated. |

## Margin policy

When a [margin policy](/guides/margin/overview) covers the feature, `can()` returns `policy`, the policy version that decided the call. `CanResult.policy` is typed as `CanPolicy`.

| Field | Meaning |
|---|---|
| `mode` | What the policy does when the call is below its thresholds: `allow`, `warn` or `deny`. |
| `on_unavailable` | What it does when the economics cannot be estimated: `allow`, `warn` or `deny`. |
| `minimum_margin_amount`, `minimum_margin_percent`, `maximum_estimated_cost` | The thresholds of the policy; each is present only when set. |
| `maximum_snapshot_age_seconds` | An estimate older than this is `stale` and follows `on_unavailable`. |
| `decision` | `allow`, `warn` or `deny`: what the policy decided for this call. |
| `reason` | Why: `within_policy`, `minimum_margin_percentage_not_met`, `minimum_margin_amount_not_met`, `maximum_estimated_cost_exceeded`, `economics_not_configured`, `economics_unavailable`, `economics_stale`, `reporting_currency_mismatch` or `margin_percentage_unavailable_for_zero_revenue`. |

A `deny` is a refusal: `allowed` is `false` and `reason` is `economic_policy_denied`. A `warn` is **not** a refusal: `allowed` stays `true`, so read the policy `decision` to see it. The call never reaches the provider on a refusal, so deny before protected work and log or alert on a warning.

A feature with no Cost Rule has `economics.status` `not_configured`, and the policy applies `on_unavailable` to it. An organization-wide policy with `on_unavailable: deny` therefore also refuses features that have no costs at all; scope such a policy to the features that have Cost Rules, or use `allow` or `warn`.

The estimate behind the decision is in `economics`: `estimated_incremental_cost`, `estimated_incremental_revenue`, `estimated_incremental_margin` and `estimated_margin_percent`, exact decimal strings. For a feature priced $0.10 per call with a $0.08 cost rule, the margin is `0.02` (20%), so a policy with a 50% minimum refuses it with `minimum_margin_percentage_not_met`.

```ts
import { RefusalReason } from '@nozle-js/node'

const check = await nozle.can('workspace_123', 'llm_tokens')
if (!check.allowed && check.reason === RefusalReason.EconomicPolicyDenied) {
  // check.policy.reason, for example 'minimum_margin_percentage_not_met';
  // check.economics.estimated_margin_percent is the margin that failed the policy
} else if (check.policy?.decision === 'warn') {
  // allowed, but flagged: log it or alert
}
```

## Spend limits

Available from `@nozle-js/node` 0.30.0 with Engine 2.34.0. When a hard [spend limit](/guides/entitlements/spend-limits) covering the feature is used up, `can()` returns `allowed: false` with `reason: 'budget_exceeded'` and the limit in `budget`. It does not throw. Compare `reason` with the exported `RefusalReason` values, never with message text:

```ts
import { RefusalReason } from '@nozle-js/node'

const check = await nozle.can('workspace_123', 'llm_tokens')
if (!check.allowed && check.reason === RefusalReason.BudgetExceeded) {
  const { limit, spent, currency, period_end } = check.budget!
  // "You reached your $500 limit; it resets on period_end."
}
```

`RefusalReason` has `FeatureNotFound`, `NoSubscription`, `SubscriptionRequired`, `NoEntitlement`, `UsageLimitExceeded`, `EconomicPolicyDenied`, `CustomerPaymentOverdue`, `InsufficientCredits` and `BudgetExceeded`. `reason` is typed `RefusalReason | string`, so a reason a newer Engine adds still arrives as its string.

`usage.check()` and `usage.track()` answer the same way, with `budget` on `UsageCheckResult` and `UsageTrackResult`. A soft limit never refuses.

### Read budgets

```ts
const { subscription_id, budgets } = await nozle.budgets.list('workspace_123', { subscriptionId: 'sub_pro_123' })
for (const budget of budgets) {
  console.log(budget.feature_code ?? 'total', budget.spent, '/', budget.limit, budget.currency, budget.status)
}
```

`budgets.list(customerId, { subscriptionId })` calls [`GET /customers/{customer_id}/budgets`](/api/list-customer-budgets) and returns `BudgetList`: `customer_id`, `subscription_id` and `budgets`. Each `Budget` has `feature_code` (`null` for the total limit), `limit`, `spent`, `held`, `remaining` (decimal strings in major units), `currency`, `period`, `period_start`, `period_end`, `mode`, `status` (`ok`, `warning`, `exceeded`), `as_of` and `counted_from` (0.31.0, Engine 2.38.0: when counting began). Types: `Budget`, `BudgetList`, `BudgetListOptions`.

For an exact cap under concurrent calls, take a [budget hold](/sdks/node/credits#budget-holds) instead of a plain `can()`.

## HTTP handler pattern

```ts
const check = await nozle.can(customerId, 'analytics')

if (!check.allowed) {
  return Response.json(
    {
      error: check.reason ?? 'upgrade_required',
      used: check.used,
      limit: check.limit,
      remaining: check.remaining,
    },
    { status: 403 },
  )
}

if (check.overage) {
  // Allowed: a soft limit is reached, so this usage is billed as overage.
  warnAboutOverage(customerId, check)
}

return runAnalyticsQuery()
```

Deny only when `allowed` is `false`. `overage: true` never denies by itself: a soft limit is reached and the usage is billed as overage.

## Authorization guidance

Perform entitlement checks on the trusted backend immediately before protected work. A React `FeatureGate` improves the interface but is not an authorization boundary.

`can()` checks entitlement and usage state; it does not reserve product credits. Use `usage.track()` for atomic credit-backed consumption.
