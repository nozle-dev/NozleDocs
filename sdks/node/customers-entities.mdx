Customers represent the merchant's billable account or workspace. Entities represent children of that customer, such as users, agents, projects, or environments.

## Upsert a customer

`customers.upsert()` sends the merchant's secret key directly to Nozle Core.
Core derives the owning organization from that key; the SDK never provisions a
customer through a global or master organization.

```ts
const customer = await nozle.customers.upsert({
  externalId: 'workspace_123',
  name: 'Acme Workspace',
  email: 'billing@example.com',
})
```

| Field | Type | Required | Description |
|---|---|---|---|
| `externalId` | `string` | yes | Stable application-owned customer identifier. |
| `name` | `string` | no | Display name. |
| `email` | `string` | no | Billing or contact email. |
| `billingConfiguration` | `CustomerBillingConfiguration` | no | Payment provider assignment. Requires Node.js `0.12.0`. |

### Link a customer that already exists in Stripe

Pass `billingConfiguration` with the Stripe customer ID to link it in the same call. Nozle stores the link and does not create a new Stripe customer. Sending the same upsert again is safe.

```ts
await nozle.customers.upsert({
  externalId: 'workspace_123',
  name: 'Acme Workspace',
  billingConfiguration: {
    paymentProvider: 'stripe',
    paymentProviderCode: 'stripe_main',
    providerCustomerId: 'cus_ABC123',
  },
})
```

| Field | Type | Required | Description |
|---|---|---|---|
| `paymentProvider` | `string` | yes | Provider type, such as `stripe`. |
| `paymentProviderCode` | `string` | no | Code of the provider connection in Nozle. |
| `providerCustomerId` | `string` | no | Existing customer ID at the provider, such as `cus_…`. |
| `syncWithProvider` | `boolean` | no | Create the customer at the provider when no `providerCustomerId` is given. |
| `providerPaymentMethods` | `string[]` | no | Payment methods the customer may use. Defaults to `card`. |

Nozle keeps the assignment with or without `syncWithProvider`, and checkout charges only through the assigned connection. See [Assign the connection to customers](/integrations/stripe#assign-the-connection-to-customers).

## Tax IDs and VAT checks

Available from Node.js `0.35.0`, which ships after Core 11.31.0. `customers.upsert` takes the address and the tax ID. Core checks the format and, for an EU VAT number on a billing entity with EU tax management, starts a VIES check.

```ts
const customer = await nozle.customers.upsert({
  externalId: 'workspace_123',
  customerType: 'company',
  legalName: 'Acme GmbH',
  address: { line1: 'Main St 1', city: 'Berlin', postalCode: '10115', country: 'DE' },
  taxId: { type: 'eu_vat', value: 'DE811128135' },
})

console.log(customer.tax_identification_status) // 'pending' while VIES runs
console.log(customer.tax_treatment)
console.log(customer.tax_identification_warnings) // for example ['country_mismatch']
```

| Field | Type | Description |
|---|---|---|
| `customerType` | `'company' \| 'individual'` | Customer type. |
| `legalName` | `string` | Legal name for invoices. |
| `address`, `shippingAddress` | `{ line1, line2, city, state, postalCode, country }` | The SDK sends Core's flat keys (`address_line1`, `zipcode`). |
| `taxId` | `{ type, value } \| null` | `null` clears the stored tax ID. Core validates the format. The SDK only refuses a `taxId` without type or value. |

Read the result with `customers.get(externalId)`. Before a checkout, wait until the check ends:

```ts
const ready = await nozle.customers.waitForTaxCheck('workspace_123') // { timeoutMs } defaults to 10000
console.log(ready.tax_identification_status) // 'valid', 'invalid' or 'unverified'
```

`waitForTaxCheck` polls `customers.get` until the status is not `pending`, and throws after `timeoutMs`. A checkout call fails with `customer_tax_location_required` (422) or `customer_tax_check_pending` (409, `error.retryAfterSeconds`). From Core 11.54.0 the checkout answers a `hosted` result whose URL is Nozle's [billing details step](/guides/billing/tax-ids#billing-details-step) instead of the 422: redirect the customer to it as for any hosted checkout. The 409 then only holds a paid plan change, an invoice checkout and a number without a type that is not well formed. See [Tax IDs, reverse charge and VAT checks](/guides/billing/tax-ids).

## Erase or delete a customer

Available from Node.js `0.43.0`, with Core 11.52.0. Both need a secret key and return the customer.

```ts
import { CustomerEraseErrorCode, NozleApiError } from '@nozle-js/node'

try {
  const erased = await nozle.customers.erase('workspace_123')
  console.log(erased.erased_at) // set; the erasure finishes in the background
} catch (error) {
  if (error instanceof NozleApiError && error.hasCode(CustomerEraseErrorCode.HasUnpaidInvoices)) {
    // settle or void the unpaid invoices first
  }
}
```

- `customers.erase(externalId)` calls `POST /customers/{external_id}/erase`. It erases the customer's personal data, irreversibly. A `422` lists `has_active_subscriptions`, `has_draft_invoices` or `has_unpaid_invoices` in `errorDetails.customer` (`CustomerEraseErrorCode`). Erasing an erased customer changes nothing.
- `customers.delete(externalId)` calls `DELETE /customers/{external_id}`. It deletes the customer and ends its subscriptions, and keeps its personal data.
- Erase is not delete. To remove personal data, for example under GDPR, call `erase`.
- Neither is retried automatically.

See [Erase a customer](/api/create-customer#erase-a-customer) for what is erased and what is kept.

## Customer tokens for the browser

Available from Node.js `0.44.0`, with Core 11.66.0. A [customer token](/api/authentication#customer-tokens) lets the signed-in customer's browser read that customer's entitlements, usage, credit balances and subscription with your publishable key. Mint it with a secret key, for the customer of your session:

```ts
const { token, customer_id, expires_at } = await nozle.customerTokens.create('workspace_123', {
  ttlSeconds: 900, // 60 to 86400; Nozle's default is 3600
  features: ['seats'], // optional: /can and usage reads limited to these features
})
```

Return the result to the browser, for example to `@nozle-js/react` `getCustomerToken` ([Provider and hooks](/sdks/react/hooks#read-from-nozle-with-a-customer-token)). Never take the customer from the request. After a leak, `await nozle.customerTokens.revoke()` refuses every token minted until now. Both need a secret key: `create` needs `customer:read`, `revoke` needs `customer:write`.

## Read Entities

```ts
const entity = await nozle.entities.get('workspace_123', 'user_42')

const page = await nozle.entities.list('workspace_123', {
  status: 'active',
  limit: 50,
})

const nextPage = page.next_cursor
  ? await nozle.entities.list('workspace_123', {
      status: 'active',
      limit: 50,
      cursor: page.next_cursor,
    })
  : null
```

`status` accepts `active` or `suspended`; Entities cannot be deleted. `limit` must be an integer from 1 to 100.

## Upsert an Entity

```ts
const result = await nozle.entities.upsert(
  'workspace_123',
  'user_42',
  {
    name: 'Asha',
    status: 'active',
    metadata: { role: 'agent' },
  },
  { idempotencyKey: 'entity-user-42-v1' },
)

console.log(result.action)
console.log(result.replayed)
```

Entity IDs and idempotency keys are limited to 255 UTF-8 bytes. Retry an uncertain mutation with the same key and payload.

## Activate or suspend

```ts
await nozle.entities.suspend('workspace_123', 'user_42', {
  idempotencyKey: 'suspend-user-42-v1',
})

await nozle.entities.activate('workspace_123', 'user_42', {
  idempotencyKey: 'activate-user-42-v2',
})
```

These helpers first fetch the Entity, then preserve its current `name` and `metadata` while changing `status`.

## Bulk upsert

```ts
const result = await nozle.entities.bulkUpsert(
  'workspace_123',
  [
    { externalId: 'user_42', name: 'Asha', status: 'active' },
    { externalId: 'user_43', name: 'Ravi', status: 'suspended' },
  ],
  { idempotencyKey: 'workspace-123-users-import-7' },
)

console.log(result.counts)
```

Each bulk request must contain 1–500 unique Entity external IDs.

## Seat billing is explicit

Entity lifecycle methods do not emit billable seat events. If seats are billed through a Feature, track add/remove operations separately with stable transaction IDs through `nozle.track()`.

```ts
await nozle.track(
  'workspace_123',
  'billable_seats',
  { user_id: 'user_42', operation: 'add' },
  {
    subscriptionId: 'workspace_123_subscription',
    transactionId: 'seat-add-user-42-v1',
  },
)
```

## Entity credits

Use Entity IDs with `nozle.credits` and `nozle.usage` for per-Entity balances, transfers, attribution, and pool policy. See [Product credits](/sdks/node/credits).
