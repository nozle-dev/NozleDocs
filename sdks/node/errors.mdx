---
title: "Errors and retries"
description: "Read failed requests with NozleApiError, branch on status and code, and retry Node SDK calls safely."
---

A request that gets a non-2xx response throws `NozleApiError`. It carries `status`, `code`, `errorDetails`, `requestId`, `retryAfter` and `hasCode()`. Any other failure is a plain `Error`: a network error, a timeout, or a local check that fails before a request is sent.

Before `0.13.0`, only `checkout()`, `checkoutInvoice()`, `verifyCheckout()`, `checkoutStatus()` and the `nozle.margin.*` queries threw it (from 0.10.0). Every other call threw a plain `Error` with the status only in its message.

| Error | Meaning |
|---|---|
| `NozleApiError`, message `<operation> failed: <HTTP status> <status text>` | Nozle returned a non-2xx response, for example `usage.track failed: 409 Conflict`. The operation is the method name; for margin queries it is `margin` followed by the path. |
| Plain `Error` with a descriptive message | Local validation failed before any request, for example a wrong key type, a bad timestamp, or a missing argument. |
| `TypeError`, `AbortError` or `TimeoutError` from `fetch` | The request did not complete: network failure or the `timeout` option. |

## Branch on `NozleApiError`

```ts
import { NozleApiError } from '@nozle-js/node'

try {
  await nozle.checkout('workspace_123', 'pro', 'https://app.example.com/billing')
} catch (error) {
  if (error instanceof NozleApiError) {
    if (error.hasCode('payment_provider_required')) {
      // Assign a payment provider to the customer, then retry.
    } else if (error.status === 422) {
      console.error(error.code, error.errorDetails)
    }
  } else {
    throw error // Local validation error or network failure.
  }
}
```

| Property | Meaning |
|---|---|
| `status` | The HTTP status. |
| `code` | The top-level `code` of the response, for example `payment_provider_required`, `validation_errors` or `invalid_date_range`. Absent when the response had none. |
| `errorDetails` | The raw `error_details` object of a `validation_errors` response, for example `{ base: ['razorpay_requires_inr'] }`. |
| `requestId` | The `X-Request-Id` response header. Core sends it; the Engine does not yet. Quote it when you contact support. |
| `retryAfter` | Seconds to wait, from the `Retry-After` header, when the service sends one. |
| `hasCode(code)` | `true` when `code` equals the value, or the value is listed in `errorDetails`. |

The message keeps the `<operation> failed: <status> <status text>` form, and the class extends `Error`.

## Workspace blocked (`402`)

Your workspace answers HTTP `402` `workspace_suspended` when its Nozle invoices stayed unpaid past the grace of your Nozle plan (7 days by default). `card_required` is only for a workspace still flagged from before Nozle stopped asking for a card at onboarding. See [Workspace billing errors](/api/errors#workspace-billing-errors). Do not retry: the SDK never retries a `402`, and every retry is refused until a member pays the Nozle invoices. Calls work again at once afterwards. Events sent while blocked are refused, not queued.

```ts
try {
  await nozle.can('workspace_123', 'code_completion')
} catch (error) {
  if (error instanceof NozleApiError && error.status === 402) {
    // error.code is 'card_required' or 'workspace_suspended'.
    // Tell your team to fix billing; the check is neither allowed nor denied.
  } else {
    throw error
  }
}
```

## Customer payment overdue

_Unreleased (0.23.0, needs Engine 2.22.0)._ One of your customers whose unpaid invoices are past the grace of their plan is blocked by your [dunning policy](/guides/billing/dunning) with HTTP `402` `customer_payment_overdue`. This is about that customer, not your workspace.

- `can()` does not throw. It returns `{ allowed: false, reason: 'customer_payment_overdue', used: 0, limit: null, remaining: null }`, so you can ask the customer to pay. `createBillingHandler`'s entitlement route, and so React `useEntitlement`, returns the same denial as data.
- `track()`, `usage.check()` and `usage.track()` throw `NozleApiError` with `code` `customer_payment_overdue` (the `CUSTOMER_PAYMENT_OVERDUE` constant). Nothing is tracked.
- `isCustomerPaymentOverdue(error)` is `true` for that `NozleApiError`, and for the LLM proxy's `402` surfaced by a provider SDK that keeps the response body (`status` 402 with `code` or `error.code`). From Engine 2.22.0 the proxy answers in the provider's error shape, so the OpenAI and Anthropic SDKs surface `error.code`; see [LLM proxy errors](/api/llm-proxy#errors). `NozleApiError.message` reads the proxy's nested `error.message` too.
- `/events/batch`: a partial batch is a `200` that stores the other customers' events and lists the refused ones by position in `error_details` (`EventBatchResponse`). `refusedEventIndexes(body.error_details, CUSTOMER_PAYMENT_OVERDUE)` returns those positions in ascending order. When every event is refused the batch answers `402` and stores nothing; `error.refusedEventIndexes(CUSTOMER_PAYMENT_OVERDUE)` lists them on the `NozleApiError`.

```ts
import { CUSTOMER_PAYMENT_OVERDUE, isCustomerPaymentOverdue } from '@nozle-js/node'

const decision = await nozle.can('customer_123', 'api_calls')
if (!decision.allowed && decision.reason === CUSTOMER_PAYMENT_OVERDUE) {
  // Show "pay your invoice" with a link to your billing page.
}

try {
  await nozle.track('customer_123', 'api_calls', { tokens: 100 })
} catch (error) {
  if (!isCustomerPaymentOverdue(error)) throw error
  // The event was refused and is not queued.
}
```

Other `402`s (`workspace_suspended`, `card_required`) still throw from `can()`.

## Branch on the status

`error.status` works on every call. Use `status` to separate a retryable failure from one that is not:

```ts
try {
  await nozle.usage.track(
    {
      customerId: 'workspace_123',
      featureCode: 'agent_execution',
      creditSystemCode: 'ai_credits',
      timestamp,
    },
    { idempotencyKey: 'agent-execution-0183f' },
  )
} catch (error) {
  if (!(error instanceof NozleApiError)) {
    // Local validation error or network failure.
  } else if (error.status === 409) {
    // The key was used with a different request. Do not retry.
  } else if (error.status === 429 || error.status >= 500) {
    // Retry with the same key and request after error.retryAfter seconds, if it is set.
  }
}
```

## Retry behavior

By default the SDK does not retry: every call is one request with a per-attempt timeout (`timeout`, default 10 seconds). Set `maxRetries` to retry network errors, timeouts, `429` and `5xx` with backoff, or after `NozleApiError.retryAfter` seconds when the service sent `Retry-After`:

```ts
import { Nozle } from '@nozle-js/node'

const nozle = new Nozle({ maxRetries: 2, retryDelayMs: 500 })
```

Only requests that are safe to repeat are retried: reads, calls that carry an idempotency key (such as `usage.track`), event, cost event and customer writes, and the read-only usage check and transition preview. `subscribe`, `checkout` and other writes without a key are never retried.

To retry in your own code instead:

- Retry only after a network error, a `429`, or a `5xx`.
- Retry with the same idempotency key and the same request, including the `timestamp`.
- For `track()`, retry the same event with the same `transactionId` and `timestamp`.
- Do not generate a new idempotency key after an uncertain outcome.

## Idempotency

`usage.track()` needs an `idempotencyKey`. A retry with an identical request returns the original result, including a denial, and does not charge again. The same key with a different request returns `409`. If you omit `timestamp`, the SDK fills in the current time once per idempotency key and reuses it for a retry on the same client. Pass a fixed `timestamp` for a retry from another process or after a restart. See [product credits](/sdks/node/credits#atomic-usage-tracking) and [usage tracking](/guides/credits/usage-tracking).
