Nozle collects payments through the payment provider you connect to your organization. Each organization connects its own provider account, so your customers pay into your account, not Nozle's.

Connect a provider in the dashboard under **Settings > Billing settings > Integrations**. Each provider shows **Connect** until it has a connection, then **Add another**, **Edit** and **Disconnect**. Nozle supports Stripe and Razorpay.

| | [Stripe](/integrations/stripe) | [Razorpay](/integrations/razorpay) |
|---|---|---|
| **Credential** | Stripe secret key | Razorpay Key ID and key secret, plus a webhook secret |
| **Currency** | The invoice currency | INR only |
| **Plan checkout** | Stripe-hosted Checkout page (a saved card is charged first) | Razorpay order in the Razorpay checkout modal |
| **Payment links** | Stripe-hosted Checkout page | Razorpay payment link |
| **Webhook** | Nozle registers it right after you connect | You add it in the Razorpay dashboard |
| **Payment confirmation** | Signed webhook only | Signed webhook, and your backend's verify call for an order |
| **Checkout status** | Paid upgrades only, by upgrade ID. It reads the session from Stripe but never settles a payment. A new subscription or invoice checkout has no status call | Every checkout, by checkout ID. It reconciles with Razorpay and settles a captured payment |
| **Renewals** | Automatic charge on the saved card | Automatic only with an auto-pay mandate (UPI, card or bank debit) |
| **Refunds and disputes** | Credit-note refunds and lost disputes | Credit-note refunds and lost disputes |

A customer pays through the provider connection assigned to that customer. A customer without one can pay through the [default payment connection](#default-payment-connection). See [Checkout](/guides/billing/checkout) for the flow that both providers share, and [Payments](/guides/billing/payments) for how payment events update invoices and subscriptions.

## Default payment connection

_Unreleased._ When a customer with no payment connection pays, Nozle uses the workspace's default connection:

- With one connection, that connection is the default.
- With several, choose the default under **Settings > Billing settings > Integrations**, in **Default payment connection**. Until you choose one, there is no default.

The default applies only when the customer starts the payment: [checkout](/guides/billing/checkout), [pay links](/guides/billing/checkout#pay-links), **Pay** in the [customer portal](/guides/billing/invoices#pay-from-the-customer-portal) and credit top-up purchases. Nozle assigns the customer to the default connection at that moment and creates the customer in the provider. Customers with their own connection keep it.

Automatic charges never use the default. A customer without a connection is not charged automatically, so you can bill some customers outside Nozle.

Without a connection for the customer and without a default, checkout answers `422` `payment_provider_required`. Its `message` names the fix: connect a payment provider, choose the default connection, or set the customer's `billing_configuration.payment_provider_code`.

## Connection health

<Note>
Available from Core 11.52.0 and dashboard 2.26.0.
</Note>

A payment connection can stop working without any payment failing at once: a revoked key, a deleted or disabled webhook, or a wrong webhook secret. Payments then never settle. Each connection under **Settings > Billing settings > Integrations** shows its health:

| Status | Meaning |
|---|---|
| **Working** (`healthy`) | The provider accepts the saved key and events arrive. |
| **Needs attention** (`warning`) | Payments may still settle, but something needs a look. |
| **Not working** (`broken`) | Payments cannot settle until you fix the connection. |
| **Not checked** (`unknown`) | The provider could not be reached, or the check does not exist for this provider. |

The connection lists the reasons in plain words, with the time the last event arrived:

| Reason | Status | Cause and fix |
|---|---|---|
| `credentials_rejected` | Not working | The provider refuses the saved key. Edit the connection and enter a valid key. |
| `webhook_not_registered` | Not working | Stripe only. Nozle could not create its webhook endpoint. Fix the cause, then save the connection again: Nozle creates the endpoint in the background. Select **Check now** after a few seconds. See [Stripe webhook setup](/integrations/stripe#webhook-setup). |
| `webhook_missing` | Not working | Stripe only. The endpoint Nozle created was deleted in Stripe. Save the connection again and Nozle creates a new one in the background, then select **Check now**. |
| `webhook_disabled` | Not working | Stripe only. The endpoint is disabled in Stripe. Save the connection again and Nozle turns it back on in the background, then select **Check now**. |
| `signature_rejected` | Not working | An event with a bad signature arrived after the last valid one, so the webhook secret does not match. For Razorpay, make the secret in Razorpay and on the connection the same. |
| `events_failing` | Needs attention | Provider events failed to process in the last 24 hours. They are retried automatically. Open **Show events** to see which. |
| `no_events_yet` | Needs attention | Razorpay only. No validly signed event has arrived yet. See [Razorpay webhook setup](/integrations/razorpay#webhook-setup). |
| `provider_unreachable` | Not checked | The provider did not answer. The check runs again later. |
| `check_not_supported` | Not checked | Nozle has no health check for this provider. |

Nozle asks the provider at most every 5 minutes per connection, and again right after you save the connection. **Check now** asks again at once. Nozle never shows or stores the request body of a rejected event; only the time of the last rejected signature is kept.

**Show events** lists the events the provider sent to the connection in the last 30 days, newest first: the event type, its status, the number of attempts, when it was received and last updated, and the provider's event ID. The payload is never shown.

Through GraphQL, with the `organization:integrations:view` permission:

- `paymentProviderHealth(id:, refresh:)` returns `status`, `reasons`, `failedEventsCount`, `lastEventAt`, `lastRejectedSignatureAt` and `checkedAt`, and for Razorpay `webhookSetupState`. `refresh: true` asks the provider again.
- `paymentProviderEvents(paymentProviderId:, page:, limit:)` lists the events, each with `id`, `eventType`, `status`, `attempts`, `providerEventId`, `createdAt` and `updatedAt`.
