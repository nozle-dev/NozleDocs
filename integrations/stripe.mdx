Nozle uses Stripe to collect payments through a Stripe-hosted Checkout page and automatic charges against a saved payment method. Each Nozle organization connects its own Stripe account, so your customers pay into your Stripe account, not Nozle's. Nozle holds no global Stripe credentials.

## What you need

- A Stripe account and a secret key. A test key starts with `sk_test_` and a live key with `sk_live_`.
- A Nozle public API URL that Stripe can reach.

Checkout is a Stripe-hosted page, so your page needs no Stripe publishable key, no Stripe.js and no Stripe packages. The optional **Publishable key** on the connection (below) is for Nozle's own card page, which is hosted by Nozle: your pages still load nothing from Stripe.

Nozle checks the secret key against Stripe when you connect, and rejects a key Stripe does not accept. It calls Stripe with that key to read the account, create and update customers, create Checkout Sessions and payment intents, create refunds, and create and update webhook endpoints. The key needs access to those resources. The optional customer and invoice import also lists Stripe customers and invoices.

## Setup

Connect Stripe in the Nozle dashboard under **Settings > Billing settings > Integrations**. In the Stripe group choose **Connect**. When a connection already exists, the button reads **Add another**. The form asks for:

| Field | What to enter |
|---|---|
| **Name** | A label for the connection. Enter one: Nozle rejects a blank name, although the form marks it optional |
| **Code** | A stable identifier. It must be unused by every other payment connection in your organization. You use it when you assign this connection to a customer, and it is part of the webhook URL |
| **Secret key** | `sk_test_...` or `sk_live_...`. Stored encrypted and shown masked. It cannot be edited: to use another key, create a new connection |
| **Support 3DSecure** | Optional, off by default. See [Saved payment methods and automatic charging](#saved-payment-methods-and-automatic-charging) |
| **Publishable key** | Optional. `pk_test_...` or `pk_live_...`, in the same mode as the secret key (a mismatch is refused). Find it in the Stripe dashboard under **Developers > API keys**. It is not a secret. With it, cards are saved on a Nozle-hosted card page that can register an e-mandate for cards issued in India. See [Indian cards and automatic payments](#indian-cards-and-automatic-payments) |
| **Mandate maximum** | Optional, for Indian cards only: a headroom multiplier over the plan price (3 by default), and a floor and a ceiling in the smallest unit of the mandate currency (defaults per currency). See [How big the mandate is](#how-big-the-mandate-is) |
| **Upcoming payment email** | Optional (`upcomingDebitEmail` in GraphQL). Whether Nozle emails your customer before an automatic debit. Unset, it is on for payments in INR and off for other currencies. See [Upcoming automatic payments](#upcoming-automatic-payments). The dashboard form has no field for it: set it through GraphQL |

An organization can hold several Stripe connections, but only one per Stripe account and mode. A test key (`sk_test_`) and a live key (`sk_live_`) of the same Stripe account are two connections, so you can go live after testing without disconnecting the test connection. Connecting the same account in the same mode again fails with `500` and the code `stripe_account_already_connected`. The message is only `Internal error`: it does not name the existing connection.

Nozle checks the key with Stripe when you connect. A key Stripe rejects fails with `422 third_party_error` and Stripe's own message, for example `Invalid API Key provided: ...`. An empty secret key fails with `422 validation_errors` and `secret_key: ["value_is_mandatory"]`, without calling Stripe. The dashboard shows only a generic error in these cases, so check the key first when Connect fails.

The connect form has no success redirect URL. After you connect, use **Add redirect URL** on the connection to set one. Nozle sends the customer there after a payment on a hosted Stripe page, which covers credit top-ups and payment links. Without it the customer lands on `https://stripe.com/`. The URL must be valid and at most 1,024 characters. An embedded checkout uses the `return_url` of the checkout request instead.

To edit a connection, change its name, code, **Support 3DSecure**, redirect URL, publishable key and mandate maximum settings. The same fields are on the GraphQL `addStripePaymentProvider` and `updateStripePaymentProvider` mutations as `publishableKey`, `mandateCapMultiplier`, `mandateCapFloorCents`, `mandateCapCeilingCents` and `upcomingDebitEmail`. Changing the code updates the customers assigned to it and updates the webhook endpoint URL in Stripe. Until that update finishes, Stripe events sent to the previous code's URL are still accepted. If the connection had no webhook endpoint, the rename registers one, and if the key may not edit webhook endpoints Nozle sends the `payment_provider.error` webhook.

To disconnect, use **Disconnect**. Customers assigned to the connection lose their assignment. Nozle does not delete the webhook endpoint it created in Stripe, so delete it in Stripe yourself.

### Assign the connection to customers

Checkout charges only through the connection assigned to the customer. Nozle never picks another connection for you. A customer with no assigned connection, or whose connection code matches no Stripe connection, gets `422 payment_provider_required`, and nothing is created in Stripe or Nozle.

To assign a connection yourself, select it in the customer's **Payment provider** setting in the dashboard, which lists connections as name and code. The same section has:

- **Provider customer ID**, for a customer that already exists in Stripe. It is locked once set.
- **Create customer in payment provider**, which makes Nozle create the Stripe customer.
- The payment methods the customer may use on hosted Stripe pages and automatic charges: `card`, `link`, `sepa_debit`, `us_bank_account`, `bacs_debit`, `boleto`, `crypto` and `customer_balance`. `link` needs `card`, and `customer_balance` cannot be combined with another method.

At checkout Nozle creates the missing Stripe customer with the customer's name, email, address and phone, and `card` as the payment method when the customer has no Stripe link yet. Moving a customer to a different Stripe connection at checkout creates a new Stripe customer in that account, so saved payment methods do not carry over.

To assign a connection from code, send `billing_configuration.payment_provider: "stripe"` and `payment_provider_code` when you create or update the customer. Nozle keeps the assignment even without `sync_with_provider`; it then creates the Stripe customer at checkout.

To link a customer that already exists in Stripe from code, pass the Stripe customer ID when you upsert the customer: `billingConfiguration` in [Node.js](/sdks/node/customers-entities#link-a-customer-that-already-exists-in-stripe), `billing_configuration` in [Python](/sdks/python/customers-entities#link-a-customer-that-already-exists-in-stripe), or `BillingConfiguration` in [Go](/sdks/go/customers-entities#link-a-customer-that-already-exists-in-stripe). Nozle stores the link without creating a new Stripe customer, so payment methods already saved in Stripe stay usable. A Stripe customer can be linked to one Nozle customer only: an upsert that links a `cus_…` already linked to another customer answers `422 validation_errors` with `billing_configuration.provider_customer_id: ["value_already_exist"]`, and nothing is saved, so a new customer is not left half-configured.

On a later upsert or update of a linked customer, Nozle sends Stripe only the name, email, phone and address that the request changed. A changed address line sends the whole address, because Stripe replaces the address as a whole. A repeated upsert, an upsert without `billing_configuration`, and an upsert that only links a `cus_…` leave the Stripe customer's email, phone and address as they are, so edits made in Stripe are kept. Nozle never clears a Stripe customer field: a field sent as `null` or blank is cleared on the Nozle customer only.

Credit top-ups and payment links do not assign a customer. The customer must already be assigned and linked to a Stripe customer. See [Credit top-ups](#credit-top-ups).

## What Nozle handles

| Feature | How it works |
|---|---|
| **Checkout** | A Stripe-hosted Checkout page for a Nozle invoice, for a new paid subscription or an existing unpaid invoice. A saved card is charged first |
| **Upgrades** | A paid plan upgrade opens a Stripe-hosted Checkout page. The current plan stays active until the payment settles |
| **Payment links** | A hosted Stripe Checkout page for credit top-ups, invoice payment URLs and overdue invoices |
| **Subscriptions** | Managed in Nozle. Paid plans activate only after the payment succeeds |
| **Credit top-ups** | Paid on a hosted Stripe Checkout page. Credits are granted once the top-up invoice is fully paid |
| **Saved payment methods** | The card used at checkout is saved for later automatic charges |
| **Refunds and disputes** | Credit-note refunds are sent to Stripe. Lost disputes update the invoice |
| **Customer import** | The dashboard imports existing Stripe customers and invoices |
| **Webhooks** | Nozle registers the webhook endpoint in your Stripe account and verifies every request |

## Webhook setup

Nozle registers the Stripe webhook for you. Right after you connect, a background job creates an endpoint in your Stripe account with the connection's secret key, stores the signing secret Stripe returns, and subscribes the endpoint to the events below. The endpoint URL is built from your public Nozle API URL and has this form:

```text
https://api.nozle.app/core/webhooks/stripe/{organization_id}?code={stripe_provider_code}
```

Nozle creates the endpoint with the Stripe API version it pins, `2025-04-30.basil` by default. The dashboard does not show the URL or the signing secret, and has no field to enter one.

| Events | Used for |
|---|---|
| `payment_intent.succeeded` | Settles the payment: marks the invoice paid, applies the plan change or grants top-up credits |
| `payment_intent.payment_failed`, `payment_intent.canceled` | Failed payments |
| `setup_intent.succeeded`, `customer.updated` | The customer's saved payment method. A card saved with a mandate also records the mandate |
| `mandate.updated` | The status of an India card mandate. When a mandate becomes active, Nozle retries the customer's pending invoices |
| `payment_method.detached` | Clears the stored default payment method when it is the detached one |
| `refund.updated`, `refund.failed` | Refund status, including a refund Stripe could not complete |
| `charge.dispute.closed` | Disputes |

Nozle subscribes the endpoint to these ten events only. The older `charge.refund.updated` is no longer subscribed, but an endpoint created earlier that still sends it keeps working: Nozle accepts it and handles it like `refund.updated` for one more release, then removes it. Endpoints that Nozle creates from now on subscribe to `refund.updated` and `refund.failed` (_Unreleased_); refresh an existing endpoint so it subscribes to them too. `mandate.updated` is new: refresh an existing endpoint to add it, or India card mandates are not kept up to date. Self-hosters run the one-time rake task `payment_providers:refresh_stripe_webhook_events` after upgrading, which updates the events of every Stripe endpoint Nozle created. Events such as `charge.refunded` and `charge.dispute.created` are not subscribed, and a valid event of any other type that reaches the endpoint is accepted and ignored.

Nozle verifies the `Stripe-Signature` header of every request against the stored signing secret, using Stripe's default time tolerance. A request with a bad signature, an unknown organization or code, or an unreadable body is answered with `400`. A valid request is stored, queued and answered with `200`. Nozle stores a Stripe event once by its event ID, so a delivery Stripe sends twice is dropped (_Unreleased_). Events received before that release have no event ID and are not de-duplicated. Replays are safe either way, because each handler acts on the state of the payment, invoice or upgrade: an upgrade or invoice that is already settled stays settled. A Stripe event whose handling failed is queued again once an hour, up to 12 attempts and only while it is younger than 3 days. After that Nozle logs the failure and reports it to its error tracker.

Each event acts only on the records of the organization that owns the webhook endpoint. A signed event that names a payment, refund, invoice, payment request or customer of another organization is ignored. A one-time payment for an invoice of another organization, or for no known invoice, is ignored too. The same applies to the webhooks of the other payment providers.

Registration is retried with increasing delays (up to 6 attempts) when Stripe rate-limits the request, is unreachable or returns a server error, so a short Stripe outage while you connect does not leave the connection without an endpoint. It still fails when the key may not create webhook endpoints, when the account has reached Stripe's limit of 16 test-mode endpoints, or when Stripe rejects the URL, for example because it is not a public host. In each case, and when the last retry fails, Nozle sends the `payment_provider.error` webhook with Stripe's message. The dashboard shows nothing, so to confirm registration open the Webhooks page of your Stripe dashboard and look for the endpoint. To recover, fix the cause and connect again. Disconnect the old connection first, or the new one fails with `stripe_account_already_connected`.

Without the webhook, Stripe can collect the payment but Nozle is not told. Checkout status reads the Checkout Session from Stripe for a paid upgrade and reports `processing` once the session is complete, but it never settles a payment. Only the webhook does. Nozle never marks an invoice paid or activates a plan from a browser callback.

## Checkout flow

1. Customer selects a plan in your app.
2. Your backend derives the customer and calls Nozle checkout with an `sk_` key.
3. Nozle computes the exact invoice or proration, keeping the current plan active.
4. If money is due, Nozle makes sure the customer exists in Stripe, creates a hosted Checkout Session and returns a `hosted` result. A saved card is charged first, and then no page opens.
5. Your app redirects the browser to the `url` of the result. Stripe sends the customer back to your `return_url` (or to `cancel_url` when they leave).
6. Stripe sends `payment_intent.succeeded` to Nozle.
7. Nozle marks the invoice paid and applies the change: it activates the new subscription, or applies the upgrade.
8. Your app confirms the result. For a new subscription, reload the subscription. For an upgrade, poll checkout status.

If prepaid credits fully cover the invoice, Nozle returns a completed checkout and Stripe is not called. The `return_url` you send must be an HTTPS URL on one of your organization's allowed origins, and Nozle passes it to Stripe as the return URL of the session. It may contain the literal `{CHECKOUT_SESSION_ID}`, which Stripe replaces with the Checkout Session ID. The optional `cancel_url` is validated the same way and defaults to the return URL. Nozle sends Adaptive Pricing disabled so the customer is charged in the invoice currency.

For an invoice that already exists, call checkout with the invoice instead of a plan. It returns the same `hosted` result. The invoice must not be paid, void or a draft.

An invoice has at most one payable Checkout Session at a time. This applies to invoice checkout and to resumed or Entity subscription checkout:

- Calling checkout again for the same invoice, with or without an `Idempotency-Key`, returns the session that is still open, with the same `url`.
- A session that expires within 10 minutes, or that was opened for another amount, is expired at Stripe before exactly one new session is created.
- While the customer's payment of the last session is processing or has succeeded, checkout answers `422 validation_errors` with `base: [payment_already_processing]` instead of opening a session that could charge the customer twice.
- If a second payment still succeeds for an invoice that is already paid, Nozle does not apply it. It refunds the payment in full at Stripe with refund reason `duplicate`, and sends you the `invoice.payment_failure` webhook with `provider_error.error_code` `duplicate_payment_refunded` and the payment intent in `error_details.provider_payment_id`. If Stripe refuses the refund, the code is `duplicate_payment_refund_failed`: refund it in the Stripe dashboard. A payment that was still processing when the invoice was paid another way, for example marked as paid, is not refunded automatically; the code is `duplicate_payment_requires_review`.
- When an invoice no longer needs paying, Nozle expires its open Checkout Sessions (the checkout page and the hosted one of its payment link) and retires its payment link, so a customer with the checkout page still open cannot pay it. This happens when the invoice is voided, marked as paid, paid by another route, partly paid, or reduced by a credit note offset. After a partial payment or an offset, the next checkout is created for the amount now due.
- If a payment still lands on a voided invoice (the customer completed the checkout before it expired), Nozle refunds it in full. The invoice stays voided and unpaid, and you get the `invoice.payment_failure` webhook with `provider_error.error_code` `voided_invoice_payment_refunded`. If Stripe refuses the refund, the code is `voided_invoice_payment_refund_failed`: refund the payment in the Stripe dashboard.
- When the amount left to pay is under Stripe's minimum charge (for example a partly paid invoice with less than $0.50 due), checkout answers `422 validation_errors` with `error_details.base` `amount_below_provider_minimum`. The invoice's earlier session is expired.

### The checkout result

```json
{
  "type": "hosted",
  "url": "https://checkout.stripe.com/c/pay/cs_live_...",
  "payment_url": "https://checkout.stripe.com/c/pay/cs_live_...",
  "checkout_id": "cs_live_...",
  "invoice_id": "invoice_uuid",
  "amount_cents": 19900,
  "currency": "USD",
  "expires_at": "2026-11-01T12:00:00Z"
}
```

- `url` is the Stripe-hosted page. Redirect the customer to it. `payment_url` is the same value. `checkout_id` is the Stripe Checkout Session ID, not a status ID.
- There is no `client_secret` and no Stripe publishable key. The old `type: "stripe"` result no longer exists.
- `amount_cents` is in the smallest unit of the invoice currency.
- A paid upgrade returns `plan_upgrade_intent_id` instead of `invoice_id`. The session stays open for 35 minutes.
- The Checkout Session of a new-subscription or single Entity checkout expires after 23 hours, when the unpaid checkout itself expires.
- An Entity checkout adds `external_entity_id` and `external_subscription_id`.
- Send an `Idempotency-Key`. A retry of an invoice checkout returns the session that is still open for that invoice.
- Starting the same upgrade again returns the session that is still open. Starting a different plan expires the open session and replaces it. If the open session cannot be replaced, for example while a payment is processing, Nozle answers `409 plan_upgrade_checkout_in_progress`.
- An upgrade is refused with `409 subscription_change_pending` while the subscription has a scheduled cancellation or plan change. Cancelling at period end or scheduling a plan change expires an open upgrade session.
- When the upgrade's time runs out, Nozle asks Stripe before it reports the upgrade expired: an open session is expired at Stripe, a completed session with a succeeded payment is settled and applied as its webhook would be, and a payment still processing (or a Stripe error) answers `409 plan_upgrade_checkout_in_progress`. Once a late payment is applied, a new checkout of the same plan answers `422 plan_already_active`. See [Upgrade checkout that ran out of time](/api/create-checkout#upgrade-checkout-that-ran-out-of-time).
- If the session expired before its time, for example because Stripe expired it, the upgrade itself stays open. A new upgrade checkout then returns `409 plan_upgrade_checkout_in_progress` until the upgrade's own 35 minutes pass, even though status already reports `expired`.
- A retry of a confirmed quoted upgrade can return `{"type": "processing", "checkout_id", "status"}`, where `checkout_id` is the upgrade ID. This is the answer while Nozle waits for the webhook of a payment that is already complete. Recover it with checkout status rather than starting another checkout.

#### Retry a new-subscription checkout

A new-subscription checkout leaves an incomplete subscription behind until the payment succeeds. Calling checkout again for the same customer and plan while that subscription is incomplete reopens the first checkout for the same invoice instead of failing, with or without the same `Idempotency-Key`. The React `CheckoutButton` retry does this. Asking for a different plan replaces the abandoned checkout: the old checkout expires and the new checkout is returned. `409 subscription_checkout_in_progress` is returned only while Stripe is still processing a payment for the old checkout, or when that checkout turns out to be paid.

An unpaid new-subscription checkout expires after 23 hours: the subscription is canceled with `cancelation_reason: timeout` (`subscription.canceled` webhook), the invoice is closed, the coupons, credit-note credits and wallet credits it used are returned, and its open Checkout Session is expired. See [Unpaid checkout expiry](/api/create-checkout#unpaid-checkout-expiry).

An invoice checkout forwards its `Idempotency-Key` to Stripe. Reusing a key with a different body returns `409 idempotency_key_reused`.

Checkout and status calls need an `sk_` key, so they run only in your backend. Bind each upgrade ID to the buyer who started it before you call Nozle. Checkout from an invoice sends no `return_url` through the SDKs, so Nozle uses its configured default return URL.

After the customer returns, reload the subscription: a new subscription or invoice checkout has no status call. For example, call `GET /billing/status` with the customer until it returns the plan the customer bought. It returns `404` while the subscription is not active. For a paid upgrade, poll `GET /checkout/{plan_upgrade_intent_id}` (not the `checkout_id`, which is the Stripe session ID): `awaiting_payment` with the hosted result nested while the buyer pays, `processing` once Stripe took the payment, `succeeded` with a nested `completed` when applied, and `expired` when the Stripe session is no longer open.

### Redirect to the hosted page

Send the browser to `url`. Nothing is mounted: no Stripe.js, no publishable key. A Nozle `pk_nozle_` key cannot start a checkout either: it is valid only for the plan catalog.

### HTTP

The SDKs call these Engine endpoints. Create and status need a secret key with `payment:write` or `payment:read`:

| Call | Purpose |
|---|---|
| `POST https://api.nozle.app/engine/api/v1/checkout` | Create the checkout. See [Create checkout](/api/create-checkout) |
| `GET https://api.nozle.app/engine/api/v1/checkout/{plan_upgrade_intent_id}?customer_id=...&subscription_id=...` | Read the status of a paid upgrade |
| `GET https://api.nozle.app/engine/api/v1/billing/status?customer_id=...` | Read the customer's active plan. See [Billing status](/api/billing-status) |

Both status scope parameters are required together. Core, called directly at `GET /api/v1/checkout_sessions/{id}`, names them `customer_id` and `external_subscription_id`. Without them the call returns `404 checkout_session_not_found`, and with only one it returns `400`. The verify endpoint is for Razorpay orders only. Nozle has no verify step for Stripe.

## How Nozle settles a payment

- **Webhook only.** Nozle settles a Stripe payment only on `payment_intent.succeeded`. It finds the payment from the data it attached when it created the session. A payment that Nozle did not create is ignored.
- **Upgrade checks.** Before it applies an upgrade, Nozle checks that the upgrade is still payable, that the payment is the one it expects, that the customer still uses the same Stripe connection, and that the subscription is still active with no pending change. It then recomputes the upgrade invoice and compares it with the quoted amount and currency. Nozle does not compare the amount Stripe collected with the quote. Any mismatch moves the upgrade to `needs_review`.
- **Statuses.** Nozle maps the Stripe payment status like this:

| Stripe payment status | Nozle treats it as |
|---|---|
| `succeeded` | Paid |
| `processing`, `requires_capture`, `requires_action`, `requires_confirmation` | Processing |
| `canceled`, `requires_payment_method` | Failed |

- **Declined cards.** On a payment-gated checkout a declined card keeps the invoice open, so the customer can try again in the same session. Any other failure marks the payment failed, closes the invoice and cancels the incomplete subscription.

A browser success callback alone never activates a plan.

## Status

`GET /checkout/{plan_upgrade_intent_id}` returns the status of a paid upgrade:

| `status` | Meaning |
|---|---|
| `awaiting_payment` | The session is open, or a declined payment can be retried |
| `processing` | The session is complete in Stripe and Nozle has not applied it yet, or is applying it |
| `succeeded` | The upgrade was applied |
| `failed` | Stripe canceled the payment, the upgrade was replaced, or the session could not be created |
| `expired` | The session passed its 35 minutes, or Stripe expired it |
| `needs_review` | A payment could not be applied safely. See below |

While the upgrade awaits payment, each status call retrieves its Checkout Session from Stripe. It reports `processing` when Stripe says the session is complete and `expired` when the session is not open any more. A status call never settles a payment: `succeeded` appears only after the webhook has applied the upgrade.

`fulfillment_status` is `pending` until the upgrade is applied, then `succeeded`. Show success only when both are `succeeded`, then reload the subscription. The response also carries `checkout_id` (the upgrade ID), `provider` (`stripe`), `amount_cents`, `currency` and `invoice_id`. `invoice_id` is empty until the upgrade is applied. While the status is `awaiting_payment`, a nested `checkout` carries the hosted result of the still-open session, so a client can resume after a reload.

`needs_review` means Stripe took a payment that Nozle could not apply. It also appears when Stripe could not confirm whether it created the session. See [Paid upgrades: rules](/api/create-checkout#paid-upgrades-rules). Nozle grants no plan and records no successful payment for it. Check the payment in the Stripe dashboard and refund or reconcile it deliberately.

## Payment links

Nozle uses a hosted Stripe Checkout page for the other payment paths: an invoice payment URL, a credit top-up purchase, and the link for overdue invoices. The page offers the payment methods set on the customer. An invoice payment link expires after 24 hours. The result is a `payment_url`, which you navigate the customer to. After payment the customer goes to the connection's success redirect URL. `payment_intent.succeeded` settles it.

## Credit top-ups

A credit top-up for a Stripe customer returns a hosted Stripe Checkout page as `payment_url`, and `payment_provider` is `stripe`. Navigate to it. Credits are granted once the top-up invoice is fully paid and the credit signal is delivered. A Stripe payment pays it; so does a manual payment for the full amount, a payment request, or marking the invoice paid.

```bash
curl -X POST https://api.nozle.app/engine/api/v1/credit-top-up-purchases \
  -H "Authorization: Bearer $NOZLE_SECRET_KEY" \
  -H "Idempotency-Key: topup-customer_123-starter_pack-1" \
  -H "Content-Type: application/json" \
  -d '{"customer_id": "customer_123", "credit_system_code": "ai_credits", "top_up_package_code": "starter_pack"}'
```

The customer must already be assigned to the Stripe connection and linked to a Stripe customer. If not, the call fails with `422 validation_errors` and `no_linked_payment_provider` or `missing_payment_provider_customer`. If the customer has a currency, it must match the package currency, or the call fails with `validation_errors` and `customer_currency_mismatch`. See [Paid Credit Top-ups](/guides/credits/top-ups) and [Create Credit Top-up Purchase](/api/create-credit-top-up-purchase).

## Saved payment methods and automatic charging

- **Saving a card.** Checkout asks Stripe to save the payment method for later off-session use. Nozle skips this for customers who use `crypto`. When the connection has a publishable key and the customer pays by card (or Link) only, a card setup link opens Nozle's card page instead of Stripe Checkout. See [Indian cards and automatic payments](#indian-cards-and-automatic-payments).
- **Automatic charges.** When an invoice is issued for a customer who has a Stripe customer ID, Nozle charges it through Stripe on its own, using the customer's saved payment method. This covers renewals. Checkout and top-up invoices are paid through their own session instead. If the saved method is gone, Nozle uses the first payment method it finds on the Stripe customer. Customers who pay by `customer_balance` bank transfer are charged on session, not off session. A card issued in India is charged automatically only through its mandate (see below). The customer's `country` is not what decides this: the card and its mandate are.
- **Authentication.** Stripe can refuse an off-session charge with `authentication_required`. With **Support 3DSecure** on, Nozle retries it on session. The payment moves to `requires_action`, Nozle sends the `payment.requires_action` webhook, and the invoice stays pending until the customer completes the action. With it off, the payment fails.
- **Small amounts.** Nozle checks Stripe's minimum charge (for example USD 0.50) before it calls Stripe, for the currencies it knows the minimum of (_Unreleased_). An off-session charge below it is not sent: the payment fails with `amount_below_provider_minimum`, the invoice stays pending and you receive the payment error webhook. An `amount_too_small` error that Stripe itself returns also leaves the invoice pending instead of failed.
- **Stripe limits and timeouts.** A charge for a payment request that Stripe rate-limits or that times out is tried again, up to 6 attempts with growing delays, like an invoice charge (_Unreleased_).
- **Keeping methods current.** `setup_intent.succeeded` makes the new method the customer's default. `customer.updated` follows a default change made in Stripe. `payment_method.detached` clears the stored default when the customer removes that card in Stripe.
- **Merchant webhooks.** Nozle sends `payment.succeeded` when a payment succeeds, `payment.requires_action` when a payment needs the customer, and [`payment.scheduled`](#upcoming-automatic-payments) when it announces an automatic debit.

## Indian cards and automatic payments

Indian rules (RBI) do not let a business debit a card issued in India on its own, month after month, unless the cardholder registered an **e-mandate** with the bank. A mandate is the cardholder's standing permission for recurring debits up to a maximum amount.

**Turn it on.** Set the **Publishable key** on the Stripe connection. Without it, nothing changes and cards are saved on Stripe Checkout as before. A card saved on Stripe Checkout has no mandate, so it cannot be charged automatically if it was issued in India.

**What the customer sees.** When the customer adds a card, the link opens a card page on Nozle's domain, with Stripe's secure card fields. For a card issued in India the bank asks for one OTP, and that registers the mandate with the card. For a card issued anywhere else the page behaves like any card form: no extra step. Nothing is charged when a card is only saved. Card details go from the browser to Stripe's fields and never reach Nozle, which keeps only Stripe's ids and the mandate status. The link is signed and expires after 24 hours.

The card page is used for the card setup links of a customer (the `customer.checkout_url_generated` webhook carries the link), and for Nozle's own workspace card step. It is used only when the customer's payment methods are `card` or `card` with `link`. The pay link of an invoice (the link in the emails, the workspace pay link and the dashboard **Pay** button) opens the same page when the connection has a publishable key and either the customer pays by card (or Link) only and the link would save the card, or the customer is from India (_Unreleased_). The customer pays the invoice there and, for a card issued in India, the bank registers the mandate in the same authentication. The page reads the amount from the invoice when it asks Stripe for the payment, so it is always the amount due at that moment. It answers `410` once the invoice is no longer payable. Other links (payment requests, crypto) and the paid plan upgrade checkout still use Stripe Checkout, which cannot register a mandate, and Checkout does not save the card of a customer from India. [`POST /customers/{customer_id}/payment-method/manage`](/api/manage-payment-method) returns the same page when the connection has a publishable key and the customer pays by card only; otherwise it returns the Stripe Billing Portal.

**What the customer is returned to.** After the card page, the customer goes to your return URL with `nozle_card=succeeded`, `processing` or `failed` added. Treat it as a hint for what to show. The saved card and mandate are recorded by Nozle from Stripe, not from the redirect.

### Show the card page in your app

By default the customer leaves your app for the card page. To keep them in your app, show the page in a frame: add `embed=1` to the `url` (the React SDK does this for you, see [NozleCardSetup](/sdks/react/components/nozle-card-setup)).

- **Who may frame it.** Only the origin (scheme, host and port) of the return URL you passed when you created the link. Nozle reads it from the signed link, never from the request. Without `embed=1`, the page cannot be framed at all. Create the link with a `return_url` on your app's origin.
- **Messages.** The page posts messages to the parent window, with the target origin set to that same origin, never `*`. A message carries no card data, ids or tokens:

```json
{ "source": "nozle", "type": "card_setup", "status": "ready", "mode": "setup" }
```

| `status` | Meaning |
|---|---|
| `ready` | Stripe's form is shown |
| `error` | The form cannot load |
| `succeeded`, `processing`, `failed` | The outcome after the bank step, which runs inside the frame |

`mode` is `setup` for a card setup link and `pay` for an invoice pay link. Check `event.origin` and `event.source` before you read a message, and treat `succeeded` as a hint: confirm through your webhooks or by reloading billing state.
- **Fallback.** If the frame never reports `ready`, or reports `error`, send the customer to the plain `url` (without `embed=1`). Opened as a top-level page, the return page redirects to your return URL with `nozle_card=` as described above.

### When Stripe rejects the publishable key

If the publishable key is well formed but Stripe rejects it, or Stripe.js does not load, the card page does not end in an error. In a browser tab it shows "Taking you to our payment partner" and redirects to Stripe Checkout for the same setup or payment. A card issued in India then pays through the pay link, as before the card page existed. Inside a frame the page never redirects: it sends the `error` message, and your page opens the plain `url`, which falls back the same way. Fix the key on the connection to get the card page back.

### How big the mandate is

The maximum of a mandate is the customer's largest recurring price times the connection's headroom multiplier (3 by default), kept between a floor and a ceiling per currency. Set the multiplier, floor and ceiling in the connection settings. The bank must accept the maximum, so a very high one can be refused by some issuers; the card is then not usable for automatic charges and the customer pays on the hosted page.

You can lower the ceiling but not raise it above what Indian banks accept. The ceiling in force is the lower of your setting and this figure, and the floor never exceeds the ceiling:

| Currency | Default floor | Highest ceiling |
|---|---|---|
| USD | 50 | 2,800 |
| EUR | 45 | 2,600 |
| GBP | 40 | 2,200 |
| INR | 4,000 | 2.5 lakh (250,000) |

A currency that is not in the table keeps whatever floor and ceiling you set, and has no default. The settings are in the smallest unit of the currency (for example `280000` for USD 2,800). The maximum only matters for cards issued in India: Stripe ignores it for other cards.

### Automatic charges of an Indian card

- **Within the limits.** Nozle charges with the mandate. The bank sends the customer a notice 24 hours before the debit, so the payment stays `processing` for up to 26 hours. Do not treat it as failed. A payment that is `processing` does not start a Nozle workspace's failed-payment clock.
- **Above about INR 15,000, or above the mandate maximum, whichever is lower.** The customer must approve the bank's notice before the debit. Raising the maximum does not remove the INR 15,000 rule: such a bill needs approval every time. If the customer does not approve, the charge is declined and the customer pays on the hosted page.
- **No active mandate** (a card saved before this, a mandate the bank cancelled or refused, or one still pending): the customer pays on the hosted page as before. A card saved earlier needs saving again on the card page.
- **Retries.** A failed charge that cannot succeed by retrying (authentication needed, a missing, cancelled or unapproved mandate, or a hard decline such as a lost or expired card) is not retried: the customer gets the pay link at once. Other failures are retried as before.
- **What the customer reads.** The wording follows the same outcome, from Stripe's codes only. When the bank needs the customer to confirm the payment, the email says "Your bank asked you to confirm this payment" with a **Pay now** button and promises no retry. For a card that will not work it says "This card could not be charged" and offers **Use another card** (**Change card** in a Nozle workspace email). Other failures keep the wording that says the card may work later. This applies to your customers' `invoice.payment_failure` email and to a Nozle workspace's failed-payment and reminder emails. For a workspace, the dashboard field `workspaceBilling.failureAction` (`CONFIRM_PAYMENT`, `CHANGE_CARD`, `RETRY_LATER`; `null` unless the workspace is past due) carries the outcome.

Other card networks and countries need no mandate. Only Visa and Mastercard get Indian mandates.

## Upcoming automatic payments

When a card payment is debited automatically after the bank's notice (it stays `processing` until then), Nozle tells the customer in advance, once per planned debit time:

- **Webhook `payment.scheduled`.** The payment plus `scheduled_at` (ISO 8601, UTC) and `method_type` (`card`). If the time changes, Nozle sends it again. Use it to send your own message.
- **Webhook `payment.schedule_cancelled`.** The announced debit will not happen. It carries `scheduled_at` and `reason`, and no `method_type`. For Stripe today the reason is `mandate_changed` when the failure is one only the customer can fix, and `notice_failed` otherwise. `invoice_paid`, `invoice_voided` and `other` are used for Razorpay debits.
- **Email.** Nozle emails the customer in your branding: "We plan to charge ... on the planned date", with a **Pay now** button. It follows the connection setting `upcomingDebitEmail`: unset, it is on for payments in INR and off for other currencies (the card's country is not read: a card issued in India is charged in INR); `true` always sends, `false` never sends. Nothing is sent to a customer without an email address. If you turn it off to send your own message, use the webhooks above.

No notice is sent for a payment that waits for the customer's approval: the approval email covers it. For a Nozle workspace, members get the same notice by email. See [Webhook events](/api/webhook-events#payments).

## Refunds and disputes

- **Refunds.** A credit-note refund is sent to Stripe against the invoice's latest successful payment. Nozle maps the credit-note reason to the Stripe reason and records the status Stripe returns. A card refund normally comes back `succeeded` at once, and the credit note is then refunded. The refund stays `pending` only when Stripe reports it as pending, until `charge.refund.updated` delivers the final status. Once the credit note has succeeded, a later `charge.refund.updated` is ignored. If Stripe rejects the refund or reports it failed, Nozle marks the refund failed and sends the `credit_note.refund_failure` webhook. Nozle creates no refund for an invoice whose dispute was lost.
- **Disputes.** On `charge.dispute.closed` with status `lost`, Nozle marks the invoice's dispute lost and sends the `invoice.payment_dispute_lost` webhook. A dispute that closes any other way changes nothing.
- **Top-ups.** A credit note or a lost dispute on a paid credit top-up invoice also takes back the top-up's unspent credits. See [Refunds and lost disputes](/guides/credits/top-ups#refunds-and-lost-disputes).

## Metadata on Stripe objects

Nozle sets `nozle_*` metadata on the Stripe objects it creates, so you can match them in your Stripe dashboard: Checkout Sessions, PaymentIntents, Customers and refunds carry `nozle_customer_id`, `nozle_invoice_id`, `nozle_payable_id`, `nozle_payable_type`, `nozle_payment_id`, `nozle_credit_note_id`, `nozle_organization_id` and `nozle_billing_entity_id` where they apply. From Core 6.0.0 Nozle writes and reads only these keys; the former-prefix keys are gone. Objects created before Core 6.0.0 keep their old keys, and Nozle still settles their payments and refunds by the provider id it recorded. If you report on Stripe metadata, read the `nozle_*` keys for new objects.

## Import existing Stripe customers and invoices

Use **Sync Stripe customers and invoices** on the connection to bring an existing Stripe account into Nozle. A preview comes first and changes nothing. Nozle then creates missing customers, links matching ones and imports invoices as read-only history. It changes no Stripe data and no subscription.

The preview and the sync run in the background. Starting one returns a sync run at once, and its `status` moves through `queued`, `previewing`, `previewed`, `syncing_customers`, `syncing_invoices`, then `completed` or `failed`. The customer sync imports the invoices after the customers without a second call. `counts` gives live totals per object type and status while the run works. A record that conflicts with another, or is invalid, is marked `conflict` or `failed` and the run goes on.

From code, the same steps are `POST /api/v1/integrations/stripe/sync/preview` (`payment_provider_id`, optional `mappings` of `stripe_customer_id` to `external_customer_id`), `POST /api/v1/integrations/stripe/sync/customers` with the previewed run's `run_id`, and `GET /api/v1/integrations/stripe/sync-runs/{id}` to poll, on the Core API with a secret key (with API key permissions: `customer:write`, and `customer:read` to poll). Each answers `{"stripe_sync_run": {...}}`. The dashboard polls the GraphQL query `stripeSyncRun` the same way. Poll until the run is `completed` or `failed`. Starting a run that is still working answers `409 stripe_sync_in_progress`, and starting a run that already finished answers `422 stripe_sync_run_finished`: start a new sync from a new preview.

Nozle matches a Stripe customer to an existing link, then to the mapping you set in the preview, then to its metadata, and otherwise creates a customer. The metadata keys are `nozle_external_customer_id`, `external_customer_id`, `org_id`, `organization_id` and `workspace_id`. A customer whose email matches one Nozle customer is a suggestion to confirm, not an automatic link. The sync reads at most 10,000 customers and 10,000 invoices, and the preview shows the first 500 rows. A linked customer can then pay by top-up and automatic charge.

## Errors

Checkout errors that are specific to Stripe. See [Create checkout](/api/create-checkout#errors) for the full list.

| Status | Code | Cause |
|---|---|---|
| `422` | `payment_provider_required` | The organization has no Stripe connection and the customer is not on Razorpay |
| `422` | `validation_errors` | `error_details.base` is `amount_below_provider_minimum`: the amount left to pay on the invoice is under Stripe's minimum charge |
| `422` | `stripe_customer_required` | Nozle could not create the customer in Stripe. A `customer.payment_provider_error` webhook carries the Stripe error |
| `409` | `subscription_checkout_in_progress` | A new-subscription checkout for this customer on a different plan is still being paid. See [Retry a new-subscription checkout](#retry-a-new-subscription-checkout) |
| `422` | `validation_errors` | `error_details.base` is `invalid_invoice_status_or_payment_status` when the invoice is paid, voided, a draft, closed, failed or has nothing due (checkout and payment URL), `missing_stripe_customer` or `missing_payment_provider` when the connection or Stripe customer is missing, or `no_linked_payment_provider` and `missing_payment_provider_customer` for a payment link or top-up |
| `409` | `plan_upgrade_checkout_in_progress` | A payment for the upgrade is already processing, or another upgrade checkout is open. It also stays in force after Stripe expired the session early, until the upgrade's own 35 minutes pass |
| `422` | `third_party_error` | Stripe rejected the request. `error_details.third_party` is `Stripe` and `thirdparty_error` carries Stripe's message |
| `404` | `checkout_session_not_found` | Unknown upgrade ID, or a status call without the customer and subscription scope |
| `500` | none | An invoice checkout reused an `Idempotency-Key` with a different body. Stripe's idempotency error is not handled today. Send the same body with the same key |

Connecting Stripe can fail with `500 stripe_account_already_connected` (message `Internal error`), or with `422 third_party_error` and Stripe's message when Stripe rejects the secret key or no key is given.

## Limits

- Every Stripe checkout is a Stripe-hosted page (`checkout.stripe.com`, valid until `expires_at`; 24 hours for credit top-ups, invoice payment URLs and overdue invoices). Nozle returns no card form and no client secret.
- A saved card is charged first. Only when it cannot be charged does a page open.
- An upgrade session lasts 35 minutes. A new-subscription, single Entity or bulk Entity checkout lasts 23 hours. See [Entity Subscriptions](/api/entity-subscriptions#purchase-multiple-entity-plans-together).
- One connection per Stripe account and mode (test or live) in an organization. The secret key of a connection cannot change.
- Nozle manages the webhook signing secret. You cannot enter it in the dashboard.
- Bank transfers through `customer_balance` support USD, GBP, JPY, MXN and EUR. For EUR the customer or your billing entity must be in Belgium, Germany, Spain, France, Ireland or the Netherlands.
- Nozle does not restrict the payment methods of a Checkout Session. Which methods appear depends on your Stripe settings.

## Troubleshooting

| Symptom | Check |
|---|---|
| Customer paid in Stripe but the plan is not active | The webhook endpoint exists in your Stripe account, shows the URL above, and lists the eight events. Check its delivery attempts. For an upgrade, check the status for `needs_review` |
| Stripe shows `400` for webhook deliveries | The endpoint URL carries a code that no connection has any more, or the endpoint was recreated in Stripe so its signing secret no longer matches the one Nozle stored |
| No webhook endpoint in Stripe | Registration failed. Check the key's permissions, the 16 test-endpoint limit and that your public Nozle API URL is a host Stripe accepts, then disconnect and connect again. The `payment_provider.error` webhook carries Stripe's message |
| `payment_provider_required` | The organization has no Stripe connection |
| `stripe_customer_required` | Nozle could not create the Stripe customer. Check the `customer.payment_provider_error` webhook for the reason |
| Customer lands on stripe.com after a top-up | Add a success redirect URL to the connection |
| An upgrade shows `expired` | The session ended. Start the upgrade again. If Stripe expired the session early, the new call returns `409 plan_upgrade_checkout_in_progress` until the upgrade's 35 minutes pass |
| A checkout returns `409 subscription_checkout_in_progress` | A payment for the customer's new-subscription checkout on another plan is processing, or it was paid. Wait for the webhook and reload the subscription |
| Status call returns `404 checkout_session_not_found` | Send `customer_id` and `subscription_id` together, and use the upgrade ID, not an invoice ID |

Test your flows with a test-key connection before you connect live keys.
