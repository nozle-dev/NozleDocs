The `can()` endpoint is the core of Nozle's entitlement system.

## Request

```
GET /api/v1/can?customer_id=cust_123&feature=api_calls
Authorization: Bearer sk_nozle_...
```

Call this endpoint from a trusted backend with a restricted secret key. Derive `cust_123` from the authenticated application user; publishable keys are rejected.

| Query parameter | Required | Description |
|---|---|---|
| `customer_id` | yes | External customer ID |
| `feature` | yes | Feature code |
| `subscription_id` | no | External ID of one current subscription of the customer. Evaluates that subscription |
| `entity_id` | no | External ID of an Entity. Evaluates the Entity's own subscription, else the customer's own subscription |
| `metadata` | no | URL-encoded JSON object of event properties for the economics estimate. It does not filter usage: `used`, `limit` and `remaining` cover all of the feature's usage |

See [Which subscription is checked](#which-subscription-is-checked).

## Field reference

| Field | Type | Description |
|-------|------|-------------|
| `allowed` | `boolean` | Whether the customer can use this feature |
| `reason` | `string?` | Why access was denied. Omitted when `allowed` is `true`. See [Denial reasons](#denial-reasons) |
| `feature_type` | `string?` | Type of the feature. Not returned when the feature or the subscription is missing |
| `configuration` | `object?` | Configuration values granted by the plan for a non-metered feature |
| `used` | `number` | Usage in the current billing period, or the running total for a recurring Feature. Also the real usage of a metered Feature that has no entitlement and is only priced by a charge. `0` when the denial is decided before usage is read |
| `limit` | `number \| null` | Usage cap for this feature. `null` when there is no cap, and for a Feature priced only by a charge |
| `remaining` | `number \| null` | `limit - used`, never below `0`. `null` when `limit` is `null` |
| `overage` | `boolean?` | `true` when usage has reached a soft limit; the request is still allowed. Omitted otherwise |
| `economics.status` | `string` | `estimated`, `not_configured`, `unavailable`, or `stale` |
| `economics.currency` | `string?` | The currency of the matched Cost Rules. Cost, revenue and margin are all in it. See [Currencies](#currencies) |
| `economics.reason` | `string?` | Why the estimate is not `estimated`, for example `revenue_currency_mismatch` |
| `economics.fx_date` | `string?` | Engine 2.20.0 and later. Date (`YYYY-MM-DD`) of the exchange rate that converted revenue into `currency`. Omitted when revenue and cost share a currency |
| `economics.estimated_incremental_cost` | `string?` | Exact decimal incremental cost for the proposed Feature Event |
| `economics.estimated_incremental_revenue` | `string?` | Exact decimal usage revenue of the proposed call: the standard charge's unit price × the call's units (1 for a count Feature; the value of the Feature's `field_name` in `metadata` for a sum Feature) |
| `economics.estimated_incremental_margin` | `string?` | Estimated revenue minus estimated cost |
| `economics.estimated_margin_percent` | `string?` | Margin percentage when estimated revenue is greater than zero |
| `economics.rule_version_ids` | `string[]?` | Immutable Cost Rule versions used by the estimate |
| `economics.includes` | `string[]?` | Cost categories included in the estimate |
| `economics.excludes` | `string[]?` | Costs unavailable before execution, such as future Detailed Cost Events |
| `economics.calculated_at` | `string` | Time at which the estimate was calculated |
| `policy` | `object?` | Versioned policy, thresholds, fallback behavior, decision, and reason |

## Runtime behavior

The service may cache entitlement and usage state. Always treat the returned decision as point-in-time and enforce it immediately before protected work.

A subscription on an override plan (a plan made from a catalog plan for one customer, for example a negotiated price or a subscription created from a quote) gets the entitlements and usage limits of the catalog plan it was made from. Its usage is still priced with the override plan's own charges.

The optional `economics` object is also point-in-time, but it is not a financial ledger entry. Calling `/can` never consumes usage, changes a pricing period, or records cost. If a Feature uses `detailed_events_only`, the estimate is `unavailable` because the actual Cost Events do not exist yet. If it uses `add_both`, the known Feature Event Cost is returned and `future_detailed_cost_events` appears in `excludes`. An estimate older than the policy's `maximum_snapshot_age_seconds` is returned as `stale` and follows `on_unavailable`.

Estimated revenue is the standard charge's unit price × the units of this call. A count Feature adds 1 unit. A sum Feature adds the value of its value property (`field_name`) in the call's `metadata`, for example `{"tokens": 500}`; without that value the estimate is `unavailable` with `revenue_quantity_missing` in `excludes`. Max, latest, unique count, weighted sum and custom aggregations do not add a fixed amount per call, so their estimate is `unavailable` with `non_additive_revenue_aggregation`. When the estimate is `unavailable`, a margin policy decides with its `on_unavailable` value (`allow`, `warn` or `deny`), and `policy.reason` is `economics_unavailable`.

## Currencies

The estimate uses the currency of the matched Cost Rules, not the organization's reporting currency or the plan currency. Monetary values are decimal strings in currency units of `economics.currency`.

When the plan charge is priced in another currency than the cost, Engine 2.20.0 and later convert the revenue into the cost currency at both currencies' exchange rates of the request date. The response then carries `fx_date`, and `includes` lists `foreign_exchange_conversion`. If either currency has no rate, the estimate is `unavailable` with `reason` `revenue_currency_mismatch`, and `excludes` lists `foreign_exchange_conversion`.

<Note>
Before Engine 2.20.0, a charge in another currency than the cost always made the estimate `unavailable` with `revenue_currency_mismatch`, even when a rate existed.
</Note>

Two other currency codes can appear:

| Code | Where | Meaning |
|---|---|---|
| `mixed_reporting_currencies` | `economics.reason` | The Cost Rules that match the Feature use different currencies, so no cost is estimated. Publish them in one currency. |
| `reporting_currency_mismatch` | `policy.reason` | The margin policy's currency differs from `economics.currency`. The policy applies its `on_unavailable` value. |

The same two codes mark rated events `uncosted`. See the [currency rule](/api/cost-intelligence-report#currency-rule).

## Which subscription is checked

Plan, entitlements, limits and usage all come from one subscription, and only subscriptions that are current at this moment count: started, not ended, and before their end date.

- With `subscription_id`, `/can` evaluates that subscription of the customer. With `entity_id`, it evaluates the Entity's own subscription, else the customer's own subscription (not owned by an Entity). When both are sent, the subscription must belong to that Entity. An unknown or ended selection answers `no_subscription`.
- Without either, `/can` evaluates the customer's only current subscription. A customer with several current subscriptions is evaluated on its own subscription (not owned by an Entity) when there is exactly one. Otherwise the answer is `allowed: false` with the reason `subscription_required`: send `subscription_id` or `entity_id`. The newest subscription is never picked for you.

A customer with one current subscription sees no change. Usage is counted per subscription, so the usage of one Entity's seat never counts against another subscription's limit, and the counter continues across plan changes of the same subscription.

[`POST /billing/upgrade`](/api/upgrade) selects the subscription the same way. For a customer with several current subscriptions it answers `409 subscription_required` unless exactly one of them is the customer's own.

## Usage and billing periods

`used` follows the billing period in which Nozle invoices the usage, for every plan interval (weekly, monthly, quarterly, semiannual, yearly), for calendar and anniversary billing, and in the customer's time zone (the customer's, else its billing entity's):

- Periods start at midnight in that time zone. A weekly calendar period starts on Monday.
- An anniversary subscription that starts on the 29th to the 31st starts on the last day of shorter months.
- A yearly or semiannual plan that bills its charges monthly resets monthly.

A recurring Feature, such as seats or storage, keeps one running total across billing periods: a hard limit keeps blocking after a period ends instead of reopening on the first day. For these limits, a weighted sum or custom Feature counts the running sum of event values, not its time-weighted or custom billing value.

## Denial reasons

A denial is an HTTP `200` response with `allowed: false` and one of these `reason` values:

| `reason` | Meaning |
|----------|---------|
| `feature_not_found` | No feature with this code exists in the organization |
| `no_subscription` | The customer has no active subscription: none started, ended or cancelled, or the customer does not exist. Also an unknown or ended `subscription_id` or `entity_id` |
| `subscription_required` | The customer has several current subscriptions and not exactly one of them is the customer's own (not Entity-owned). Send `subscription_id` or `entity_id` |
| `no_entitlement` | The customer's plan does not include the feature |
| `usage_limit_exceeded` | A hard limit is reached. A soft limit never denies; it sets `overage` to `true` |
| `economic_policy_denied` | A margin policy in `deny` mode rejected the estimated cost or margin. The `policy` object has the detail |

`customer_payment_overdue` comes with HTTP `402`, not `200`: see [Unavailable or blocked](#unavailable-or-blocked).

For example, an unknown feature code returns:

```json
{
  "allowed": false,
  "reason": "feature_not_found",
  "used": 0,
  "limit": null,
  "remaining": null
}
```

## SDK wrappers

**Node:**

```ts
nozle.can('cust_123', 'api_calls')
```

**Python:**

```python
from nozle import Nozle

nozle = Nozle()  # reads NOZLE_SECRET_KEY

nozle.can('cust_123', 'api_calls')
```

**Go:** `client.Can(ctx, "cust_123", "api_calls")`. Pass `nozle.CanOptions{SubscriptionID: ...}` or `EntityID` to `CanWithOptions` to choose a subscription (`nozle-go` v0.16.0).

The Node (0.17.0), Python (`nozle-sdk` 0.17.0) and React (`useEntitlement`, 0.16.0) wrappers take the same selectors: see [Node](/sdks/node/entitlements#choose-the-subscription), [Python](/sdks/python/entitlements#choose-the-subscription) and [React hooks](/sdks/react/hooks#the-hooks).

**React:** fetch the result through your authenticated backend and pass it to `FeatureGate`, `UsageGate`, or your own UI.

## Availability and freshness

If usage cannot be read reliably, the hosted API returns HTTP `503` with a structured error and request ID, without an access decision. Treat it as unavailable; do not convert the failure into `allowed: true` or zero usage. Use bounded retries within your request budget and retain the request ID for support.

Entitlement configuration refresh is approximately once per minute. A plan or quota edit may take that interval to appear in `can()` results. Usage projections are asynchronous, and a separate `can()` followed by `track()` does not reserve quota atomically. Use [Track and Consume Credits](/api/usage-track) for atomic product-credit consumption.

## Unavailable or blocked

Two statuses are not a decision about the customer, and they ask for different handling:

- `503`: Nozle could not read usage. Retry within your budget, as described above.
- `402` `workspace_suspended` (_Unreleased_): your own workspace is suspended over unpaid Nozle invoices (`card_required` only for a workspace still flagged from before cards became optional). Do not retry. Every call fails until the invoices are paid, and the next request works again. The Nozle SDKs throw their API error with that `code` and never retry it; `can()` throws instead of returning `allowed: false`. See [Workspace billing](/guides/getting-started/workspace-billing).

One `402` is a decision about the customer:

- `402` `customer_payment_overdue` (_Unreleased_, Engine 2.22.0): this customer's unpaid invoices are past the grace of their plan and your [dunning policy](/guides/billing/dunning) blocks them. The body reads like a denial: `{"allowed": false, "reason": "customer_payment_overdue", ...}`. The Node SDK (0.23.0) returns it from `can()` as `{ allowed: false, reason: "customer_payment_overdue", used: 0, limit: null, remaining: null }` instead of throwing, so you can ask the customer to pay. The next call after the invoices are paid is allowed again.

Whether your app lets users through while `/can` is unavailable or blocked (fail open) or stops them (fail closed) is your decision. Nozle does not make it for you. Decide per feature, and fail closed where letting a user through costs you money.
