Plans describe what **your customers** buy from your product. Create them in your Nozle workspace; a new workspace does not automatically contain the example plan codes used in these docs. Your own Nozle platform subscription is separate from this customer plan catalog.

## Create a first plan

1. Open [the dashboard](https://app.nozle.dev) and create a metered Feature with a stable code, such as `api_calls`. For the quickstart, use count aggregation so each unique event contributes one unit.
2. Create a plan with a unique code such as `quickstart_free`, a monthly interval and a zero subscription price. Add the Feature entitlement with a usage limit of 10,000.
3. Create a customer with an external ID from your application, then activate a subscription to this plan. A plan alone does not grant a customer access.
4. Submit events with the matching Feature code and check the customer's usage after asynchronous processing. See the [quickstart](/guides/getting-started/quickstart).

For a paid plan, configure currency, subscription amount, billing interval and any usage charges explicitly. A Feature entitlement controls access; it does not by itself define a monetary usage charge. Configure your payment provider and [checkout flow](/guides/billing/checkout) before accepting payment.

For a sum-based meter, choose a numeric aggregation property such as `tokens` and send that property on every event. Keep the documented event code, aggregation and entitlement aligned.

## Read your catalog

The Engine `GET /api/v1/plans` endpoint returns your organization's plan catalog: all top-level plans, with their charges, taxes, minimums, entitlements and credit grants. A publishable `pk_` key can read it, which makes everything in a plan public. Nozle platform prices and feature availability are not returned as your customer plans. See the [public plan catalog](/api/list-plans) for the full response, which plans are included and how to keep sensitive pricing out of it.

```tsx
import { usePlans } from '@nozle-js/react'

const { plans, isLoading, error } = usePlans();
```

Use React `0.10.1` or later (`0.11.0` is the current release) and handle `error` before rendering a pricing table. Configure `BillingProvider` with a publishable key as shown in [React setup](/sdks/react/installation).

```ts
import { Nozle } from '@nozle-js/node'

const nozle = new Nozle() // reads NOZLE_SECRET_KEY

const plans = await nozle.plans();
```

```python
from nozle import Nozle

nozle = Nozle()  # reads NOZLE_SECRET_KEY

plans = nozle.plans()
```

## Change a plan customers pay for

Changing the price, charges, credits or entitlements of a plan that has subscribers saves the plan's next version: new customers get it, and existing subscribers keep the price they bought until you move them. See [Plan versioning](/guides/billing/plan-versions).

## Sell a plan in several currencies

A plan family can sell one plan per interval and currency, each at its own fixed price. See [Multi-currency pricing](/guides/billing/multi-currency-pricing).

## Grace days and dunning

_Unreleased (Core 11.16.0 and 11.19.0)._ A plan says how long a subscriber keeps access while one of its invoices stays unpaid. Set the grace days on the plan form under **Unpaid invoices**, or in the REST `plan` payload of `POST /plans` and `PUT /plans/{code}`. The campaign link is set through the API only (REST `dunning_campaign_code`, GraphQL `dunningCampaignId`).

| Field | Meaning |
|---|---|
| `unpaid_invoice_grace_days` | Days between day 0 of an unpaid invoice of the plan and the end action of its [dunning policy](/guides/billing/dunning). Whole days, 0 to 90, default 7. `0` blocks at once. |
| `limit_grace_days` | Days after the unpaid invoice of an automatic upgrade at the plan's MRR limit. Whole days, 0 to 90, default 7. Nozle reads it for its own plans (see [Workspace billing](/guides/getting-started/workspace-billing#grace-a-and-grace-b)). The dunning policy of your customers reads `unpaid_invoice_grace_days` only. |
| `dunning_campaign_code` | The dunning campaign the plan's unpaid invoices follow, before the customer's or the billing entity's. `null` unlinks it. An unknown code returns `404` `dunning_campaign_not_found`. |

- A value outside 0 to 90 is refused with `value_is_out_of_range`.
- Editing these fields never creates a new plan version, even when the plan has subscribers. New versions copy them, and a plan family copies them to its other currencies.
- Deleting a dunning campaign unlinks the plans that point to it.

See [subscriptions](/guides/billing/subscriptions) for activation and lifecycle changes, and the [production integration checklist](/guides/getting-started/production-readiness) for features requiring additional setup.
