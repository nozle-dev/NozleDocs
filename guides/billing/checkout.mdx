Nozle collects plan payments through the payment provider connected to your organization: Stripe or Razorpay. The flow is the same for both:

1. Customer selects a plan in your application
2. The React SDK calls your authenticated merchant callback with `{ planCode, returnUrl }`
3. Your backend derives the customer, validates the plan and return origin, and calls Nozle with `sk_`
4. Nozle keeps the current plan active and computes the exact invoice or proration
5. If money remains due, Nozle returns a provider result: an embedded Stripe Checkout Session secret, or a Razorpay order
6. Customer completes payment in the provider's UI
7. The provider confirms the payment to Nozle (a signed webhook, and for Razorpay also your verify call)
8. Nozle applies the paid plan change only after verified success

<Info>
Plan checkout is payment-gated: a paid plan change is not applied until the payment provider confirms payment. If prepaid credits reduce the exact amount due to zero, Nozle applies the change transactionally and returns `type: "completed"` without creating a provider session.
</Info>

A customer whose provider is not connected cannot pay: checkout returns `payment_provider_required`. At checkout Nozle creates the customer in Stripe when it is missing, and returns `422 stripe_customer_required` if it cannot.

## Stripe

Plan and invoice checkout always create an embedded Stripe Checkout Session and return its `cs_` client secret. They never return a Stripe-hosted URL. Credit top-ups are the exception: they return a Stripe-hosted `checkout.stripe.com` `payment_url` that is valid for 24 hours. Mount the secret with Stripe Embedded Checkout (the React [`Checkout`](/sdks/react/components) component does this for a `cs_` secret).

### Required Stripe webhook setup

When you connect a Stripe account, Nozle registers a Stripe webhook endpoint for that account and stores Stripe's webhook signing secret. Your Stripe account must allow webhook endpoint creation.

The webhook target is derived from your public Nozle API URL:

```text
{NOZLE_PUBLIC_API_URL}/webhooks/stripe/{organization_id}?code={stripe_provider_code}
```

Stripe events Nozle handles:

- `payment_intent.succeeded`
- `payment_intent.payment_failed`
- `payment_intent.canceled`
- `setup_intent.succeeded`
- `payment_method.detached` (received, but it does not clear the stored payment method today)
- `customer.updated`
- `charge.refund.updated`
- `charge.dispute.closed`

Nozle subscribes to these eight events only. Without this webhook, Stripe may collect payment but Nozle is not told. Checkout status of a paid upgrade reads the Checkout Session from Stripe and reports `processing` once it is complete, but it never settles a payment, so only the webhook does. See the [Stripe integration](/integrations/stripe) for setup, flows and limits.

A new-subscription Stripe checkout returns no checkout ID to poll. After Embedded Checkout completes, reload the subscription or wait for your `subscription.started` webhook. A paid upgrade returns `plan_upgrade_intent_id`; poll its status with [`GET /checkout/{id}`](/api/subscription-management) and the subscription scope.

Retrying a new-subscription checkout while its subscription is still incomplete returns `422 validation_errors` with `error_details.subscription: ["subscription_incomplete"]`, even with the same `Idempotency-Key`. Recover with an invoice checkout for the `invoice_id` of the first response. See [Retry a new-subscription checkout](/integrations/stripe#retry-a-new-subscription-checkout).

## Razorpay

Connect Razorpay in the dashboard with its key ID, key secret and webhook secret. Optional settings enable recurring mandates (with a maximum mandate amount). Razorpay supports only INR. Nozle does not register the Razorpay webhook for you: copy the webhook URL Nozle shows for the connection into your Razorpay dashboard, with the same webhook secret. See the [Razorpay integration](/integrations/razorpay) for setup, events and limits.

```text
{NOZLE_PUBLIC_API_URL}/webhooks/razorpay/{payment_provider_id}
```

Nozle checks the `X-Razorpay-Signature` header against the webhook secret and de-duplicates on `X-Razorpay-Event-Id`. On `payment.authorized`, `payment.captured`, `payment.failed`, `order.paid` and `payment_link.paid`, Nozle fetches the payment from Razorpay and settles the checkout once the payment is captured. Refund, mandate and dispute events are also handled.

A Razorpay checkout runs in four steps:

1. **Create.** Checkout returns `{"type": "razorpay", "checkout_id", "key_id", "order_id", "amount_cents", "currency", "expires_at", "invoice_id"}`. A paid upgrade has `plan_upgrade_intent_id` instead of `invoice_id`. A mandate checkout (`register_mandate`) also has `customer_id`, `recurring: true` and `mandate_max_amount_cents`. If the order is not ready yet, or has expired, the result is `{"type": "processing", "checkout_id", "status"}` instead. A bulk Entity checkout first answers `{"entity_subscription_checkout": {"type": "processing", "status": "open", "checkout_id": "..."}}`. A `processing` result carries an internal operation status such as `ready`, not the state of the checkout.
2. **Pay.** Load `https://checkout.razorpay.com/v1/checkout.js` and open `new window.Razorpay({ key: key_id, order_id, handler })`.
3. **Verify.** Send the three fields from the handler to your backend, which calls `POST /checkout/{checkout_id}/verify` with `razorpay_order_id`, `razorpay_payment_id` and `razorpay_signature`. A missing field returns `400`. Nozle checks that the order matches the checkout and that the signature is the HMAC-SHA256 of `order_id|payment_id` with your key secret; a mismatch returns `422 validation_errors` with `invalid_checkout_signature`. Nozle then fetches the payment from Razorpay and settles only a `captured` payment. The response is the checkout status.
4. **Poll.** Call `GET /checkout/{checkout_id}` until `status` and `fulfillment_status` are both `succeeded`. Each call reconciles with Razorpay.

| Field | Values |
| --- | --- |
| `status` | `succeeded`, `needs_review`, `failed`, `expired`, `awaiting_payment`, `processing` |
| `fulfillment_status` | `pending`, `processing`, `succeeded` |

The nested `checkout` of the status response is present while the checkout is `awaiting_payment` and also for an `expired` unpaid order. For the expired order it is `{"type": "processing", "status": "ready"}`, so do not reopen the modal for it. A status call without a customer and subscription scope needs a secret key; an unknown ID returns `404 checkout_session_not_found`. The React [`CheckoutButton`](/sdks/react/components) runs steps 2 to 4 for you when `BillingProvider` has `verifyCheckout` and `getCheckoutStatus` callbacks; it polls 30 times, one second apart.

To retry a new-subscription checkout, do not call checkout again: while the first order is unpaid it returns `422 validation_errors` with `error_details.subscription: ["subscription_incomplete"]`, even with the same `Idempotency-Key`. Reopen the modal on the same order with the checkout that status returns while `awaiting_payment`, or call an invoice checkout for the `invoice_id` of the first response. The React "Payment failed. You can retry checkout." button calls checkout again, so for a new subscription use the stored checkout instead. See [Retry a new-subscription checkout](/integrations/razorpay#retry-a-new-subscription-checkout).

`POST /checkout` never returns `type: "hosted"` for Razorpay. A Razorpay payment link comes from an invoice payment URL (`POST /invoices/{id}/payment_url`) or a credit top-up purchase, as an `rzp.io` `payment_url` with no checkout ID to poll. Redirect the customer to it; the `payment_link.paid` webhook settles it.

## API shape

Plan checkout:

```json
{
  "customer_id": "customer_123",
  "plan_code": "growth",
  "return_url": "https://app.example.com/settings/billing"
}
```

Free plans and paid upgrades fully funded by prepaid credits return a completed response instead. Downgrades and other cycle-end transitions return a scheduled response from the same `/checkout` endpoint; browser sessions never call `/billing/upgrade` or `/subscriptions/change`.

## Response

```json
{
  "type": "stripe",
  "client_secret": "cs_...",
  "clientSecret": "cs_...",
  "invoice_id": "invoice_uuid",
  "amount_cents": 19900,
  "currency": "USD"
}
```

The browser calls your authenticated merchant backend, which derives the Nozle customer and starts checkout with a restricted `sk_`. A Nozle publishable key is valid only for the plan catalog. If you mount embedded Stripe checkout yourself, your app also needs the Stripe publishable key for the same Stripe account connected in Nozle.

Credit-funded completion response:

```json
{
  "type": "completed",
  "status": "succeeded",
  "payment_source": "credits",
  "plan_code": "growth",
  "amount_cents": 0,
  "currency": "USD"
}
```

Scheduled transition response:

```json
{
  "type": "scheduled",
  "status": "pending",
  "subscription_id": "subscription_uuid",
  "plan_code": "starter",
  "transition_direction": "downgrade",
  "transition_policy": "next_period",
  "effective_at": "2026-11-01T00:00:00Z"
}
```

Changing an existing subscription needs a [plan transition policy](/api/plan-transition-policies) for that pair of plans. Without one, checkout returns `405 plan_transition_policy_required`. See [Create checkout](/api/create-checkout) for every result type and error.

## React implementation

### Option A -- CheckoutButton (simplest)

```tsx
<CheckoutButton
  planCode="growth"
  returnUrl="https://app.example.com/settings/billing"
  label="Subscribe to Growth"
  onStripeClientSecret={setClientSecret}
/>
```

### Option B -- Custom flow with `useCheckoutSession`

```tsx
const { fetchClientSecret, isLoading } = useCheckoutSession();

const handleCheckout = async () => {
  const clientSecret = await fetchClientSecret(
    'growth',
    'https://app.example.com/settings/billing',
  );
  // Pass the cs_... secret to <Checkout>
};
```

### Option C -- Embedded Stripe Checkout

```tsx
<Checkout
  clientSecret={secret}
  publishableKey={import.meta.env.VITE_STRIPE_PUBLISHABLE_KEY}
  onComplete={() => router.refresh()}
/>
```

`onComplete` does not fire when the session redirects to the `return_url`, and Nozle sessions redirect. Show success from your return page, or by reading billing status for the customer.

## Server-side plan changes

For B2B scenarios where payment is already handled outside embedded checkout:

```typescript
await nozle.customers.upsert({ externalId: 'customer_123', name: 'Acme' });
const result = await nozle.subscribe('customer_123', 'growth');
// { subscription_id: 'sub_...', status: 'active' }
```

`subscribe()` requires a secret key (`sk_`) and an existing customer: an unknown customer returns `404 customer_not_found`. Embedded checkout should be used when Nozle needs to collect payment before activating a paid plan.

## Mixed Entity plan checkout

Seat-based products can sell different Entity plans in one invoice and one payment. Every plan in the basket must require an up-front payment: a free, trial or pay-in-arrears plan is refused with `paid_plan_required`. Your backend first creates or reuses active placeholder Entities, then calls the bulk Entity checkout endpoint with the selected plan for each placeholder.

```text
Customer workspace
├── seat_pro_001 -> Pro monthly
├── seat_pro_002 -> Pro monthly
└── seat_max_001 -> Max monthly
           │
           └── one Nozle invoice -> one Stripe or Razorpay checkout
```

Keep the secret key in your backend. The browser should send only merchant-facing intent, such as `{ proSeats: 2, maxSeats: 1 }`; your backend derives the customer, creates stable Entity IDs, validates the return origin, and calls Nozle.

Use `billing_time: "anniversary"` when the first successful purchase should establish the customer's renewal day. Later Entity purchases align to that day and use Nozle's invoice proration.

See [Entity Subscriptions](/api/entity-subscriptions#purchase-multiple-entity-plans-together) for the complete request and response.
