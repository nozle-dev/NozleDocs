title: Subscriptions
description: Create, upgrade, downgrade, cancel, and restore subscriptions safely

Subscription changes run from a trusted merchant backend. Derive customer and subscription IDs from server-owned records; never accept either as authoritative browser input.

## Create a subscription

Use checkout for payment-gated plans. Direct subscription creation is available for flows that do not require interactive payment.

```ts
await nozle.customers.upsert({ externalId: 'customer_123', name: 'Acme' })
const subscription = await nozle.subscribe('customer_123', 'free')
```

The customer must exist before you subscribe it. An unknown customer returns `404 customer_not_found` and creates nothing.

`subscribe` creates the subscription `sub-<customer_id>-<plan_code>`; calling it again for the same plan returns that subscription and creates nothing. Calling it for a customer who already has a subscription to a different plan adds a second active subscription; it does not replace the first, and plan credit grants are granted again. After that, tracking without an explicit subscription ID fails because the customer has two. To move a customer to another plan, change the existing subscription through checkout with its `subscription_id`, or cancel it with `immediate` timing and then subscribe. Pass the new subscription ID to `track`: the Node.js and Python clients cache the subscription they resolved first.

`subscribe` does not collect payment, even for a paid plan. Use checkout when payment must succeed first.

## Billing alignment

The organization setting **Billing alignment** decides when the billing periods of new subscriptions start: `calendar` (the first of the month, the default) or `anniversary` (the day the subscription starts). Set it in the dashboard under **Settings > Billing settings > General** (Subscription periods), or with `PUT /organizations` as `billing_configuration.billing_alignment`, which the organization object returns.

A subscription can override it with `billing_time` (`calendar` or `anniversary`) on `POST /subscriptions`, checkout and [Entity checkout](/api/entity-subscriptions). Without `billing_time`, Nozle uses the organization's alignment. Changing the setting does not move existing subscriptions.

## Customer self-service

Use [the native React billing portal](/sdks/react/billing-portal), or add `CancellationControl` and `PlanChangeControl` to your own billing page. Your authenticated Node.js, Python, or Go backend supplies their action adapters.

| Customer action | Behavior |
| --- | --- |
| Cancel | Confirm the exact ending date; access continues until that saved boundary. |
| Keep | Remove a cancellation before it takes effect. |
| Upgrade | Review a signed quote and complete required payment before activating the target plan. |
| Downgrade | Schedule an eligible plan for renewal, preserving the current plan until then. |
| Withdraw downgrade | Remove the exact pending change while preserving the active subscription. |

The matching hosted API is available. Use React `0.10.2` with Node `0.10.0`, Python `0.10.0`, or Go `v0.9.1`, or later; the [portal guide](/sdks/react/billing-portal) provides setup and integration examples.

## Select, preview and confirm

A customer may have multiple subscriptions. Use its **external subscription ID** on every management call. Plan changes follow the [default policy](/api/plan-transition-policies#the-default-policy) (`self_serve_default`: an upgrade now, prorated; a downgrade at the end of the period) unless you configure a [plan transition policy](/api/plan-transition-policies) for the pair of plans, which wins. An immediate downgrade, a hidden or older plan and a trial need a pair policy: without one, preview and checkout return `422 plan_transition_policy_required`. The organization's free-to-paid policy still applies from a free plan to a paid plan. Check eligibility through subscription options; do not infer it from price or catalog membership.

The Node `subscriptionOptions`, Python `subscription_options`, and Go `SubscriptionOptions` methods return current, pending and eligible plans. Their `previewSubscriptionChange`, `preview_subscription_change`, and `PreviewSubscriptionChange` methods return an opaque signed quote with exact minor-unit amounts, currency, effective date and renewal date.

After customer confirmation, pass the quote and a stable idempotency key to checkout for upgrades. For scheduled downgrades, use the existing transition API with end-of-period timing and `keep_anchor`. A quote is valid for five minutes and binds the subscription state, plan versions, policy and amounts. A changed quote returns HTTP 409 and requires a fresh confirmation.

Preserve the same key, quote and payload when retrying one confirmed action after an uncertain response. Replaying an accepted action can succeed after quote expiry. Save merchant retry context durably; do not generate another collection attempt merely because a browser callback was lost.

## Payment and reload behavior

The current paid plan remains active until required payment is fulfilled. Razorpay requires capture; Stripe requires backend settlement. A browser callback or redirect alone does not establish activation. Reload authoritative state after checkout, failures and page reloads, and resume a recoverable checkout using its existing ID. Treat processing, expiry and support review as separate states.

Scheduled downgrades keep a distinct pending plan/effective date. Withdrawal uses its exact internal pending UUID, whereas ordinary management calls use the active subscription's external ID. A stale withdrawal cannot remove a replacement pending change.

See [Node billing](/sdks/node/billing#subscription-self-service), [Python billing](/sdks/python/billing#subscription-self-service), [Go billing](/sdks/go/billing), and [the HTTP contract](/api/subscription-management) for signatures and examples.

## Simple cancellation

Without a timing, a cancellation follows the organization's cancellation settings (dashboard **Settings → Billing → General → Cancellations**). Nozle's default timing is the end of the period. Pass `end_of_period` to say so explicitly (the examples below do):

```ts
const result = await nozle.cancelSubscription('customer_123', 'subscription_123', 'end_of_period')
console.log(result.subscription.ending_at)
```

```python
from nozle import Nozle

nozle = Nozle()  # reads NOZLE_SECRET_KEY

result = nozle.cancel_subscription("customer_123", "subscription_123", policy="end_of_period")
print(result["subscription"].get("ending_at"))
```

```go
import nozle "github.com/nozle-dev/nozle-go"

client := nozle.New("") // reads NOZLE_SECRET_KEY

result, err := client.CancelSubscription(ctx, "customer_123", "subscription_123", "end_of_period")
if err != nil { return err }
fmt.Println(result.Subscription.EndingAt)
```

Settlement options are optional as well: `credit_action` (`credit`, `refund`, `offset`, `none`) for unused paid time of a pay-in-advance plan, `refund_mode` (`prorated`, `full`) and `final_invoice_action` (`generate`, `skip`). Each one left out follows the subscription, then the organization's settings. Node.js takes them in an options object (`{ policy, creditAction, refundMode, finalInvoiceAction }`), Python as keyword arguments, Go as `nozle.CancelSubscriptionOptions`. See [Cancel Subscription](/api/cancel-subscription) for the rules.

```ts
await nozle.cancelSubscription('customer_123', 'subscription_123', {
  policy: 'immediate',
  creditAction: 'refund',
  refundMode: 'prorated',
})
```

```python
nozle.cancel_subscription(
    "customer_123", "subscription_123", "immediate", credit_action="refund", refund_mode="prorated"
)
```

```go
_, err := client.CancelSubscription(ctx, "customer_123", "subscription_123", "immediate",
	nozle.CancelSubscriptionOptions{CreditAction: "refund", RefundMode: "prorated"})
```

Pass `immediate` explicitly only after the merchant confirms that access should end now. For customer-facing Cancel/Keep, use the transition preview/apply flow and forward the exact `expectedEffectiveAt` / `expected_effective_at` / Go `ExpectedEffectiveAt` timestamp. Keep does not restart an ended subscription. Cancellation removes a pending downgrade; Keep does not recreate it.

## Settlement transitions

The backend SDKs provide preview and apply operations for `cancel`, `downgrade`, and `uncancel`.

```ts
const params = {
  customerId: 'customer_123',
  subscriptionId: 'subscription_123',
  operation: 'downgrade' as const,
  timing: 'end_of_period' as const,
  targetPlanCode: 'growth_monthly',
  creditAction: 'none' as const,
}

const preview = await nozle.previewSubscriptionTransition(params)

const result = await nozle.applySubscriptionTransition(
  params,
  'transition-subscription-123-growth-v1',
)
```

Settlement options include:

- timing: `end_of_period` or `immediate`;
- billing anchor: `keep_anchor` or `reset_anchor`;
- proration: `prorate_immediately` or `none`;
- credit action: `credit`, `refund`, `offset`, or `none`;
- refund mode: `prorated` or `full`; and
- final invoice: `generate` or `skip`.

Preview first, present the monetary effect to the merchant, and apply with a stable idempotency key. End-of-period transitions require `creditAction: 'none'`; uncancel does not accept settlement options.

<Warning>
Payment webhooks and the applied transition result are authoritative. Do not unlock paid access from a browser callback alone.
</Warning>

## Trials

A plan with a `trial_period` (in days) starts each subscription in a trial. The trial ends that many days after the subscription starts. `trial_ends_at` on the subscription shows the end (`null` when there is no trial) and `in_trial` is `true` while it runs. `trial_ended_at` holds the time the trial ended. For a trial converted early, it is the time of the conversion.

Change the trial with `PUT /api/v1/subscriptions/{external_id}` on Core. Send `trial` with exactly one of these fields:

| Field | Effect |
|---|---|
| `extend_days` | Adds a positive number of days to the current trial end. |
| `ends_at` | Sets an absolute new end in ISO 8601. It may shorten or extend the trial and must be at least 30 minutes in the future. |
| `convert` | `true` ends the trial now and starts paid billing per the plan. |

`reason` is optional (a string of up to 500 characters). Both the reason and the actor are kept in the activity log.

```bash
curl -X PUT "https://api.nozle.app/core/api/v1/subscriptions/subscription_123" \
  -H "Authorization: Bearer $NOZLE_SECRET_KEY" \
  -H "Content-Type: application/json" \
  -d '{"subscription": {"trial": {"extend_days": 14, "reason": "Needs two more weeks"}}}'
```

To convert now, send `{"subscription": {"trial": {"convert": true}}}`. The response is the subscription with `trial_ends_at` and `in_trial`. See the [Node, Python and Go](/sdks/node/billing#trials) helpers. In GraphQL, `updateSubscription` takes `trial: {extendDays, endsAt, convert, reason}` (exactly one of the three), and the `Subscription` type has `trialEndsAt` and `inTrial`.

### Limits and errors

An extension is at most 90 days. The trial's total length, from the subscription's first start, is at most 365 days. You can extend more than once.

Only a subscription that is in a trial can be changed. A trial that already ended cannot be extended. A change is refused while a plan change is pending, and for externally billed and incomplete subscriptions, as for other updates.

| Status | `code` | Cause |
|---|---|---|
| 422 | `trial_invalid_params` | Not exactly one of `extend_days`, `ends_at` and `convert`, or a bad value. |
| 422 | `trial_not_active` | The subscription is not in a trial, or its trial already ended. |
| 422 | `trial_extension_too_long` | The extension is over 90 days, or the total trial length would pass 365 days. |
| 422 | `trial_end_in_past` | `ends_at` is less than 30 minutes in the future. |
| 422 | `payment_method_required` | `convert` on a pay-in-advance plan when the customer has no way to pay. |
| 409 | `plan_change_pending` | A plan change is pending on the subscription. |

The 422 codes are listed under `error_details.trial`.

### What is billed

Extending changes only the trial end. Nothing is billed by the extension, and billing periods are unchanged.

Converting ends the trial now:

- **Pay in advance:** the first invoice is created immediately.
- **Pay in arrears:** no invoice is created immediately. Usage and the subscription fee are billed at period end, prorated from the conversion date.

The payment follows the normal collection flow. A failed payment does not undo the conversion; it follows the usual [dunning](/guides/billing/dunning).

### Reminders

`subscription.trial_ending` (webhook and email) is sent again for the new end. It is sent once per trial end date, so a reminder is not repeated for the same end. The lead time before the end is 7 days for trials of 14 days or more, 3 days for 7 to 13 days, and 1 day otherwise. A trial shortened to less than the lead time before its end is reminded at the next daily run.

### Webhooks and entitlements

An extension sends `subscription.updated`. A conversion sends `subscription.trial_ended` and `subscription.updated`. There are no new event types.

`subscription.trial_ending` runs daily at 09:00 UTC, before the end. `subscription.trial_ended` comes from the hourly job, up to an hour after a normal end, and immediately on a conversion. A conversion can send `trial_ended` with no earlier `trial_ending`. See [Webhook events](/api/webhook-events#subscription-trial-ending-and-subscription-trial-ended).

An extension does not change `/can` answers or credits. After the trial ends, access follows the plan rules.

## Enforce access in your application

The portal changes billing state; your application enforces feature access using Nozle entitlement checks. The hosted Engine reads the current subscription and database clock for `/can`, denying access at its saved ending even if the termination job has not yet updated the row. Keep is visible after commit without waiting for the old subscription-cache refresh.

## Independent plans per Entity

One customer can own multiple Entity subscriptions with different plans and billing intervals:

```text
Customer: workspace_123
├── user_42 → Pro monthly
└── user_43 → Max annual
```

Each Entity receives a stable subscription identity and follows the standard checkout, invoice, renewal, transition, and cancellation lifecycle. Operations are isolated: upgrading, downgrading, or cancelling one Entity does not mutate another Entity.

Nozle revalidates the live Entity before checkout. Suspended Entities fail closed. Suspending does not cancel the subscription: cancel it yourself to stop billing. See [Entity Subscriptions](/api/entity-subscriptions).

For seat-pool purchases, bulk Entity checkout combines multiple Pro/Max-style Entity subscriptions into one invoice and one payment. The first successful paid Entity checkout can establish an anniversary billing anchor for the customer; later Entity purchases align to that anchor and prorate their initial period.
