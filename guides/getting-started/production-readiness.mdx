---
title: Production integration checklist
description: What to verify before real customers use your Nozle integration
---

Run the integration in your [sandbox](/guides/getting-started/sandbox) first, with sandbox keys (`sk_nozle_test_`) and your payment provider's test credentials. The sandbox is a separate organization, so test customers, events and payments never mix with live activity, and it sends no customer emails. Then repeat the checks that matter in live with live keys. Tick each item only after you have seen it work.

## Keys and setup

- [ ] Secret keys (`sk_`) are only on your server and read from the environment. The browser only has a publishable key (`pk_`), which can read the plan catalog and nothing else. See [authentication](/api/authentication).
- [ ] Production runs with live keys (`sk_nozle_`, not `sk_nozle_test_`), and its responses carry `X-Nozle-Livemode: true`. Nothing is copied from the sandbox: the plans, features and webhook endpoints you need exist in live. See [Go live](/guides/getting-started/sandbox#go-live).
- [ ] You use the latest Node.js, Python, Go and React SDK releases. See each SDK's installation page for the current versions.
- [ ] The feature, plan, customer and active subscription exist before events are sent. The event name equals the feature code exactly.
- [ ] Customer identity comes from your authenticated backend, never from the browser.
- [ ] If a customer can hold more than one active subscription, you pass the subscription explicitly.

## Events

- [ ] Each business event has a stored transaction ID, timestamp and payload. A retry sends all three unchanged; a new ID creates a new event. See [idempotency](/api/idempotency).
- [ ] You send an event, then read usage back and see the expected count. Acceptance of a request is separate from asynchronous usage processing, so read after a few seconds.
- [ ] Batches have at most 100 events, and you resend a whole batch after an unreadable failure. See [events](/api/events).
- [ ] You tested a wrong event name: it is accepted but never counted.

## Decisions and credits

- [ ] `can()` is treated as a point-in-time decision, not a quota reservation. A `503` (`usage_unavailable`) is handled as an unavailable decision, never as permission or zero usage, with a bounded retry. You keep the request ID for support. Entitlement changes can take about a minute to refresh.
- [ ] Credit-backed work uses [`usage.track`](/api/usage-track) with a stable idempotency key per unit of work, and a denial (`allowed=false`) stops the work.
- [ ] Initial subscription credit grants are asynchronous: you wait for the expected balance before admitting credit-backed work.

## Errors and retries

- [ ] Your code retries only network errors, timeouts, `5xx` and `503` with `Retry-After`, always with the same key and payload. It does not retry `4xx`. See [errors](/api/errors).
- [ ] You forced each of these once and saw the right behaviour: a bad key (`401`), a `pk_` key on a protected call (`403`), an unknown customer (`404`), the same idempotency key with a different request (`409`), and a network failure mid-request.
- [ ] A retry from a new process passes an explicit `timestamp` for `usage.track`, because the SDK only remembers the time it filled in for the client that sent it.

## Webhooks

- [ ] Your endpoint uses the `standard` signature scheme, and your receiver verifies the signature and the 5-minute timestamp window on the raw body, deduplicates on `webhook-id`, answers `2xx` within 10 seconds (a redirect counts as a failure) and returns `200` for events it does not handle. See [receive webhooks](/api/receive-webhooks).
- [ ] You do not rely on delivery order, and you read the object from the API when you need its latest state.
- [ ] If one receiver handles live and sandbox deliveries, it branches on the payload's `livemode` before acting.

## Cost rating

- [ ] The Cost Rules and composition for the usage you price are configured and published.
- [ ] A test transaction shows its rated amount. An event with `uncosted` status is recorded but has no rated cost yet: review its reason before it reaches financial reports.

## Payments

- [ ] Your payment provider is connected and the flows your product exposes work: successful checkout, decline and retry, subscription changes, cancellation, renewal, refunds and authentication challenges. A free subscription or a rendered billing component does not test payment settlement.
- [ ] Your production checkout origins are registered for your organization (dashboard **Developers > Checkout return**), and a default return URL is set. See [return URLs](/guides/billing/checkout#return-urls-and-your-organizations-origins).

## Operations

- [ ] You monitor your request errors, processing lag and reconciliation differences, and you have tested email delivery, any SSO provider you enable, and your own backup and restore.
- [ ] You measured your own workload before promising a capacity or latency SLA. Request acceptance throughput alone does not establish processing capacity.
