Nozle does not support self-hosting today, and Nozle Cloud sets all of these for you. This page lists the variables that Core and Engine read, for people who develop on Nozle itself.

## Core

Core reads its database, Redis, public URL and SMTP settings from environment variables with a Core-specific prefix. Take the exact names from the Core repository (`docker-compose.yml` and `api/config/environments/production.rb`), not from this page. The names below are the generic ones that Core does not read, so do not use them:

`API_URL`, `SMTP_ADDRESS`, `SMTP_PORT` and `SMTP_FROM_EMAIL`.

Without the SMTP variables Core reads, no email is sent: sign-up verification codes and invoice emails never arrive. `DATABASE_URL` and `REDIS_URL` are the names Core uses for PostgreSQL and Redis. In Nozle Cloud the dashboard is at [app.nozle.app](https://app.nozle.app).

### Core browser origins

| Variable | Description |
|----------|-------------|
| `CORS_ALLOWED_ORIGINS` | Comma-separated list of the browser origins that may call Core, for example `https://app.example.com,https://portal.example.com`. Each entry is an exact origin: scheme, host and optional port, no path. Values are lower-cased and a default port or trailing slash is dropped. |
| Dashboard front URL variable of Core | Public URL of the dashboard. When `CORS_ALLOWED_ORIGINS` is unset, Core allows only the origin of this URL (its path is ignored). |

Core denies by default. A browser call from an origin that is not in the list gets no CORS headers, on the preflight too, so the browser blocks it. Server-to-server calls with an API key are not affected. When neither variable gives a valid origin, Core allows no browser origin outside development and test, and prints a warning at boot that names any value it ignored. Development and test also allow `localhost` and `127.0.0.1` on any port.

Set `CORS_ALLOWED_ORIGINS` to every browser origin that calls Core (the dashboard and any app of yours) before you upgrade to Core 5.0.0. Core used to answer every origin with `Access-Control-Allow-Origin: *`.

The customer portal is the exception: `POST /graphql` from any origin is allowed when it carries the `customer-portal-token` header, so the [billing portal](/sdks/react/billing-portal) keeps working on your customers' sites. Credentials (cookies) are never allowed. CORS does not authenticate a caller: the portal token or an API key does.

### Core upgrade steps

These steps are for the operator of a Core deployment. Merchants who use Nozle Cloud need none of them.

**Core 6.0.0 (no former-prefix names in the public API).** Stripe metadata changes from the former-prefix keys to `nozle_*` (see [Stripe](/integrations/stripe#metadata-on-stripe-objects)). A Checkout Session opened before the deploy and paid after it is not applied: the payment is logged and ignored, so its invoice or payment request stays pending and dunning or a retry can charge the customer again. Plan upgrades settle later through their reconcile jobs. Run this command before the deploy and once more right after it, as a one-off job from the 6.0.0 image (it needs no migration):

```bash
bin/rails payments:open_checkout_sessions
```

The dry run lists open Stripe Checkout Sessions, each labelled `tracked` (Core stored the session id) or `customer` (not stored, but it belongs to a Stripe customer recorded for the connection; this can include sessions your own app opened). Add `APPLY=1` to expire the `tracked` ones. Expire the `customer` ones only after you have checked them, with `APPLY=1 INCLUDE_CUSTOMER_MATCHES=1`, or settle those payment requests by hand. A session paid before it is expired settles as before.

**Core 7.0.0 (API keys looked up by digest).** Core finds an API key by the SHA-256 digest of its token, which it stores with the key's type prefix and last 4 characters. The migration computes them for every existing key, so existing keys keep working, and it removes keys from the recorded change history. Deploy the dashboard that shows a new or rotated key once before Core 7.0.0: older dashboards read the key back to copy it, and that now fails. After every pod runs Core 7.0.0, run the digest backfill once more so keys created by older pods during the rollout get their digest. It changes only rows whose stored key and digest disagree, so it is safe to repeat:

```bash
bin/rails runner 'require Rails.root.join("db/migrate/20261026060503_backfill_api_key_digests").to_s
  ActiveRecord::Base.connection.execute(BackfillApiKeyDigests::BACKFILL_SQL)'
```

This is step 1 of 2: the full key is still stored in this release.

## Nozle API Keys

Regardless of deployment model, you need Nozle API keys to use the SDKs:

| Key Type | Prefix | Use |
|----------|--------|-----|
| Publishable | `pk_nozle_` | Client-side public plan catalog only |
| Secret | `sk_nozle_` | Server-side (Node.js, Python, Go SDKs) |

Create your keys in the Nozle dashboard at [app.nozle.app](https://app.nozle.app) under **Developers > API keys**. There are no separate live and test keys.

## Engine: browser settings

| Variable | Description |
|----------|-------------|
| `CORS_ORIGIN` | Transitional single-origin setting retained for older API replicas during a rolling deployment. |
| `CORS_ALLOWED_ORIGINS` | Comma-separated browser-origin allowlist, for example `https://app.example.com,https://portal.example.com`. |

The Engine has no checkout return settings. `CHECKOUT_RETURN_URL` and `CHECKOUT_RETURN_URL_ALLOWED_ORIGINS` are no longer Engine settings and are ignored. Core validates checkout return URLs against each organization's own origins (**Developers > Checkout return** in the dashboard) and its deployment list, `CHECKOUT_RETURN_URL_ALLOWED_ORIGINS`. Move any origin that only the Engine list allowed into the organization's settings before you upgrade. CORS controls which browser origins may call an endpoint; it does not authenticate callers or make a return URL safe.
